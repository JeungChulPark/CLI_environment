# objpose — SLAM 기반 객체 위치 추정 + localhost 시각화

두 대의 RealSense(SLAM 카메라, SAM 카메라)로 녹화한 `Dataset/260826_etri_eightcircle_dark`를
입력으로, **Mac(219.113)의 ORB-SLAM3 위치**와 **PC(219.100)의 SAM-6D 객체 포즈**를 시간 동기화·보간해
SLAM 지도 좌표계의 객체 위치를 `http://localhost:8765`에 실시간으로 보여준다.

```
PC 219.100                                                     Mac 219.113
hub.py ── ssh -R 17001 ─ "run_slam.sh --features 2000 --mode live" ─► slam_stream (ORB-SLAM3 f2000)
   ▲                                                               │ SLAM 원본 세션 1x 재생
   └──────────── pose JSON (t_ns, state, T_wc) ◄── TCP 터널 ───────┘
   │
   ├─ SAM 원본 세션 1x 재생 ─► 공유메모리 ─► sam6d_infer.py (수정 없음)
   ├─ 결과 ─► fusion.py:  T_w_obj = T_w_slam(s)·X·T_sam_obj,  T_sam_obj(t) = (T_w_slam(t)·X)⁻¹·T_w_obj
   └─ localhost:8765 ─ 영상(객체 박스·3축) + 3D 지도(월드 3축·궤적·객체 박스) + 상태
```

## 실행

```bash
# (한 번) 카메라 RT 추정 — Mac ORB-SLAM3 f2000 궤적 두 개(objpose/rt/*_traj_tum.txt)로
/home/jucpark/anaconda3/envs/sam6d/bin/python objpose/pc/estimate_rt.py

# 전체 실행 — Mac 에 SLAM 명령을 내리고 SAM-6D 를 띄운 뒤 같은 데이터 시각에서 동시에 시작
bash objpose/run.sh                     # 브라우저: http://localhost:8765 , 종료: Ctrl+C
```

주요 옵션(`objpose/pc/hub.py --help`): `--duration-s`, `--start-s`, `--rate`, `--overlay-max-age`(기본 10 s),
`--display-delay`(기본 0.25 s), `--sam-feed-hz`(기본 10), `--no-mac`(외부 SLAM 클라이언트 대기).

## 동기화 규약

- 모든 시각은 **SLAM 호스트 시계**로 통일하고, 프레임 시각은 **color 메타데이터 `timestamp`**(`pc/clock.py`)를 쓴다.
  SLAM 세션의 `rgbd_timestamp_associations.json` 스탬프는 프레임 드롭 때문에 녹화 구간에 따라 **−2.1 ~ +3.8 s** 틀어져 있어 쓰지 않는다
  (Mac `slam_stream --time-source frame` 이 기본, 허브도 `frame_idx` 로 다시 매긴다).
- SAM 시각 = SAM 메타데이터 시각 − 18 225 662 057 ns(피어 시계 차) + τ(−48 ms, SAM "System Time" 은 도착 시각이라 늦음; RT 추정에서 측정).
- SAM-6D 추정 프레임 시각 s 의 SLAM 포즈는 앞뒤 포즈(간격 ≤ 0.25 s) 사이 SE(3) 보간.
- 추정 사이의 표시 프레임 t 에서는 객체를 월드에 고정하고 SLAM 움직임으로 카메라 기준 포즈를 옮긴다.
- 지도 번호(map_id)가 바뀔 때만 포즈 버퍼를 비운다(루프 클로저는 같은 지도라 유지).
- **키프레임 기준 객체** (`ORB_POSE_CONSISTENCY_FOR_SAM6D.md` 권장 2): 포즈마다 기준 키프레임(`ref_kf`, `T_w_kf`)을 받고
  객체는 `T_kf_obj` 로 저장한다. Mac 이 1 s 마다·루프 클로저 직후(+0.5 s, +3 s) `kf_update` 로 전체 키프레임 포즈를 보내면
  월드 좌표(`T_w_obj = T_w_kf(최신)·T_kf_obj`)와 카메라 포즈를 다시 계산한다. 컬링된 키프레임은 직전 스냅샷으로 가장 가까운
  키프레임에 옮긴다. 루프 클로저 ±1 s 추정은 표시하고, 깨끗한 앵커를 대체하지 않는다.

## 카메라 RT (오프라인, `pc/estimate_rt_offline.py` → `rt/X_slam_sam.json`)

1. 각 카메라 궤적 평면의 법선 = "아래" 방향 (평면 이탈 RMS SLAM 0.6 cm / SAM 0.2 cm)
2. 수평 오프셋·yaw: 수평화한 두 궤적의 **상대 움직임**(0.5–4 s 창)으로 SE(2) hand-eye (AX = XB), Huber
3. 높이 차: 각 카메라 depth 의 바닥 평면(RANSAC, 법선 제약)

결과(2026-09-13): 잔차 중앙 0.41 cm, 구간 편차 ≤ 6.6 mm / 0.15°, 부트스트랩 sd 약 2 mm / 0.05°, URDF 대비 3.5 cm / 0.54°.
기각한 방법: 두 지도 AX = ZB(수평 회전만이라 조건 불량), SAM 을 SLAM 지도에 localization(지도 휘어짐, 잔차 p90 12 cm).

### 객체 메모리 (`pc/memory.py`, v5)

`objectmemory_ws` 의 `StreamingObjectMemory`(연관 게이트, 임시→활성 승격, 시야 기반 존재 확률, SE(3) 융합, 다중 개체)를
그대로 쓴다. SAM-6D 가 처리한 모든 프레임(검출 0 건 포함)을 키프레임 기준 카메라 포즈와 함께 보관하고, `kf_update` 로
키프레임이 바뀌면 보정된 좌표로 처음부터 재생해 메모리를 다시 만든다(308 프레임 75 ms). 연관은 **위치만**(0.15 m)으로 한다 —
상자형 물체는 SAM-6D 회전이 180° 뒤집혀 회전 게이트(45°)가 한 물체를 두 개체로 쪼갰다.

v5 결과: 남은 개체 **8 개 = 8 종**, 각 개체 위치가 그 물체 관측 중앙값과 0.1–1.3 cm. 1.84 m 떨어진 가짜 `milk` 관측 4 건은
전부 삭제. 끝에 시야 밖 물체는 `remembered`(기억) 상태로 남아 지도에만 흐리게 표시된다.
(그 가짜 `milk` 는 `--pd-base` 를 0.08 로 낮춘 뒤 다시 살아남는다 — 아래 **중복 인스턴스 억제** 참고.)

존재 확률 파라미터(2026-09-19): 기본값 `--pd-base 0.08 --clutter-ratio 0.01`. 모든 프레임이 포즈를 받게 된 뒤
(260901_cbnu_eightcircle) SAM-6D 가 시야 안 물체를 검출하는 비율은 프레임당 6–20 %(대부분 7–9 %)였다. 이전 값
0.15 / 0.03 은 9.2 % 이상을 요구해 8 개 중 5 개가 `lost` 로 끝났고, 같은 녹화를 재생하면 0.08 / 0.01 에서는 8 개 모두
`active` 로 남는다. 대신 치운 물체가 `lost` 가 되기까지 시야 안 미검출이 약 14 → 27 프레임으로 늘어난다.

검출 거리 한계(2026-09-19): `--pd-max-range 1.5`(m). 화면 안에 있어도 카메라에서 1.5 m 보다 먼 물체는 못 본 것을
미검출로 세지 않는다. SAM-6D 는 `Mugcup_high`·`Sikhye_high` 를 0.5–0.6 m 안에서만 잡는데(다른 물체는 ~2.2 m 까지),
`260901_cbnu_bigeightcircle` 처럼 2–4 m 밖에서 오래 바라보는 경로에서는 그 프레임이 전부 미검출로 쌓여 관측 2–3 회인
두 물체가 50 초 만에 `lost` → 삭제(관측 5 회 미만)됐다. `tune_memory.py --max-range 0 1.5 2.0 2.5` 로 재생하면 1.5 m 에서
LiDAR 실행의 두 물체 표시 비율이 37 / 46 % → 83 / 82 %, ORB-SLAM3+IMU 실행의 머그컵·식혜·초코가 55 / 54 / 15 % → 82 %
가 되고 eightcircle 실행은 그대로다. 대가로 치운 물체는 1.5 m 안으로 다가가야 `lost` 가 되고, 멀리서 본 미검출로
지워지던 17 cm 어긋난 중복 인스턴스(bigeightcircle ORB-SLAM3+IMU 의 식혜)가 남는다.

## 중복 인스턴스 억제 · feature 수 · 루프 클로징 (2026-09-20)

### 중복 인스턴스 억제 (`hub.py --dup-ratio`, 기본 5)

SAM-6D 가 다른 물체를 아는 클래스로 최고점에 읽어버리는 일이 있다. `260826_etri_eightcircle_dark` 에서 진짜 `milk`
(`z` 0.48)와 **1.8 m 떨어진 `z` 2.30** 에 두 번째 `milk` 를 69 프레임 중 4 프레임에 놓았고, 그 4 건의 점수는
0.96–1.00 이었다. 연관 게이트(0.15 m)는 m 단위로 떨어진 둘을 합칠 수 없고 점수로도 못 가르는데, 진짜 물체를
살리려고 `--pd-base` 를 0.08 로 낮춘 뒤로는 존재 필터도 이걸 안 지운다 — 확률 0.92 로 화면에 남았다.

가르는 것은 **관측 수**다. 같은 이름의 다른 랜드마크가 `--dup-ratio` 배보다 많은 관측을 가지면 표시에서 감춘다
(`memory.py ObjectMemory._mark_duplicates`). 값이 **클수록 관대**하다(임계 = 최대/ratio). 억제된 랜드마크는
플래그와 함께 `summary.json` 에 남아 사후 확인이 되고, `--dup-ratio 0` 으로 끌 수 있다.

기본값이 5 인 이유: 260826 세 실행에서 진짜가 유령을 **65:3, 72:3, 68:4** 로 앞섰다 — 비율 21.7 / 24.0 / **17.0**.
처음 고른 20 은 재생에서는 걸렀지만 첫 실시간 실행에서 17.0 을 놓쳤다. 재생 5 실행 모두 ratio 3 까지 내려도 멀쩡한
물체는 하나도 안 걸린다(관측이 가장 적은 260901 `choco_hazelnut_high` 4 회는 같은 이름 랜드마크가 자기뿐이라 비교
자체가 없다). 5 면 중복이 표시되려면 선두의 1/5 이 필요하고, 관측된 유령은 1/17 이다.

검증 — 재생 5 실행 + 실시간 4 실행. 260826 f2000·f4000 은 각각 정확히 1 개(유령)를 억제하고, 260901 f2000·f4000 은
0 개를 억제한다. 물체별 표시 비율과 끊긴 구간 수는 **40 칸 전부 변화 없음**.

버린 대안: **관측 시간 분산 게이트**. 오프라인으로는 깨끗해 보였지만(유령 span 3.5–4.7 s, 진짜 213 s 이상) 유령이
아니라 재방문 간격을 벌했다 — 260901 의 큰 8 자 경로에서 멀쩡한 물체가 68 % → 26 % 로 무너졌다.

### `--features 2000` vs `4000`

같은 코드·설정에서 feature 수만 바꿔 두 데이터셋에서 실행했다. IMU 는 260826 에 없으므로 양쪽 다 끄고 비교했다.

| | 260826 dark | 260901 cbnu |
|---|---|---|
| 추적 시간 f2000 → f4000 | 10.05 → 16.6 ms (**+65 %**) | 12.06 → 21.3 ms (**+77 %**) |
| 두 실행 궤적 정합 RMSE | 0.44 cm | 2.32 cm |
| 관측 흩어짐 중앙 | 0.92 → 0.88 cm | 1.76 → 1.56 cm |
| 보간 예측 0–3 s 중앙 | 0.48 → 0.44 cm | 1.79 → 1.88 cm |
| SAM-6D 적중률 | 12.7 → 12.7 % | 51.8 → 52.1 % |
| 표시 객체 | 8 → 8 | 8 → 8 |

정확도 차이는 0.04–0.2 cm 로 측정 잡음과 구분되지 않고 방향도 데이터셋마다 갈리는데, 추적 시간만 65–77 % 늘어난다.
(루프 클로징 사고는 feature 수와 무관하다 — 아래 40 회 실측 참고.)
**이 두 데이터셋에서는 f2000 이 맞다.** (어두운 260826 의 SAM-6D 적중률 12.7 % 는 260901 의 52 % 와 4 배 차이인데,
그래도 메모리는 양쪽 다 8 종을 유지한다.)

### 루프 클로징이 가끔 지도를 망가뜨린다 — 40 회 실측, 판별자 없음 (2026-09-21)

`260901_cbnu_bigeightcircle` 을 f4000 으로 20 회씩 두 번, 모두 같은 입력·설정으로 돌리고 LiDAR(KISS-ICP,
루프 클로징 없음)를 독립 기준으로 판정했다.

| 배치 | 오차 중앙 범위 | 파손(30 cm↑) | 열화(5–30 cm) | `loop≥4` |
|---|---|---|---|---|
| 1차 (`_loop01`–`20`) | 2.1 – **54.4** cm | **2 건** | 2 건 | 7 건 |
| 2차 (`_corr01`–`20`) | 2.2 – **6.8** cm | 0 건 | 2 건 | 6 건 |

1 차 파손 2 건은 LiDAR 대비 중앙 17.0 / 54.4 cm 였고, 후자는 p95 218 cm 에 표시 객체가 8 → 13 개로 늘었다
(지도가 흩어지며 같은 물체가 여러 자리에 등록되는데, 관측 수가 비슷해 `--dup-ratio` 로는 못 거른다 — 중복 억제는
SAM-6D 오검출용이지 SLAM 파손용이 아니다). 오프라인으로 그 closure 직전까지의 `kf_update` 만 재생해 보면 네 실행 모두
**2.1–2.5 cm 로 돌아온다**. 즉 문제의 closure 들은 드리프트를 걷어낸 것이 아니라 멀쩡한 지도를 망가뜨렸다.

**`LOOP_GAP` 에 찍히는 어떤 값도 결과를 예측하지 못한다.** 다섯 가지를 차례로 기각했다.

| 값 | 기각 근거 |
|---|---|
| `kf_max_correction_cm` | 361 cm 인 실행이 2.2 cm(최선), 301 cm 인 실행이 6.8 cm(최악) |
| `gap_m` | 대부분이 **물리적 거리**다. 소스 주석의 "accumulated drift" 는 틀렸다 |
| `\|sim3t\|` | `Scw` 의 평행이동 크기 = **보정된 카메라 중심의 원점 거리**. 매칭 키프레임이 지도 어디에 있느냐를 잴 뿐이라 월드 원점에 의존한다 |
| `corr_m` | 보정이 카메라를 실제로 옮긴 거리(2026-09-21 추가). `loop≥4` 6 건이 2.97–3.16 으로 같은데 결과는 2.2–6.8 cm 로 갈린다 |
| `resid_m` | 보정 후 매칭 키프레임과의 거리. 2.52 인 실행이 2.6 cm, 0.95 인 실행이 6.8 cm 로 역전 |

`gap_m` 이 드리프트가 아니라는 것은 LiDAR 로 직접 쟀다 — closure 양쪽 키프레임의 **실제** 거리를 LiDAR 궤적에서
읽으면 14 건 중 13 건이 `gap_m` 과 0.20–0.27 m 차이다. 그 차이가 진짜 드리프트이고, 나머지는 두 카메라가 서로 다른
자리에서 같은 물체 무리를 본 물리적 간격이다(루프 클로징의 제약은 "같은 위치"가 아니라 "같은 맵 포인트 관측"이다).
그래서 `gap_m` 3.39 는 "드리프트 3.39 m" 가 아니라 "2.98 m 떨어진 두 지점 + 드리프트 0.40 m" 다.

**문제는 closure 의 기하가 아니라 스레드 타이밍으로 보인다.** 두 배치의 유일한 차이는 `LoopClosing.cc` 에 로그 두 줄
(`corr_m`, `resid_m`)을 추가하고 재빌드한 것인데 — 계산에는 영향이 없다 — 파손이 2 건에서 0 건으로 사라졌다. 같은
입력으로 20 회 중 16 회가 2 cm 대이고 몇 회만 망가지는 것도 같은 그림이다. 로깅이 바꾼 미세한 타이밍이 경합 양상을
바꾼 것으로 보이며, 그렇다면 closure 지표를 아무리 봐도 예측이 안 되는 것이 당연하다.

입력 데이터 문제는 아니다. 같은 녹화로 40 회 중 36 회가 LiDAR 와 2.1–2.6 cm 로 맞고, 드리프트도 0.20–0.40 m 로
일정하다. 입력이 깨졌다면 매번 망가져야 한다.

지표 기반 거부 게이트는 만들지 않았다. 대안은 (1) 스레드 타이밍을 로깅해 경합 지점을 찾기, (2) 실행이 끝난 뒤
파손을 판정해 자동 재실행(실시간에는 못 쓴다), (3) 루프 클로징이 없는 `--slam lidar`(KISS-ICP) 쓰기.

### 비교 도구가 컬링 리다이렉트를 건너뛰던 것 (`compare_runs.py`, `tune_memory.py`)

두 도구 모두 마지막 `kf_update` 의 키프레임 목록에 `ref_kf` 가 있는지만 보고 보정된 지도를 만들었다. 로컬 매핑은
중복 키프레임을 컬링하고 `KeyframeMap` 은 컬링된 id 를 가까운 생존 키프레임으로 재앵커링하는데(`fusion.py resolve`
가 실시간으로 따라가는 경로), 멤버십 검사는 그 리다이렉트를 통째로 놓친다. 260901 실행에서 포즈의 **27.5 %** 가
보정 없이 live(드리프트 포함) 좌표로 남았고, LiDAR 대비 3 cm 이내인 두 지도가 서로 **6.0 cm RMSE** 로 보였다.

이제 두 도구 모두 모든 업데이트를 `KeyframeMap` 으로 재생하고 `resolve()` 를 쓴다. 미보정 포즈가 27.5 % → **3.5 %**
로 줄고 같은 비교가 **2.3 cm** 가 된다. `compare_runs` 는 제외한 포즈 수를 `unrefined_poses` / `unrefined_dropped`
로 보고하고, `live_vs_final` 을 보정된 포즈만으로 계산한다(미보정 포즈는 차이가 구조적으로 0 이라 중앙값을 끌어내렸다).
`tune_memory` 는 그동안 메모리 재생에 드리프트가 남은 카메라 포즈를 먹이고 있었다 — 다만 위 `--dup-ratio` 결론은
수정 전후가 같다.
