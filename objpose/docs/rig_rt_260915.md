# 2026-09-15 리그 외부 파라미터 재추정 (`objpose/rt/260915/`)

260915 녹화 3종(`260915_dense`, `260915_distance`, `260915_eightcircle`)에 대해 카메라–카메라 RT(`T_slam_sam`)와
라이다–SAM 카메라 RT(`T_lidar_sam`)를 다시 추정하고, 오늘까지 쓰던 260910 RT와 비교했다.

**결론: 리그는 바뀌었다 — 단, 움직인 것은 SLAM 카메라 하나다.**
라이다↔SAM 카메라 RT는 260910 과 **0.3 cm / 0.61°** 로 같고, 라이다↔SLAM 카메라 RT만 **4.0–5.3 cm / 0.7°** 달라졌다.
그 결과 카메라–카메라 RT 는 260910 대비 **5.0 cm / 1.74°** 이동했다. `run_one.sh` 의 260915 블록을 새 RT 로 교체했다.

## 1. 입력과 방법

### 데이터 (NAS `/mnt/synology/Dataset/data_slam_converted/<세션>`)

| 세션 | SLAM/SAM 프레임 | 길이 | 궤적 길이 | 요(yaw) 범위 | 라이다 메시지 | 중복 제거 후 | 실제 사용 스캔 |
|---|---|---|---|---|---|---|---|
| 260915_eightcircle | 3,860 / 3,861 | 128.7 s | 25.0 m | **1,125.6°** | 5,104 | 2,552 | 1,276 (10 Hz) |
| 260915_dense | 4,093 / 4,095 | 136.5 s | 26.3 m | **1,126.8°** | 5,414 | 2,707 | 1,354 (10 Hz) |
| 260915_distance | 5,710 / 5,710 | 190.4 s | 30.8 m | 192.8° | 7,548 | 3,774 | 1,887 (10 Hz) |

시각은 세 세션 모두 **변환본 헤더 스탬프 = 하나의 시계**다(`info.json` `clock.method = manifest_scheduled_start`,
SAM 보정량 −0.41 ~ −0.48 ms 는 변환기가 이미 적용). 실제로 hand-eye 가 찾은 τ 가 0.000 / +0.004 / +0.002 s 로,
260826(τ = −48 ms)과 달리 추가 보정이 필요 없음을 확인했다.

`dense` 는 "정지에 가까운" 녹화가 아니라 **eightcircle 과 사실상 같은 수준의 회전량**(요 1,127°)을 가진 조밀 스캔이고,
`distance` 만 요 범위 193° 의 직선 주행이다. 평면 hand-eye 의 지렛대(tx, ty)는 요 변화량으로 관측되므로
**주 데이터셋 = eightcircle, 교차검증 = dense, 약한 교차검증 = distance** 로 정했다.

### 카메라 내부 파라미터 — 새 yaml 이 필요 없었다

`info.json` 의 K 는 기존 yaml 과 다르다(예: SAM 카메라 fx 385.134 vs yaml 384.925, cx 320.789/cy 243.438).
그러나 `mac_slam/slam_stream.cc` 의 `settings_with_camera()` 가 **세션 bag 의 `camera_info` 로 `Camera1.*` 와
`Camera.width/height` 를 통째로 덮어쓴다**. 실행 로그로 확인:

```
[slam_stream] converted bag: 3860 pairs ... K fx=387.023 fy=386.452 cx=322.784 cy=250.280 D=[-0.056362 ...]  (SLAM)
[slam_stream] converted bag: 3861 pairs ... K fx=385.134 fy=384.563 cx=320.789 cy=243.438 D=[-0.055259 ...]  (SAM)
```

즉 yaml 은 `RGBD.DepthMapFactor 1000`, `Stereo.ThDepth 40`, `Stereo.b 0.0745`, ORB 파라미터만 제공한다. 새 yaml 을 만들지 않고
기존 두 파일을 그대로 썼다(260910 과 완전히 같은 조건 유지). 다만 **기기 배정은 260826 과 반대**다:
260915 의 SLAM 폴더 카메라(cx 322.784)가 `settings/sam_camera_nf2000.yaml` 의 기기이고, SAM 폴더 카메라(cx 320.789)가
`settings/orbslam3_260826_dark_nf2000.yaml` 의 기기다. 260910 도 같은 배정이다.

### 라이다 bag — 40 Hz 로 보이는 이유 (중요)

260915 의 `/velodyne_points` 는 260910(10 Hz, 1,583 스캔)과 달리 ~40 Hz 다. 실제 내용은:

1. **모든 메시지가 두 번 녹화돼 있다** — 바이트 단위로 동일(md5 일치), rosbag2 구독이 둘.
2. 남은 고유 스탬프도 **독립된 10 Hz 퍼블리셔 2개**가 번갈아 낸 것이다(전부 29,184 점 = 16 링 × 1,824 방위 = 완전 1회전).
   두 퍼블리셔의 간격은 eightcircle 6.6 ms, distance 15.9 ms, dense 82.3 ms.

그대로 KISS-ICP 에 넣으면 스캔 간격이 6.6 ms / 94 ms 로 번갈아 들어가 등속 deskew 가 깨진다. 그래서
`objpose/rt/260915/kiss_260915.py` 가 **헤더 스탬프로 중복 제거 → 홀/짝 분리로 퍼블리셔 하나만 사용**한다.
결과는 260910 과 같은 깨끗한 10 Hz 스트림(간격 중앙 100.865 ms, 표준편차 0.09–0.24 ms)이다.

| 세션 | 사용 스캔 | ms/스캔 | 궤적 길이 | 귀환 오차 |
|---|---|---|---|---|
| eightcircle | 1,276 | 9.05 | 22.80 m | 14.2 cm |
| dense | 1,354 | 9.08 | 24.74 m | 27.8 cm |
| distance | 1,887 | 9.85 | 29.82 m | 28.9 cm |

### 실행 명령

```bash
# 1) ORB-SLAM3 오프라인 궤적 (이 PC, ~/objpose/build/slam_stream, 세션당 약 3.5분)
for s in eightcircle distance dense; do
  for cam in SLAM SAM; do
    ~/objpose/run_slam.sh --session /mnt/synology/Dataset/data_slam_converted/260915_$s/$cam \
      --settings objpose/mac_slam/settings/<sam_camera_nf2000|orbslam3_260826_dark_nf2000>.yaml \
      --features 2000 --time-source frame --mode offline \
      --out objpose/rt/260915/${s}_<slam|sam>_orb_tum.txt
  done
done

# 2) 라이다 KISS-ICP (kiss-icp 1.3.0 venv: python3 -m venv ~/objpose_kiss_venv && pip install kiss-icp==1.3.0 numpy scipy)
~/objpose_kiss_venv/bin/python objpose/rt/260915/kiss_260915.py \
    --session <lidar dir> --out objpose/rt/260915/kiss_<세션>

# 3) 카메라–카메라 RT (pc/estimate_rt_offline.py 와 같은 방법, 변환본 세션용 래퍼)
$SAM6D_PY objpose/rt/260915/fit_cam_rt_260915.py --session 260915_<세션> --floor-frames 1600 \
    --slam-traj .../<세션>_slam_orb_tum.txt.optimized.txt --sam-traj .../<세션>_sam_orb_tum.txt.optimized.txt \
    --out objpose/rt/260915/fit_cam_<세션>_f1600.json

# 4) 라이다–카메라 RT (기존 도구 그대로)
$SAM6D_PY objpose/lidar/estimate_lidar_cam_rt.py --dataset <세션 dir> --camera SAM|SLAM \
    --cam-traj .../<세션>_<sam|slam>_orb_tum.txt.optimized.txt \
    --lidar-traj objpose/rt/260915/kiss_<세션>/base_tum.txt \
    --out objpose/rt/260915/T_<sam|slam>cam_lidar_<세션>.json

# 5) 검증 (끝난 실행의 SAM-6D 추정을 다른 RT 로 다시 배치)
$SAM6D_PY objpose/rt/260915/replace_rt.py objpose/output/one_260915_distance_orb_f3000_260915_162409 \
    old_260910=objpose/rt/260910/X_slam_sam_260910.json new=objpose/rt/260915/X_slam_sam_260915.json \
    --out objpose/rt/260915/validate_replace_distance_run.json
```

`fit_cam_rt_260915.py` 는 `pc/estimate_rt_offline.py` 의 함수(`trajectory_down`, `levelling`, `planar`,
`rel_pairs`, `solve_planar`, `floor_heights`)를 그대로 import 해서 쓴다. 다른 점은 두 가지뿐이다:
바닥 평면을 원본 SDK 세션(`RsSession`)이 아니라 **변환본(`pc/conv_session.ConvSession`)**에서 읽고,
두 카메라가 이미 같은 시계라 `SAM_MINUS_SLAM_CLOCK_NS` 보정을 하지 않는다.

## 3. 교차 검증 — 세션 간 / 260910 대비 (평행이동 cm / 회전 °)

**direct** = 평면 hand-eye + 바닥 높이(`estimate_rt_offline` 방법), **composed** = 라이다–SLAM카메라 RT ∘ (라이다–SAM카메라 RT)⁻¹.

읽는 법:
- **회전이 많은 두 세션(eightcircle · dense)은 서로 2.1 cm / 0.49° 로 일치**하고, 260910 과는 5.0–5.6 cm / 1.7–1.8° 로 벌어진다.
  즉 260910 과의 차이는 방법의 재현 산포(2 cm)의 2.5배이며 **실제 변화**로 보아야 한다.
- distance 는 나머지와 4.7–10 cm 어긋난다(요 범위 193°). 지렛대가 관측되지 않아 신뢰하지 않는다.
- 260910 자신의 direct(=260826 RT) vs composed 차이가 이미 2.66 cm / 1.63° 였다(README 의 "2.7 cm / 1.6°").
  같은 교차검증이 260915 에서는 eightcircle 4.28 cm / **0.04°**, dense **0.46 cm / 0.04°** 로, 회전은 훨씬 잘 맞고
  남은 차이는 전부 높이축이다.

라이다 RT 는 260910 과 0.34 cm / 0.61° 차이라 실질적으로 같지만, 이번 세션의 데이터로 직접 구한 값이므로 함께 교체했다.

### 남은 불확실성 / 주의

- **높이축(dz)이 여전히 약하다.** SLAM 카메라가 바닥을 거의 못 봐(1,600 프레임 중 69–88 장) direct dz 는
  eightcircle +8.7 cm, dense +10.8 cm, distance +5.9 cm 로 흩어진다. 라이다 겹침 경로로 본 dz 는 +13.0 / +10.9 / +2.0 cm.
  회전이 많은 네 추정의 평균은 **+10.8 ± 1.8 cm**이고 채택값(+8.7 cm)은 그보다 2 cm 낮다.
  더 줄이려면 SLAM 카메라가 바닥을 오래 보는 구간이 있는 녹화나, 두 카메라 depth 로 같은 평면을 동시에 보는 보정이 필요하다.
- `distance` 는 RT 추정용으로 쓰지 말 것(요 범위 193°, 구간 편차 57 mm).
- 라이다 bag 의 중복/이중 퍼블리셔는 **녹화 설정 문제**다. 실시간 경로(`lidar_stream.py`, `hdl_stream.py`)는 중복을 거르지
  않으므로 260915 bag 을 실시간 레인에 넣으면 같은 스캔을 두 번, 서로 6–82 ms 어긋난 두 스트림을 섞어 처리하게 된다.
  다음 녹화에서 퍼블리셔/구독을 하나로 줄이는 것이 좋다.
