라이다가 있는 실데이터 16개 세션(260901 4개, 260910 1개, 260915 11개) 전부에서 SLAM 시스템 다섯 가지를 1회씩 돌렸다.
기준은 라이다 pseudo-GT(`rt/gt`, 방법은 `own_gt_261017.md`)다.

- 실행: `rt/bench/run_bench.sh`
- 채점: `rt/bench/score_bench.py`

### ORB-SLAM3: 이 저장소 수정본과 원본의 차이

여기서 ORB-SLAM3는 모두 수정본이다. 원본은 UZ-SLAMLab `v1.0-release`다.
수정본과 원본의 비교 실험(OpenLORIS-Scene, 모션캡처 GT)은 `orbslam_ws/openloris/report_261018.md`에 있다.

| 수정 | 내용 | OpenLORIS에서 확인한 효과 |
|---|---|---|
| 자이로 보조 | 원본 RGB-D 모드는 IMU를 쓰지 않는다. 수정본은 자이로를 **회전에만** 쓴다(tightly-coupled). 넣는 곳은 다섯 군데다. ① 모션 모델: 다음 프레임 회전을 자이로 적분으로 예측. ② PoseOptimization: 자이로 회전 사전 엣지. ③ LocalBA: 키프레임 상대 회전 엣지. ④ 루프 후보를 회전으로 거부. ⑤ 정지 구간에서 바이어스 갱신 | Sim(3) ATE office −30%, home −14~21%, corridor −19~33% |
| 실시간 설정 C | `Optimizer.PoseIterations [10,5,5,5]`, `PoseEarlyExit 1` | 추적 시간 7.5–8.0 → 4.6–5.1 ms. 정확도 차이는 반복 편차 안 |
| 버그 수정 | isBad 교착, `DetectNBestCandidates` 무한 루프, Sim3Solver NaN, Shutdown 대기. 2026-10-18에 2건 추가(`MapPoint` 스택 배열 SIGBUS, `LocalMapping::Release()` 해제 후 사용) | 비정상 종료 원본 11회 → 0회 |
| 루프 임계값 완화 | BoW 0.8 → 0.5, 연속 일치 3 → 1, 매칭 수 축소. 저장소 첫 커밋부터 | 따로 측정하지 않음 |

자이로는 추적 상실 자체를 막지 못한다. 추적 정상 비율과 맵 끊김 횟수는 세 버전(원본, 수정본, 수정본+자이로)이 같았다.

## 2. 채점 방법과 주의점

- 채점기는 260901 때 쓰던 `eval_traj.py`를 그대로 쓴다.
  - ATE: 실행 전체를 SE(3) Umeyama로 정렬한 뒤의 위치 RMSE와 최대 오차
  - 회전 오차: 평균 회전 차이(보정값 오차)를 뺀 RMSE
  - RPE: 10초 구간 상대 오차
- **live**는 그 순간 내놓은 포즈, **final**은 종료 후 최적화한 궤적이다(KISS는 하나뿐).
- 카메라 시스템은 기준 카메라 포즈 = 라이다 pseudo-GT × 카메라-라이다 보정값(rig)으로 채점한다.
  - 260901: 세션별 rig(`rt/260901/rtab_odom/rigs/`)를 쓴다.
  - 260910·260915: `rt/bench/rigs/rig_260915.json` 하나를 쓴다. 260915_eightcircle의 ORB final 궤적으로 hand-eye를 맞춘 값이다.
    - 시간 오프셋은 0으로 고정했다. 상관 추정은 +70 ms(상관 0.79)였지만, 260915 라이다 타임스탬프가 불규칙해서 믿을 수 없다.
    - ATE는 오프셋 0과 70 ms 사이에서 0.2–0.5 cm만 달라진다.
- 채점기 수정: 10초 RPE는 이제 같은 인덱스 간격이 아니라 시간으로 짝을 찾는다.
  260915 라이다 타임스탬프가 불규칙해서 짝이 하나도 안 생겼기 때문이다. 260901 값은 그대로다(차이 0.0).

**읽을 때 주의**
1. **KISS-ICP는 독립된 점수가 아니다.** pseudo-GT가 KISS 오도메트리에 루프 보정을 더한 것이라 기준과 거의 같은 궤적이다.
2. **라이다 시스템과 카메라 시스템의 비교는 라이다 쪽에 유리하다.**
   - hdl은 기준과 같은 라이다 데이터를 쓰고, 라이다 좌표계에서 직접 채점된다.
   - 카메라 시스템에는 rig 오차가 섞인다. 260901 세션별 rig로 다시 맞추면 ORB ATE가 0.8–0.9 cm 달라졌다(`own_gt_261017.md` §3).
     평면 주행이라 수직 레버암도 관측되지 않는다.
3. **카메라끼리의 비교(ORB vs RTAB, 자이로 유무)는 같은 rig·같은 기준이라 공정하다.**
4. **1회 실행이다.** 같은 세션 반복 편차는 office 기준 0.05 cm였지만, 실데이터에서는 아직 재지 않았다.
5. **260915의 기준 품질은 260901보다 약간 낮다.** pseudo-GT 시작·끝 보류 검사에서 1–3 cm였다.

## 6. ORB-SLAM3 vs RTAB-Map: 위치 추정과 지도 (bigeightcircle, 3회 반복)

- 실행: `rt/bench/run_orb_vs_rtab.sh`
- 평가: `rt/bench/map_eval.py`
- 원자료: `rt/bench/out_cmp/260901_cbnu_bigeightcircle/` (`map_eval.json`)
- ORB 지도를 얻으려고 `slam_stream`이 오프라인 실행 끝에 현재 맵의 점을 `<out>.mappoints.xyz`로 쓰게 했다.
  이 바이너리는 `~/objpose/build`와 별도로 빌드했다.
- 두 시스템의 IMU 사용 방식이 다르다.
  - ORB+자이로: 우리 패치(§1). 자이로 회전을 포즈 최적화와 LocalBA 안의 **제약**으로 넣는다.
  - RTAB+IMU: RTAB-Map 기본 기능. Xsens 자세를 다음 프레임 회전의 **초기값**과 중력(롤·피치) 제약에만 쓴다(§9).

- **같은 조밀 지도를 놓고 보면 정확도는 ORB 궤적 쪽이 높다.** 같은 깊이 영상을 쌓았을 때 오차 중앙값이

- ORB 특징점 지도의 점당 정확도(1.74 cm)가 가장 높다. 모서리처럼 깊이가 잘 정해지는 점만 남기 때문이다.
  "검증 가능 비율"(89%)은 라이다가 보는 높이·거리에 점이 많다는 뜻이고, 지도의 완성도를 뜻하지는 않는다.
- **결론: 조밀한 지도가 필요하면, ORB 포즈로 깊이 영상을 쌓는 조합이 두 시스템의 장점을 함께 얻는다.**

  - 최대 오차는 113초의 루프 보정 순간에 live 포즈가 점프하는 크기(16–39 cm)가 정한다. 자이로가 줄이는 값이 아니다.

## 9. RTAB-Map에서 IMU 효과가 없는 이유

네 세션 모두 RTAB+IMU는 RTAB와 같거나 조금 나빴다. 원인은 두 가지다.

### 9.1 RTAB-Map은 IMU 회전을 초기값으로만 쓴다

RTAB-Map 0.23.8 소스(`rtabmap_ws/src/rtabmap/corelib/src`)에서 IMU가 쓰이는 곳은 세 군데다.

| 위치 | 하는 일 | 결과에 남는가 |
|---|---|---|
| `Odometry.cpp` 629–640행 | 이전 IMU 자세와 현재 IMU 자세의 차이로, 다음 프레임 움직임 추정값(guess)의 회전 부분을 바꾼다. guess는 특징점 대응을 찾는 탐색 창(`Vis/CorGuessWinSize` 40 px)에 쓰인다 | 아니다. 포즈는 그 뒤 특징점 대응 + RANSAC으로 영상만 보고 다시 계산된다 |
| `OdometryF2M.cpp` 217–224, 382행 | 로컬 번들 조정에 현재 프레임의 중력 링크(`Link::kGravity`)를 넣는다 | 롤·피치만. 요(yaw)는 제약하지 않는다 |
| `OptimizerG2O.cpp` 690–700행 | 그래프 최적화에서 노드마다 중력 방향 제약(`Optimizer/GravitySigma`) | 롤·피치만 (`Transform(0,0,0,roll,pitch,0)`) |

- 이 데이터의 회전은 대부분 지면 위에서 도는 요 회전이다. RTAB-Map은 이 회전을 IMU로 제약하지 않는다.
- 우리 ORB-SLAM3 수정본은 자이로 회전 전체(요 포함)를 PoseOptimization과 LocalBA 안의 엣지로 넣는다.
  특징점 추정이 흔들려도 회전이 자이로 쪽으로 붙잡힌다.

### 9.2 RTAB-Map의 오차는 회전이 아니라 이동에서 나온다

live 궤적, 3회 평균. RPE는 1초 간격 상대 오차, 추적 상실은 `frames.csv`의 `LOST` 프레임 수다.

|---|---|---|---|---|---|
| bigeightcircle | RPE 1 s 이동 cm / 회전 ° | 1.51 / 0.26 | 1.73 / 0.26 | 2.71 / 0.67 | 3.42 / 0.76 |
| eightcircle | | 2.00 / 0.35 | 1.78 / 0.34 | 3.40 / 0.73 | 3.65 / 0.82 |
| digut | | 2.62 / 0.45 | **1.81 / 0.33** | 7.42 / 0.99 | 7.74 / 1.02 |
| longcircle | | 1.96 / 0.36 | 1.65 / 0.33 | 2.96 / 0.68 | 3.10 / 0.65 |
| 네 세션 | 추적 상실 프레임 | 0 | 0 | 0 | 0 |

- **RTAB-Map은 추적을 한 번도 놓치지 않았다.** digut에서도 프레임당 인라이어가 중앙값 약 330개다.
  회전 추정이 틀어져 놓치는 문제가 아니므로, 회전 초기값을 IMU로 바꿔도 달라질 것이 없다.
- **이동 오차가 ORB의 1.5–3배다.** digut은 1초에 7.4 cm(ORB 2.6 cm)다. 자이로는 이동을 알려 주지 않는다.
  프레임 사이 이동을 계산하는 시각 오도메트리(F2M)의 정밀도 문제로 보인다. 원인을 더 나눠 보지는 않았다.
- **실행마다 편차가 크다.** digut live ATE가 15–32 cm로 흔들린다. IMU 유무의 차이가 이 편차 안에 묻힌다.

### 9.3 ORB에서는 왜 효과가 컸나

ORB의 큰 오차는 빠른 회전 구간에서 회전 추정이 틀어질 때 생긴다. 자이로를 켜면 live 최대 회전 오차가 19–54% 줄었다(§8).
자이로가 바로 그 약점을 제약으로 메운다. RTAB에서는 약점(이동)과 IMU가 메우는 것(롤·피치, 초기값)이 겹치지 않는다.

RTAB-Map을 나아지게 하려면 IMU보다 오도메트리를 바꾸는 쪽이 맞다.
예를 들어 다른 `Odom/Strategy`를 쓰거나, 외부 오도메트리(`rtab_stream --ext-odom`, 라이다나 ORB 궤적)를 넣을 수 있다. 이 방법들은 아직 시험하지 않았다.

## 10. hdl_graph_slam은 왜 pseudo-GT와 2–3 cm 차이가 나나 (260901)

두 가지를 확인했다. 바닥 제약이 1.2–1.5° 기울기의 원인인지, 오차가 그래프 키프레임 자체에 있는지 키프레임 사이에 있는지다.

- 실행: `rt/bench/run_hdl_ablation.sh` (바닥 검출 켬/끔, 세션마다 1회, 실시간 1배속, 끝에 그래프 덤프)
- 채점: `rt/bench/score_hdl_ablation.py` → `rt/bench/hdl_ablation.csv`
- 원자료: `rt/bench/out/<세션>/hdl_floor_{on,off}/run1/` (`live_tum.txt`, `final_tum.txt`, `kf_tum.txt`, `graph/`)

### 10.1 바닥 제약은 원인이 아니다: 한 번도 쓰이지 않았다

- 네 세션 모두, 바닥 검출을 켠 실행에서도 그래프의 바닥 제약 수가 0이다(`floor_constraints=0`, 덤프한 그래프에 평면 정점·엣지 없음).
  §3–5의 원래 hdl 실행도 마찬가지다.
- 그래서 켬과 끔의 결과가 같다(final ATE 차이 ≤ 0.01 cm). 기울기 1.1–1.5°는 바닥 제약 때문이 아니다.
- 바닥이 검출되지 않은 이유는 따로 확인하지 않았다. 런치 파일의 바닥 검출 설정(`sensor_height 0.5`,
  `height_clip_range 0.5`, `tilt_deg 0`)이 이 로봇의 VLP-16 장착 높이와 맞지 않을 가능성이 있다.
- 새 실행과 §3–5의 실행 결과도 0.02 cm 안에서 같다. hdl은 반복해도 결과가 거의 같다.

### 10.2 오차는 그래프 키프레임 자체에 있다

키프레임 시각에서 비교했다(SE(3) 정렬, cm / °). kf는 최적화된 키프레임 포즈, final과 live는 같은 시각의 스캔별 포즈다.

| 세션 | 키프레임 수 | kf ATE / 최대 / 회전 | final ATE / 최대 / 회전 | live ATE / 최대 / 회전 |
|---|---|---|---|---|
| bigeightcircle | 152 | 2.23 / 5.05 / 1.19 | 2.21 / 5.01 / 1.22 | 2.85 / 9.47 / 1.39 |
| eightcircle | 129 | 3.07 / 6.62 / 1.27 | 3.13 / 7.54 / 1.29 | 4.03 / 9.01 / 1.45 |
| digut | 168 | 2.80 / 7.06 / 1.86 | 2.84 / 6.89 / 1.88 | 3.81 / 10.11 / 1.86 |
| longcircle | 109 | 2.21 / 4.48 / 1.10 | 2.27 / 4.61 / 1.11 | 2.93 / 6.28 / 1.14 |

- **키프레임 포즈만 봐도 오차가 final과 같다(2.2–3.1 cm).** 키프레임 사이를 오도메트리로 잇는 과정에서 생기는 오차가 아니라,
  그래프가 최적화한 키프레임 위치 자체가 기준과 다르다.
- **live는 final보다 0.6–1.0 cm 크고, 최대 오차는 1.4–3.2 cm 크다.** 루프 보정이 나중에 들어와 고쳐지는 몫이다.
- 회전 오차가 1.1–1.9°로 크다. KISS-ICP(1 s RPE 회전 0.08°)와 비교하면 hdl의 1 s RPE 회전은 0.34–0.56°다.

### 10.3 남은 가설 (시험하지 않음)

- **스캔 왜곡 보정(deskew)이 없다.** hdl 경로(`hdl_stream.py` → hdl_graph_slam)는 VLP-16 스캔을 보정 없이 쓴다.
  로봇이 도는 동안 한 바퀴(0.1 s) 사이의 움직임이 스캔을 휘게 하고, 이것이 회전 오차로 나타날 수 있다.
  pseudo-GT는 KISS-ICP처럼 왜곡을 보정한 스캔으로 만들었다.
- **기준이 KISS 쪽에 유리하다.** pseudo-GT의 1단계가 KISS-ICP라, 같은 전처리를 쓰는 방법일수록 기준과 가깝게 나온다.
  hdl의 2–3 cm 중 일부는 기준의 편향일 수 있다.
- 확인하려면 왜곡을 보정한 스캔을 hdl에 넣어 다시 돌리거나, 독립된 GT가 있는 구간에서 hdl과 KISS를 비교해야 한다.

## 11. 특징점 수 × 자이로 2×2 (260901, 2026-10-19)

자세한 내용은 `slam_nf4000_vs_gyro_261019.md`에 있다. 수정 ORB-SLAM3를 NF2000 / NF4000 × 자이로 없음 / 있음으로 바꿔
