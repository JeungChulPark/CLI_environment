# 0부. 개요 (P01–P06)

### P01. 표지 — 무엇을 만들었는가
**핵심 한 줄:** 움직이는 카메라 리그가 실내를 돌면, 지도 좌표계에 물체의 6D 자세(위치+방향)를 실시간으로 채워 넣는 시스템.

**슬라이드 본문**
- 제목: *SLAM 포즈와 SAM-6D 객체 포즈의 시간 동기 융합에 의한 실시간 객체 지도 구축*
- 입력: RGB-D 카메라 2대(SLAM용 / 인식용) + VLP-16 라이다 1대를 얹은 카트
- 처리: SLAM 호스트(노트북·Mac·Ubuntu PC)에서 자세 추정 → 워크스테이션에서 SAM-6D 추론 → 시간 동기·좌표 융합 → 객체 메모리
- 출력: 브라우저(`http://<PC>:8765`)에 ① 객체 박스·3축이 그려진 영상, ② 3D 지도(궤적 + 객체 박스), ③ 상태 표
- 코드 위치: `objpose/`(허브·융합·뷰어), `sam6d_realtime/`(추론), `objectmemory_ws/`(객체 메모리), `hdlgraphslam_ws/`·`orbslam_ws/`(SLAM)

**그림·표 제안:** 실제 뷰어 스크린샷 1장(영상 패널 + 3D 지도 패널)을 전면에 깔고 제목을 얹는다.

**발표 노트:** "지금까지 만든 것은 알고리즘 하나가 아니라, 서로 다른 기계 3대에서 도는 SLAM·인식·메모리를 하나의 시계와 하나의 좌표계로 묶은 파이프라인"이라고 첫 문장에서 못 박는다.

### P02. 문제 정의 — 왜 SLAM과 6D 포즈를 따로 두고 융합하는가
**핵심 한 줄:** 6D 포즈 추정기는 "카메라 기준" 자세만 주고, 그 카메라는 계속 움직인다. 지도에 물체를 고정하려면 SLAM 자세가 반드시 곱해져야 한다.

**슬라이드 본문**
- SAM-6D 출력 = `T_sam_obj` (SAM 카메라 좌표계에서 본 물체 자세). 카메라가 움직이면 같은 물체도 매 프레임 값이 달라진다.
- 필요한 것 = `T_w_obj` (지도 좌표계의 물체 자세). 물체는 정지해 있으므로 이 값은 시간에 대해 상수여야 한다.
- 관계식: `T_w_obj = T_w_slam(s) · X · T_sam_obj(s)`
  - `T_w_slam(s)`: SLAM 카메라의 지도 내 자세(시각 s)
  - `X = T_slam_sam`: 리그 외부 파라미터(두 카메라의 고정 상대 자세)
- 세 가지가 동시에 맞아야 한다: **시계**(s가 같은 순간을 가리키는가), **외부 파라미터**(X가 mm 단위로 맞는가), **지도 일관성**(루프 클로저로 지도가 움직여도 물체가 따라 움직이는가)
- 이 세 축이 그대로 이 발표의 1부(시계)·2부(X)·4부(지도 일관성)다.

**그림·표 제안:** 좌: 카메라 기준 박스가 프레임마다 흔들리는 그림 / 우: 지도 기준으로 한 점에 모이는 그림.

**발표 노트:** "융합"이라는 말이 추상적이므로, 식 하나와 세 가지 실패 요인으로 환원해서 보여 주는 장. 이후 모든 장이 이 세 요인 중 하나를 해결하는 이야기다.

### P03. 시스템 전체 데이터 흐름 (한 장 요약)
**핵심 한 줄:** 데이터는 "센서 → 두 갈래(SLAM 자세 / 인식 프레임) → 융합 → 메모리 → 화면"으로 흐르고, 두 갈래는 오직 타임스탬프로만 만난다.

**슬라이드 본문**
```
[SLAM 호스트 : Mac 192.168.20.55 / Ubuntu 192.168.20.3 / 노트북 192.168.2.1]
  RGB-D 세션(db3) 또는 라이브 카메라 ──► ORB-SLAM3 / RTAB-Map
  VLP-16 스캔(db3) 또는 라이브 라이다 ──► KISS-ICP / hdl_graph_slam
        │  줄 단위 JSON over TCP (hello → start → pose… → kf_update… → end)
        ▼
[워크스테이션 192.168.20.5 (RTX 4090) : objpose/pc/hub.py]
  ├ Lane: 포즈 서버 + PoseBuffer + KeyframeMap + Fusion + ObjectMemory + 로그   (SLAM 스트림 1개당 1 Lane)
  ├ SAM 세션 재생(1x) ──공유메모리(seqlock)──► sam6d_infer.py (ISM + PEM, 별도 프로세스)
  │                     ◄──공유메모리(JSON)── 결과 {stamp_ns, dets[R, t_mm, score]}
  ├ 융합:  T_w_obj = T_w_slam(s)·X·T_sam_obj ,  저장은 키프레임 기준 T_kf_obj
  ├ 객체 메모리: 연관 → 포즈 융합 → 존재확률 → 상태기계 → depth 검사
  └ HTTP/SSE :8765 ──► 브라우저(three.js): 영상 오버레이 + 3D 지도 + 상태 표
```
- 두 갈래가 만나는 지점은 단 하나: **SAM 프레임의 타임스탬프 s에서의 SLAM 자세를 SE(3) 보간으로 구하는 곳**(`pc/fusion.py`).
- 갈래마다 독립된 지연을 가진다: SLAM 자세 20~100 ms, SAM-6D 결과 0.5~1.0 s. 이 차이를 흡수하는 장치가 뒤에 나오는 보간·대기·표시 지연이다.

**그림·표 제안:** 위 아스키 도식을 그대로 블록도로. 색: SLAM 파랑(#56c2e0), 라이다 주황(#f2a03d), SAM-6D 초록, 메모리 보라.

**발표 노트:** 이 한 장을 목차 대신 쓰고, 이후 각 부 시작마다 이 그림에 빨간 테두리로 "지금 설명하는 블록"을 표시하면 좋다.

### P04. 하드웨어 리그와 좌표계
**핵심 한 줄:** 카트 위에 RealSense D455f 2대와 VLP-16 1대가 고정돼 있고, 각 센서 사이의 상대 자세(RT)를 오프라인으로 추정해 둔다.

**슬라이드 본문**
- **SLAM 카메라**: RealSense D455f, 640×480 @30 fps, RGB-D. SLAM 전용(ORB-SLAM3 / RTAB-Map 입력).
- **SAM 카메라**: RealSense D455f, 640×480 @30 fps. 인식 전용(SAM-6D 입력). SLAM 카메라와 다른 방향을 본다.
- **라이다**: Velodyne VLP-16, 10 Hz, 채널 16(최하 −15°). 실내에서는 바닥을 거의 못 본다(높이 관측 불가 → P21에서 따로 처리).
- 좌표계 정의
  - 카메라 광학 좌표계(x 오른쪽, y 아래, z 전방) — ORB-SLAM3 월드도 이 관례
  - 라이다 좌표계(z 위) — 라이다 레인이 기준일 때 뷰어가 z-up으로 그린다
  - `X = T_slam_sam`: SLAM 카메라 좌표계에서 본 SAM 카메라 (4×4, m 단위)
- 리그는 고정이지만 **바뀔 수 있다**: 260915 녹화에서 SLAM 카메라만 5 cm/1.7° 이동한 것을 RT 재추정으로 검출(P23).

**그림·표 제안:** 카트 사진 또는 3D 스케치 + 세 좌표축 화살표 + `X`, `T_cam_lidar` 표시.

**발표 노트:** "SAM 카메라와 SLAM 카메라를 분리한 이유는, 인식용 카메라가 물체를 보는 동안 SLAM 카메라는 특징이 풍부한 방향(벽·천장)을 보도록 하기 위함"이라고 설명.

### P05. 실행 형상 — 어느 기계에서 무엇이 도는가
**핵심 한 줄:** 무거운 추론은 4090 워크스테이션 한 대에, SLAM은 데이터가 있는 호스트에 두고, 둘을 TCP 한 줄짜리 프로토콜로 잇는다.

**슬라이드 본문**

| 역할 | 기계 | 실행물 | 포트 |
|---|---|---|---|
| ORB-SLAM3 (녹화 세션) | Ubuntu 192.168.20.3 / Mac 192.168.20.55 | `mac_slam/slam_stream.cc` 빌드본 | 17001 / 17004 |
| ORB-SLAM3 (라이브 카메라) | 노트북 192.168.2.1 | `live_orb/orb_live_stream.py` + orbslam3_ros2 | 17001 |
| RTAB-Map | Mac / 노트북 | `mac_slam/rtab_stream.cc` / `live_orb/rtab_live_stream.py` | 17008 |
| KISS-ICP (라이다) | Mac / .3 / 노트북 | `lidar/lidar_stream.py` (venv, ROS 불필요) | 17006 / 17007 |
| hdl_graph_slam (라이다) | 이 PC / .3 / Mac / 노트북 | `lidar/hdl_stream.py` + ROS 2 워크스페이스 | 17002 / 17005 / 17003 |
| 허브·SAM-6D·메모리·뷰어 | 워크스테이션 192.168.20.5 (RTX 4090 ×4, cuda:0만 사용) | `pc/hub.py`, `sam6d_realtime/realtime/sam6d_infer.py` | HTTP 8765 |

- 연결 방식 4가지(`hub.py --link`): `tunnel`(ssh -R 역터널) / `direct`(SLAM 호스트가 PC로 직접 접속) / `manual`(사람이 명령 실행) / `local`(같은 PC에서 실행).

**그림·표 제안:** 기계 3~4개를 박스로 그리고 화살표에 포트 번호를 적는다.

**발표 노트:** 포트를 백엔드별로 고정한 이유는 "한 번에 하나만 실행"을 보장하면서도 백엔드 전환 시 충돌을 막기 위함.

# 1부. 입력 데이터와 시계 (P07–P15)

### P07. 입력 데이터 3종
**핵심 한 줄:** 같은 허브가 원본 SDK 세션·변환 bag·라이브 센서 3가지 입력을 모두 받으며, 세 경우의 차이는 "시계를 어떻게 얻는가"뿐이다.

**슬라이드 본문**
- **(A) 원본 RealSense SDK 세션** (`260826_etri_eightcircle_dark`): `*.db3`(librealsense rosbag2, `/device_0/...` 토픽) + `rgbd_timestamp_associations.json`. depth가 color에 **정렬돼 있지 않다** → 허브가 직접 정렬.
- **(B) 변환본 bag** (`data_slam_converted/260910_object`, `260915_*`): 표준 RealSense 토픽(`/camera/camera/color/image_raw`, `/camera/camera/aligned_depth_to_color/image_raw`, `camera_info`), depth 이미 정렬, 헤더 스탬프가 이미 공용 시계.
- **(C) 라이브 센서**: 이 PC의 D455f → `realsense2_camera`(ROS 2, `align_depth.enable:=true`) 토픽을 `live_session.py`가 구독.
- 각 세션 폴더 구성: `SLAM/`(SLAM 카메라), `SAM/`(인식 카메라), `lidar/`(VLP-16) — 세 개가 같은 주행을 동시에 녹화한 것.

**그림·표 제안:** 폴더 트리 3종을 나란히.

**발표 노트:** (A)를 계속 지원하는 이유는 260826 데이터가 가장 잘 검증된 기준 데이터셋이기 때문. 새 데이터는 (B)로 통일하는 중.

### P08. 원본 SDK 세션의 내부 구조 (`pc/rs_session.py`)
**핵심 한 줄:** ROS 없이 sqlite에서 직접 메시지를 꺼내 읽고, depth를 color 화소 격자로 직접 정렬한다.

**슬라이드 본문**
- `rgbd_timestamp_associations.json` → `associations[]`: `{color_message_id, depth_message_id, associated_host_epoch_timestamp_ns}`. 이것이 프레임 인덱스의 정의.
- 카메라 파라미터는 bag 안의 문자열 메시지에서 파싱: `camera_info`(fx, fy, ppx, ppy, coeffs 5개), depth→color 외부 파라미터(`tf/ref_0`의 rotation 9 + translation 3), `Depth_Units`.
- `read(i, with_depth)` → `Frame(index, t_ns, color_bgr, depth_raw)`. color 인코딩 rgb8/bgr8 모두 처리.
- `align(depth_mm)`: depth 센서 격자의 각 화소를 3D로 역투영 → depth→color 강체 변환 → color 내부 파라미터 + Brown-Conrady 왜곡으로 재투영 → 반올림한 화소에 **가까운 값이 이기도록**(z 내림차순 write) 채운다. 결과는 color 격자 위의 uint16 mm.
- 이 `align()`은 SAM-6D 학습·검증에 쓰인 변환기(`sam6d_realtime/data/convert_recording.py`)의 동일 함수를 이식한 것 — 변환본과 **비트 단위 동일**함을 확인했다.

**그림·표 제안:** depth 격자 → 3D → color 격자 재투영 3단계 그림. 화소 충돌 시 "가까운 값 우선" 표시.

**발표 노트:** 여기서 정렬을 직접 하는 이유: 원본 12 GB 세션을 변환 없이 바로 재생하기 위함. Mac 쪽 C++ 스트리머도 같은 함수를 이식해 두 호스트가 동일 입력을 본다.

### P09. 변환본 bag과 라이브 입력 (`conv_session.py`, `live_session.py`)
**핵심 한 줄:** 세 리더가 같은 인터페이스(`K, kc, W, H, t_ns, read(), align()`)를 제공하므로 허브 본체는 입력 종류를 모른다.

**슬라이드 본문**
- `ConvSession`: color/depth를 **헤더 스탬프 완전 일치**로 짝짓는다(짝 없는 color 프레임은 버리고 개수를 보고). `align()`은 항등 함수(이미 정렬).
  - 성능 문제 해결: 13 GB bag의 스탬프 인덱싱이 NFS에서 3분 걸려, bag 파일의 크기·mtime을 키로 `.npz` 캐시(`rt/clock/conv_*.npz`)를 둔다.
- `LiveSamSession`: rclpy 백그라운드 스레드에서 `message_filters.ApproximateTimeSynchronizer(slop=20 ms)`로 color+aligned depth를 짝지어 **가장 최신 한 쌍**만 보관. 허브는 `latest()`로 가져간다(오래된 프레임은 그냥 버려진다 = 실시간 정책).
  - 드라이버는 `global_time_enabled` 상태여서 헤더 스탬프가 호스트 시계.
- 라이브에는 타임라인이 없으므로 허브가 재생 루프 대신 "`--sam-feed-hz`(기본 10 Hz)로 최신 프레임 급전" 루프를 돈다.

**그림·표 제안:** 세 리더를 같은 인터페이스 박스로 감싸 "허브는 구분하지 않음"을 보이는 그림.

**발표 노트:** 라이브 모드는 2026-09-17에 추가. 이후 성능 지표 계산식이 바뀐 부분(시작 오프셋 제거)은 P40에서 다룬다.

### P11. 시계 문제 1 — 시계가 세 개다
**핵심 한 줄:** SLAM 호스트 시계, SAM 카메라 시계, 연관 파일의 호스트 시각이 모두 다르고, 최악은 초 단위로 틀어져 있었다.

**슬라이드 본문**
- 후보 시각 3종
  1. `rgbd_timestamp_associations.json`의 `associated_host_epoch_timestamp_ns` (연관 스탬프)
  2. 컬러 스트림의 **프레임 메타데이터 `timestamp`** (프레임 시계)
  3. 변환본 bag의 헤더 스탬프
- 측정 결과(`pc/clock.py` 주석)
  - SLAM 세션: 컬러 프레임 드롭(100 ms·200 ms 공백) 때문에 연관 스탬프가 실제 프레임 시각에서 **−2.1 s ~ +3.8 s** 표류. 선형 보정해도 RMS 1.1 s 남음.
  - SAM 세션: 드롭이 없어 연관 스탬프가 ~4 ms 이내.
  - 프레임 메타데이터는 bag 자체 프레임 시각과 SLAM 1.4 ms / SAM 0.1 ms 일치.
- 두 카메라는 서로 다른 시간 도메인: SLAM은 "Global Time", SAM은 "System Time"(= 도착 시각이라 늦다).

**그림·표 제안:** 시간 축 하나에 3개 시계를 겹쳐 그리고 −2.1 s/+3.8 s 표류 구간을 강조.

**발표 노트:** 이 발견 전에는 융합 결과가 통째로 어긋났다. "정확도 문제로 보였던 것이 실은 시계 문제였다"는 서사로 쓰면 설득력이 좋다.

### P12. 시계 문제 2 — 채택한 규약
**핵심 한 줄:** 모든 시각을 **SLAM 호스트의 프레임 시계**로 통일하고, SAM 쪽에는 피어 시계차와 잔여 지연 τ를 더한다.

**슬라이드 본문**
- 규약
  1. 프레임 시각 = 컬러 메타데이터 `timestamp` (`pc/clock.py: frame_clock()`), 결과는 `.npz`로 캐시.
  2. SAM 시각 = SAM 프레임 시각 − **18,225,662,057 ns**(두 호스트 시계차, `SLAM/peer_timestamp_comparison.json`) + **τ**.
  3. τ(잔여 지연)는 RT 추정 과정에서 함께 최적화된 값: 260826 = **−48 ms**, 260915 = 0 ~ +4 ms, 라이다–카메라 = +4~8 ms.
  4. Mac 스트리머는 `--time-source frame` 기본, 허브도 받은 `frame_idx`로 시각을 다시 매긴다(`Lane.on_msg`).
  5. 변환본 bag은 이미 공용 시계이므로 τ만 적용.
- 라이브 모드: 두 호스트의 벽시계 차이를 `tools/clock_offset.py`(UDP 왕복, 대칭 경로 가정)로 직접 측정해 `--sam-tau-s`로 넣는다. 직결 케이블에서 RTT < 1 ms라 20 ms 허용오차 대비 충분.
- 레인마다 τ가 다를 수 있으므로(리그 RT json마다 `sam_tau_s` 보유), 재생 시계는 하나로 두고 **레인별 τ 차이를 자세 조회 오프셋**(`Fusion.t_offset_ns`)으로 처리한다.

**그림·표 제안:** `SLAM 시각 = SAM 메타 시각 − 18.2258 s + τ` 식을 큰 글씨로.

**발표 노트:** "τ를 따로 두지 않고 RT와 동시에 추정한다"는 점이 방법론적 포인트 — 시간 오프셋과 공간 오프셋이 결합돼 있기 때문.

### P13. 시계 교정의 효과 (수치)
**핵심 한 줄:** 시계를 바꾼 것만으로 정지 객체의 위치 흩어짐이 중앙값 5.6 cm → 1.5 cm로 줄었다.

**슬라이드 본문**

| 지표 | 처음(두 지도 AX=ZB RT + 연관 스탬프) | 최종(오프라인 RT + 프레임 시계) |

| 정지 객체 월드 위치 흩어짐 | 중앙 5.6 / p90 16.7 cm | **중앙 1.5 / p90 7.1 cm** |

**그림·표 제안:** 위 표 + 흩어짐 분포 히스토그램 전/후.

**발표 노트:** 이 표가 "1부(시계)와 2부(RT)를 왜 그렇게 고생해서 했는가"의 답이다.

# 2부. 오프라인 보정: 리그 외부 파라미터 (P16–P24)

### P16. 왜 X가 mm 단위로 필요한가
**핵심 한 줄:** X의 오차는 물체 위치 오차에 **그대로** 더해지고, 카메라가 회전하면 각도 오차가 거리에 비례해 증폭된다.

**슬라이드 본문**
- `T_w_obj = T_w_slam · X · T_sam_obj` 에서 X의 평행이동 오차 δt는 물체 위치에 δt 그대로 들어간다.
- X의 회전 오차 δθ는 물체까지 거리 d에 대해 d·δθ 만큼의 위치 오차를 만든다(d = 1 m, δθ = 1° → 1.7 cm).
- 목표 정확도: 정지 객체 흩어짐 1 cm 수준 → X는 **≤ 0.5 cm, ≤ 0.1°** 급이 필요.
- 게다가 시간 오프셋 τ가 틀리면, 카메라가 움직이는 동안 X 오차처럼 보인다 → τ와 X를 함께 풀어야 한다.

**그림·표 제안:** X 오차 → 물체 위치 오차 전파 그림(거리에 비례하는 각도 오차).

**발표 노트:** 여기서 "URDF에 적힌 설계값을 왜 안 쓰는가"를 예고: 실측과 3.54 cm / 0.54° 차이가 났다.

---

### P17. 기각한 두 가지 방법
**핵심 한 줄:** 전통적인 두 접근(AX=ZB, 공유 지도 재측위)은 이 리그·이 주행에서 원리적으로 불리했고, 실제로 나빴다.

**슬라이드 본문**
- **방법 1: 두 지도 사이 AX = ZB** (각 카메라가 독립 지도를 만들고 대응)
  - 카트가 **요(yaw)만 회전**하므로 회전축이 한 방향뿐 → 문제가 ill-posed(조건 불량).
  - 결과: 최종 해 대비 13.76 cm / 2.95° 차이.
- **방법 2: SAM 카메라를 SLAM 카메라의 저장 지도에 재측위(localization)**
  - 동작은 하지만 지도의 국소 변형을 그대로 상속 — 10 s 구간마다 5~45 cm로 답이 흔들리고 잔차 p90 12 cm.
- 교훈: **지도 전체를 가로질러 절대 위치를 비교하는 방법은 쓰지 않는다.** 대신 X를 "각 센서가 잘 관측하는 성분"으로 쪼갠다.

**그림·표 제안:** 두 방법의 실패 모드 그림(회전축 하나 / 지도 뒤틀림).

**발표 노트:** 논문에서 "왜 이 방법인가"를 정당화하는 절이 될 부분. 실패를 수치와 함께 남겨 둔 것이 강점.

---

### P18. 채택한 방법 — X를 세 조각으로 분해 (`pc/estimate_rt_offline.py`)
**핵심 한 줄:** 중력 방향은 궤적 평면에서, 수평 오프셋·요는 상대 움직임 hand-eye에서, 높이는 depth 바닥면에서 — 각각 가장 잘 관측되는 곳에서 뽑는다.

**슬라이드 본문**
- **1단계 — "아래" 방향**: 각 카메라 궤적점에 SVD → 최소 주성분 = 궤적 평면 법선 = 중력 방향.
  - 평면 이탈 RMS: SLAM 0.6 cm, SAM 0.2 cm (카트가 평평한 바닥을 움직이므로 유효)
  - 이 방향으로 두 좌표계를 수평화(levelling): `L_slam`, `L_sam`.
- **2단계 — 평면 hand-eye (SE(2) AX = XB)**: 수평화한 좌표에서 각 카메라의 **상대 움직임**(0.5–4 s 창, stride 3)을 쌍으로 모아 `tx, ty, φ(yaw)`와 τ를 Huber 손실 최소제곱으로 동시 추정(`scipy.least_squares`).
  - 짧은 창은 국소적으로 정확하고, 8자 주행이 요 변화를 크게 만들어 조건이 좋다.
  - 260826: 쌍 14,592개, 잔차 중앙 0.412 cm / p90 1.105 cm.
- **3단계 — 높이 차**: 평면 운동으로는 관측 불가 → 각 카메라의 aligned depth에서 **바닥 평면을 RANSAC**(법선을 1단계의 "아래"로 제약)으로 잡아 카메라 높이를 직접 측정.
  - SLAM 1.1068 m, SAM 0.9981 m (MAD 2.31 / 1.22 cm, 사용 프레임 64 / 209)
- 합성: `X = L_slamᵀ · [Rz(φ) | (tx, ty, h_slam − h_sam)] · L_sam`

**그림·표 제안:** 3단계를 세 칸으로 나눈 그림(궤적 평면 / 상대 움직임 쌍 / 바닥 평면).

**발표 노트:** 핵심 아이디어 한 줄 — "관측 가능한 성분만 그 성분이 관측되는 데이터로 푼다". 논문 기여로 내세울 수 있는 부분.

### P20. 라이다–카메라 RT (`lidar/estimate_lidar_cam_rt.py`)
**핵심 한 줄:** 같은 분해 전략을 라이다에도 적용했고, 높이만은 hand-eye가 아니라 "점–표면 겹침 최대화"로 구했다.

**발표 노트:** 센서의 물리적 한계(FOV)가 추정 전략을 바꾼 사례로 설명하면 좋다.

**발표 노트:** 사소해 보이지만 재현성 사고를 막은 장치. 질문이 나올 만한 지점이라 한 장 배정.

### P23. 오프라인 궤적은 어떻게 만드나 (RT 입력용)
**핵심 한 줄:** RT 추정에는 실시간 포즈가 아니라 **루프 클로저·GBA가 반영된 최종 궤적**을 쓴다.

**슬라이드 본문**
- `slam_stream --mode offline --out traj.txt`는 두 개의 궤적을 남긴다.
  - `traj.txt` — 프레임마다의 **실시간** 포즈(TUM). 그 시점의 드리프트를 포함.
  - `traj.txt.optimized.txt` — `SaveTrajectoryTUM`, 즉 종료 후 키프레임 기준으로 다시 계산한 **최적화** 궤적.
- RT 추정과 비교 평가에는 `*.optimized.txt`를 쓴다(README 주석: 실시간 포즈는 나중의 보정을 받지 못함).
- 부수 산출물: `traj.txt.frames.csv`(프레임별 state/track_ms/map_id/map_changed/추적 맵포인트 수/vo_only), `traj.txt.json`(요약·구간 정보).
- 궤적 시각을 프레임 시계로 다시 매기는 도구: `pc/clock.py: remap_tum()` (연관 스탬프 → 프레임 시각, 허용 1 ms).

**그림·표 제안:** 실시간 궤적 vs 최적화 궤적 겹쳐 그린 탑뷰(루프 닫히는 지점 강조).

**발표 노트:** "같은 실행에서 실시간/최종 두 궤적을 모두 남기는 구조"가 뒤의 평가(실시간 포즈 vs 최종 포즈 차이)를 가능하게 했다.

# 3부. SLAM 레인 (P25–P34)

### P25. 스트리머 공통 프로토콜
**핵심 한 줄:** 모든 SLAM 백엔드는 줄 단위 JSON 5종만 말하면 되고, 허브는 백엔드를 구분하지 않는다.

**슬라이드 본문**
- 연결: 스트리머가 허브의 포즈 서버(TCP, 포트 17001~17008)에 접속. `TCP_NODELAY` on.
- 메시지 (모두 `\n`으로 끝나는 JSON 한 줄)

| 방향 | type | 필드 |
|---|---|---|
| 스트리머→허브 | `hello` | `source`, `first_ns`, `last_ns`, `n_frames`, `time_source`, `time_domain`, `kf_updates`, `features`, `params` |
| 허브→스트리머 | `start` | `t0_ns`, `rate` |
| 스트리머→허브 | `pose` | `t_ns`, `state`, `T_wc`[16], `track_ms`, `frame_idx`, `dropped`, `map_id`, `map_changed`, `ref_kf`, `T_w_kf`[16], `kf_map_id` |
| 스트리머→허브 | `pose_refine` | `t_ns`, `T_wc`, `smooth_n` (지연 평활 포즈; KISS-ICP 전용) |
| 스트리머→허브 | `kf_update` | `t_ns`, `map_id`, `reason`(periodic/map_changed/loop/optimize/end), `kfs`[[id, T12], …] |
| 허브→스트리머 | `stop` | (라이브 모드 종료 요청) |
| 스트리머→허브 | `end` | `processed`, `dropped`, … |

- 이 설계의 이점: 새 SLAM을 붙이는 비용 = "이 5종을 말하는 얇은 브리지 1개".
  실제로 ORB-SLAM3(C++), RTAB-Map(C++), KISS-ICP(Python venv), hdl_graph_slam(ROS 2) 4종을 같은 허브에 붙였다.

**그림·표 제안:** 시퀀스 다이어그램(hello → start → pose ×N / kf_update ×M → end).

**발표 노트:** "ROS를 공통 인터페이스로 쓰지 않은 이유"를 물으면: 호스트마다 ROS 배포판이 다르고(Mac에는 없음), 네트워크 DDS가 광역에서 불안정하며, 무엇보다 추론 프로세스와 GIL/도메인 충돌을 피하기 위해서.

### P26. ORB-SLAM3 스트리머 (1) — 세션 읽기와 추적 (`mac_slam/slam_stream.cc`)
**핵심 한 줄:** ROS 없이 db3를 직접 읽고, PC와 동일한 depth 정렬을 적용해 ORB-SLAM3 RGB-D에 넣는다.

**슬라이드 본문**
- 입력: `<session>/*.db3` + `rgbd_timestamp_associations.json` (또는 변환 bag 자동 인식)
- 프레임 처리 `process()`
  1. sqlite에서 color/depth blob 조회 → 이미지 메시지 파싱(기하·크기 검증)
  2. rgb8이면 BGR로 변환(ROS 노드와 동일하게 BGR을 넘김)
  3. `depth_to_color()` — PC의 `rs_session.align()`과 동일 알고리즘
  4. `slam.TrackRGBD(color, depth, t)` → `Tcw`, `T_wc = Tcw⁻¹`
  5. 상태 수집: `GetTrackingState()`, `MapChanged()`, 현재 맵 id, 추적 맵포인트 수, VO 전용 여부
- Atlas/Tracking의 private 멤버 접근: 명시적 템플릿 인스턴스화 트릭(`PrivateAccess`)으로 **ORB-SLAM3 소스를 수정하지 않고** 맵 id·참조 키프레임을 읽는다.
- 상태 문자열: `SYSTEM_NOT_READY / NO_IMAGES_YET / NOT_INITIALIZED / OK / RECENTLY_LOST / LOST / OK_KLT`. 허브는 `OK`, `OK_KLT`만 버퍼에 넣는다.

**그림·표 제안:** 프레임 처리 5단계 파이프라인 그림 + 각 단계 소요(prep_ms / track_ms).

**발표 노트:** "원본 라이브러리를 고치지 않는다"는 원칙을 여기서도 지켰다는 점(패치는 `mac_slam/patches/`에 별도 보관).

### P27. ORB-SLAM3 스트리머 (2) — 실시간 페이싱과 pose 메시지
**핵심 한 줄:** 허브가 정해 준 t0에서 시작해 데이터 시각대로 재생하고, 늦으면 **프레임을 건너뛰어** 실시간성을 유지한다.

**슬라이드 본문**
- 페이싱 루프
  - `due_s = (frame.t_ns − t0_ns) / rate`, 벽시계 경과와 비교. 이르면 최대 5 ms 씩 sleep.
  - 늦었으면 **이미 마감된 가장 최신 프레임까지 건너뛴다**(`dropped` 증가) — 밀린 프레임을 따라가느라 더 밀리는 것을 막음.
- pose 메시지 구성: 기본 필드는 nlohmann json, 그 뒤 키프레임 필드는 6자리 고정 소수로 직접 문자열 접합(기본 직렬화는 17자리라 메시지가 3배 커진다).
- `ref_kf`: `tracker->mCurrentFrame.mpReferenceKF->mnId` — **이 프레임의 포즈가 기준으로 삼은 키프레임**. `T_w_kf`는 그 키프레임의 현재 자세.
  - 이 두 필드가 뒤의 "키프레임 앵커링"(P42)을 가능하게 하는 핵심.
- 260826 전체 실행: 7,074 포즈 OK, 버림 0, 추적 10.5~16.6 ms/프레임.

**그림·표 제안:** 시간 축에 프레임 마감 시각과 실제 처리 시각, 건너뛴 프레임 표시.

**발표 노트:** "실시간"의 정의를 여기서 분명히: 데이터 시각 기준으로 1배속을 지키되, 처리 지연이 생기면 최신 프레임으로 점프한다.

### P28. ORB-SLAM3 스트리머 (3) — kf_update: 지도 보정을 전파하는 통로
**핵심 한 줄:** 1초마다, 그리고 루프 클로저 직후(+0.5 s, +3 s) 전체 키프레임 자세를 통째로 보낸다.

**슬라이드 본문**
- `send_kf_update(reason)`
  - 현재 맵의 모든 키프레임을 id 순으로 순회, `isBad()` 제외, `GetPoseInverse()` = `T_w_kf`의 앞 3×4를 6자리로 직렬화
  - `{"type":"kf_update","t_ns":…,"map_id":…,"reason":…,"n":…,"build_ms":…,"kfs":[[id, 12개 수],…]}`
- 발송 시점
  - 주기: 1.0 s
  - `map_changed`(루프 클로저·GBA) 감지 즉시 1회 + 0.5 s 후 + 3 s 후(최적화가 수렴한 뒤의 값을 받기 위해)
  - 종료 시 1회(`reason: end`)
- 비용 실측: 빌드 시간 평균 수 ms, 메시지 크기 평균 수십 KB(키프레임 150~180개 기준). 1 Hz면 네트워크 부담 없음.
- 관측된 보정 크기: 260826 최대 9.0 cm, 260910 ORB 최대 **84.3 cm**, hdl 2.7 cm.

**그림·표 제안:** 시간 축에 루프 클로저 이벤트와 kf_update 발송(즉시/+0.5 s/+3 s) 표시.

**발표 노트:** "SLAM이 과거를 고쳐 쓴다"는 사실을 시스템 전체가 알아야 한다 — 이 메시지가 그 통로다. 여기가 이 시스템의 가장 중요한 설계 결정 중 하나.

### P31. KISS-ICP 라이다 스트리머 (2) — 흔들림의 원인과 처리
**핵심 한 줄:** 궤적 스파이크의 원인은 **등속 가정 deskew**였고, 반복 deskew + 이동평균으로 고주파 흔들림을 절반으로 줄였다.

**슬라이드 본문**
- 증상: 1 s 이동평균 잔차는 0.62 cm로 양호하나, 출발·정지·회전 전환 순간에 1.5–2.7 cm 스파이크(67.8 s, 102 s, 108 s, 123.8 s).
- 원인 아님으로 배제한 것: 기하 퇴화(수평 제약 고유값 비 0.73), 점 수·가림, 스캔 누락·`time` 필드, 스탬프 기준.
- 원인 확정: 가속 크기와의 순위상관 — 선가속 0.70, 요 각가속 0.63. KISS-ICP는 **직전 스캔의 움직임으로 현재 스캔을 편다**. 움직임이 급변하면 잘못 펴져 정합이 1–2 cm 밀린다. deskew를 끄면 그 순간 가속이 1.84 → 0.63 cm로 사라짐.
- 대책 비교(`lidar/kiss_variants.py` + `eval_lidar_variants.py`)

| 방식 | ms/스캔 | 가속 p99 | 고주파 차(전체/스파이크) | 객체 흩어짐 중앙 |
|---|---|---|---|---|
| 기존(등속 deskew) | 9.5 | 1.50 | 0.51 / 2.30 | 1.14 |
| deskew 끔 | 11.1 | 1.37 | 0.39 / 0.91 (저주파 RMSE 악화 5.25) | 1.35 |
| 반복 deskew 2회 | 14.8 | 1.36 | 0.35 / 0.70 | 1.02 |
| **반복 2회 + 5스캔 평균** | 14.8 | 0.52 | **0.26 / 0.43** | 1.03 |

**그림·표 제안:** 시간 축 가속 그래프에 스파이크와 회전 전환 구간을 겹쳐 표시.

**발표 노트:** "원인 규명 → 대안 6개 측정 → 채택"의 전형적 절차. 논문에서는 이 표가 ablation이 된다.

### P32. KISS-ICP 스트리머 (3) — 평활 포즈를 늦지 않게 전달하기 (`pose_refine`)
**핵심 한 줄:** 평균한 포즈만 보냈더니 화면의 95 %에서 박스가 사라졌다. 원시 포즈를 먼저 보내고 평활값을 나중에 갈아끼우는 방식으로 해결했다.

**슬라이드 본문**
- v4 실패: 5스캔 중앙 이동평균은 **다음 스캔까지 기다려야** 계산되므로 도착 지연 19 → 328 ms. 표시 지연(0.3 s)을 넘겨 화면 프레임의 95 %에 자세가 없었고, Sikhye 첫 표시가 41.8 → 57.9 s로 밀리고 메모리에서 Dinosaur가 둘로 쪼개졌다.
- v5 수정
  1. 원시 포즈를 즉시 `pose`로 전송(지연 22 ms) → 화면은 끊기지 않음
  2. 0.2 s 뒤 `pose_refine{t_ns, T_wc, smooth_n}` 전송(지연 223 ms)
  3. 허브 `PoseBuffer.refine(t_ns, T_wc)`가 **같은 타임스탬프의 항목만** 찾아 자세를 교체(키프레임 상대 자세 `T_kf_c`도 같은 키프레임 기준으로 재계산)
  4. 로그에는 `T_wc` = 최종(평활), `T_wc_raw` = 스트리밍된 원시값을 함께 남김
- 결과: 포즈 없는 화면 프레임 0 %, 객체 8종 유지, 스캔 간 가속 중앙/p99 0.29/1.56 → **0.11/0.52 cm**, ORB 대비 고주파 차 0.51 → 0.26 cm.

**그림·표 제안:** 타임라인 2줄(원시 즉시 / 평활 0.2 s 후)과 버퍼 교체 화살표.

**발표 노트:** "지연과 정확도의 교환을 자료구조로 회피한 사례". 실시간 시스템 설계에서 자주 쓸 수 있는 패턴.

### P33. hdl_graph_slam 스트리머 (`lidar/hdl_stream.py`)
**핵심 한 줄:** ROS 2 그래프 SLAM을 띄우고, `/odom`과 키프레임 Path를 조합해 **라이다에서도 키프레임 앵커링**을 제공한다.

**슬라이드 본문**
- 기동 구조: 이 스크립트가 `ros2 launch hdl_graph_slam hdl_graph_slam_501.launch.py`를 띄우고, bag의 `/velodyne_points`를 **직렬화된 채로** 10 Hz 재생 + `/clock` 퍼블리시(use_sim_time).
  - 파이프라인: prefiltering → scan matching odometry(fast_gicp, 10 Hz) → graph_slam_node(키프레임 0.5 m/0.25 rad, g2o 2 s 주기, 루프 클로저)
  - 이 프로젝트에서 추가한 퍼블리셔: `/hdl_graph_slam/keyframes`(nav_msgs/Path, 최적화 때마다 전체 키프레임 자세)
- 포즈 계산(`on_odom`): `T_wc = T_map_kf(ref) · T_odom_kf(ref)⁻¹ · T_odom_c`
  - `ref` = 스캔 시각 이전의 최신 키프레임. 즉 **ORB-SLAM3와 같은 의미의 `ref_kf`/`T_w_kf`**를 제공.
  - 키프레임 추정이 아직 없으면 `T_map_odom · T_odom_c`(월드 앵커링, `ref_kf: null`)
- `kf_update` 사유 판정: 루프 카운트 증가 → `loop`, 키프레임이 1 mm 초과 이동 → `optimize`, 그 외 → `periodic`
- 구현 함정 2가지
  - rclpy는 **SingleThreadedExecutor**여야 한다 — MultiThreaded는 GIL을 잡아 재생 루프가 1 스캔/s로 붕괴
  - hello 전 예열(`--warmup-s 20`): 첫 스캔이 DDS + fast_gicp 초기화로 ~10 s 걸려, 예열 없이는 시작 직후 91 스캔을 버렸다

**그림·표 제안:** ROS 노드 그래프(재생 노드 → prefiltering → odometry → graph_slam → 이 브리지).

**발표 노트:** "라이다에도 키프레임 앵커를 준 것"이 카메라/라이다 레인을 동일한 융합 로직으로 다룰 수 있게 한 열쇠.

### P36. 레인(Lane) 개념 — 하나의 SLAM 스트림 = 하나의 독립 세계
**핵심 한 줄:** 레인마다 포즈 버퍼·키프레임 지도·융합·객체 메모리·로그를 따로 가지므로, 두 SLAM을 같은 SAM-6D 검출로 **공정 비교**할 수 있다.

**슬라이드 본문**
- 레인 정의 방법
  - 레인 0 = 기존 인자(`--slam`, `--slam-port`, `--extrinsic`, `--mac-slam-session` …)
  - 추가 레인 = `--lane "name=hdl,slam=hdl,port=17002,ssh=local,session=…,extrinsic=…"`
  - 키: `name label slam port ssh link host session extrinsic tau features params runner color`
- 레인이 보유하는 것
  - 접속 정보(`link`, `host`, `port`, ssh 별칭), 실행 명령 문자열(`remote_command()`)
  - `X`(리그 RT)와 `tau_s`(레인별 시간 오프셋), `slam_clock`(원본 세션이면 프레임 시계 테이블)
  - `PoseBuffer`, `Fusion`, `ObjectMemory`
  - 로그 4종: `slam_poses`, `sam6d_estimates`, `display_objects`, `kf_updates` (레인이 2개 이상이면 파일명에 `_<name>` 접미)
  - 표시 정렬 `align`(다른 레인 → 기준 레인의 4×4)과 그 진단 정보
- 검증 규칙: 레인 이름과 포트는 중복 불가.
- 기준 레인(`Hub.ref`) = **첫 번째 라이다 레인**(z-up, 절대 스케일), 없으면 레인 0.

**그림·표 제안:** 레인 2개(ORB 파랑 / hdl 주황)가 같은 SAM-6D 결과를 받아 각자 융합·메모리를 굴리는 그림.

**발표 노트:** 이 구조 덕분에 "같은 검출, 다른 SLAM"이라는 이상적 비교 실험이 가능하다 — 인식 오차가 공통 인자로 제거된다.

### P37. 기동 절차 — 세 주체를 같은 t0에 출발시키기
**핵심 한 줄:** 모델 적재(8~11 s)와 SLAM 연결이 모두 끝난 뒤에야 재생을 시작하고, 시작 시각 t0를 허브가 정해 모두에게 알린다.

**슬라이드 본문**
- 순서
  1. 허브가 포즈 서버(레인별 포트)를 열고 대기
  2. `start_sam6d()` — 실행용 yaml 생성 후 `sam6d_infer.py`를 conda 파이썬으로 기동. 모델이 다 올라가면 `<out>/sam6d/READY` 파일 생성
  3. 각 레인의 스트리머 기동(`ssh`/`bash`), 스트리머는 접속 후 `hello` 전송
  4. 허브는 **`READY` 존재 + 모든 레인의 `hello`와 소켓**이 갖춰질 때까지 0.2 s 간격 대기
  5. t0 결정: `max(SAM 첫 프레임 시각, 모든 레인의 first_ns_frame) + max(start_s, 0.3) s`
  6. 모든 레인에 `{"type":"start","t0_ns":t0,"rate":rate}` 전송 → `wall0 = monotonic()` 기록 → 재생 시작
- 라이브 모드는 타임라인이 없으므로 `t0 = time.time_ns() + sam_tau_ns`("지금"을 SLAM 호스트 시계로).
  - 2026-09-17 수정: 라이브에서 `start_s` 오프셋을 t0에 더하면 모든 지연 지표에 +0.5 s 가짜 지연이 생겨 제거.
- 종료: 재생 끝 → `--tail-s`(기본 8 s) 대기 후 `summary.json` 저장 → 뷰어는 계속 떠 있음(Ctrl+C까지).

**그림·표 제안:** 세로 시퀀스 다이어그램(허브 / SAM-6D / 스트리머 3열, READY와 hello 합류 지점 강조).

**발표 노트:** "동시 시작"을 지키지 않으면 두 스트림의 데이터 시각이 어긋나 융합이 통째로 틀어진다. 그래서 대기 조건을 명시적 파일과 메시지로 만들었다.

### P38. SAM 세션 재생 루프 (`run_replay`)
**핵심 한 줄:** 표시는 30 fps로 채우고, 추론에는 10 Hz만 보낸다. 밀리면 표시 프레임을 건너뛰어 항상 "지금"을 유지한다.

**슬라이드 본문**
- 루프 한 바퀴
  1. 프레임 i의 마감 시각 `due = wall0 + (t_ns[i] − t0)/rate` 계산
  2. 아직 이르면 최대 50 ms sleep
  3. 마감이 지났으면, **이미 마감된 가장 최신 프레임 j**까지 건너뛴다(`dropped_display += j−i`)
  4. `feed = (now ≥ next_feed)` — 급전 주기(`1/--sam-feed-hz`, 기본 0.1 s)에 걸린 프레임만 depth까지 읽는다
  5. color는 항상 `frames` deque(최대 120장)에 넣어 표시용으로 보관, `replay_t_ns` 갱신
  6. 급전 프레임이면: depth 정렬 → 공유메모리 `FrameWriter.write(rgb, depth, K, t_ns, …)` → `remember_depth()`로 `depth[::8, ::8]` 보관 → `fed += 1`
- 왜 급전을 10 Hz로 제한하나: SAM-6D 처리량이 2.4~5.4 fps라 그 이상 보내면 어차피 덮어써진다(공유메모리는 최신 한 장만 유지).
- 실측(260826 전체): 급전 2,429, 처리 691 — 공유메모리 정책상 나머지는 **의도적으로 버려진다**.

**그림·표 제안:** 타임라인에 표시 프레임(작은 점)과 급전 프레임(굵은 점), 처리 완료 시점(화살표)을 그린다.

**발표 노트:** "프레임을 버리는 것이 기능"이라는 점을 강조. 큐에 쌓으면 지연이 누적돼 실시간 표시가 불가능해진다.

### P39. 프로세스 간 통신 — seqlock 공유메모리 (`shm_channel.py`)
**핵심 한 줄:** 락 없이 "최신 한 장"만 주고받는 구조라, 읽는 쪽이 느려도 쓰는 쪽이 절대 막히지 않는다.

**슬라이드 본문**
- 두 채널
  - `sam6d_frame` (허브 → 추론): 헤더 384 B + RGB + depth, 최대 12 MB
  - `sam6d_result` (추론 → 허브): 헤더 16 B + JSON 바이트, 최대 4 MB
- seqlock 규약
  - 쓰기: `seq += 1`(홀수 = 쓰는 중) → 본문 기록 → `seq += 1`(짝수 = 완료)
  - 읽기: `seq` 확인(짝수·새 값) → 복사 → **다시 `seq` 확인**, 달라졌으면 그 스냅샷을 버린다
- 프레임 헤더 내용: `seq, stamp_ns, h, w, pose_stamp_ns, tracking_ok, depth_stamp_ns` (int64 ×8), `recv_wall + T_map_camera 16` (float64 ×17), `K`(9), `map_id`(UTF-8 96 B)
  - 이 시스템에서는 SLAM 자세를 추론 쪽에 넘기지 않는다(`tracking_state: TRACKING_LOST`, `anchor.enabled=false`) — 앵커 기능을 끄고 순수 per-frame 추정만 받기 위함
- 결과 JSON: `{stamp_ns, t_done_ns, n, dets:[{object, score, R(3×3), t_mm(3), pose_source, …}], ms:{yolo, ism, pem, total}, n_proc, n_det}`
- 부착 타이밍 주의: 허브는 `READY` 파일이 생긴 뒤 **1초 이상 지난 다음**에 결과 채널에 붙는다(이전 실행의 낡은 세그먼트에 붙는 것을 방지).

**그림·표 제안:** seqlock 타이밍도(쓰기/읽기 겹칠 때 버리는 경우 포함).

**발표 노트:** "ROS 토픽 대신 공유메모리"의 이유 — 640×480 RGB+depth를 10 Hz로 넘길 때 직렬화·DDS 비용이 추론 시간에 맞먹었고, 도메인 격리 문제도 있었다.

### P40. PoseBuffer — 자세를 시간순으로 담는 자료구조 (`pc/fusion.py`)
**핵심 한 줄:** 시각 정렬된 배열 + 이진 탐색으로, 임의 시각의 자세를 O(log n)에 보간해 돌려준다.

**슬라이드 본문**
- 저장 단위 `FrameSample`: `t_ns`, `T_w_c`(추적 당시의 실시간 자세), `kf`(참조 키프레임 id), `T_kf_c`(키프레임 기준 상대 자세), `map_id`
- `add(t_ns, state, T_wc, map_id, kf, T_w_kf, kf_map_id, map_changed)`
  - `state`가 `OK`/`OK_KLT`가 아니면 카운트만 하고 버린다(`count_all` vs `count_ok`)
  - **맵 id가 바뀌면 버퍼를 비운다**(Atlas 새 맵 = 다른 월드). 단 `map_changed`(루프 클로저)는 같은 맵이므로 **비우지 않는다** — 이 구분이 중요하다.
  - 키프레임이 오면 `KeyframeMap.set_pose(kf, T_w_kf)`를 갱신하고 `T_kf_c = T_w_kf⁻¹ · T_w_c`를 계산해 저장
  - `bisect.insort`로 시각 순서 유지(네트워크 순서가 뒤바뀌어도 안전)
- `refine(t_ns, T_wc)`: 같은 타임스탬프 항목의 자세를 나중에 교체(KISS-ICP 평활). 이때 `T_kf_c`도 **도착 당시의 키프레임 자세 기준**으로 다시 계산해 일관성을 지킨다.
- 파생 정보: `map_changes`, `loop_events_ns`(루프 시각 목록), `last_state`, `positions(step=3)`(궤적 표시용 샘플)

**그림·표 제안:** 배열 그림 + 이진 탐색 + 삽입 위치 표시.

**발표 노트:** "맵 전환과 루프 클로저를 구분하지 못해 버퍼를 통째로 날리던 버그"가 있었음을 언급하면, 구분의 필요성이 와닿는다.

### P41. KeyframeMap — 지도 보정을 반영하는 장치
**핵심 한 줄:** 키프레임 id → 최신 자세의 사전 하나로, 루프 클로저가 과거의 모든 관측을 한꺼번에 옮긴다.

**슬라이드 본문**
- 보유 상태: `T[id] → T_w_kf`, `map_of[id]`, `redirect[culled_id] → (survivor, T_survivor_culled)`, `corr[id]`(누적 보정 거리), `snapshot`(직전 전체 스냅샷)
- `apply_update(map_id, kfs)` 처리 순서
  1. 새 자세와 기존 자세를 비교해 **이동 거리**를 누적(`corr`), 최대값 `max_correction_m` 갱신
  2. **컬링(culling) 판정**: 업데이트 목록에 없는 기존 키프레임 중 `id < 목록의 최대 id`인 것만 "컬링됨"으로 본다
     - ← **F1 수정(2026-09-14)**: 이 조건이 없을 때, 메시지 생성 이후에 만들어진 새 키프레임(포즈 메시지로 먼저 알게 된 것)을 컬링으로 오판해 잘못 재앵커했다
  3. 컬링된 키프레임은 **직전 스냅샷**(두 키프레임이 함께 존재하던 일관된 지도)에서 가장 가까운 생존 키프레임을 찾아 `redirect`에 상대 자세와 함께 기록하고 `T`에서 제거
  4. 새 자세를 모두 반영, 스냅샷 교체, `updates += 1`
- `resolve(kf)`: `redirect` 사슬을 최대 64회 따라가며 상대 자세를 누적해 `(T_w_kf, map_id)` 반환
- `correction(kf)`: 그 키프레임(또는 생존 앵커)이 지금까지 받은 누적 보정 거리 — 관측 가중치 실험(P66)에 사용

**그림·표 제안:** 키프레임 그래프에서 하나가 컬링되고 이웃으로 재앵커되는 그림(직전 스냅샷 좌표 사용 강조).

**발표 노트:** "SLAM이 키프레임을 지우는 것"까지 다뤄야 실시간 시스템이 며칠짜리 주행에서도 버틴다.

### P42. 키프레임 앵커링 — 이 시스템의 핵심 설계
**핵심 한 줄:** 물체를 월드가 아니라 **키프레임 기준**으로 저장하면, 루프 클로저가 지도를 고칠 때 물체가 함께 따라간다.

**슬라이드 본문**
- 저장/사용 규칙
  - 프레임마다: `T_kf_c = T_w_kf(추적 시점)⁻¹ · T_w_c(실시간)`
  - 추정마다: `T_kf_obj = T_w_kf(현재)⁻¹ · T_w_c(s) · X · T_sam_obj`
  - 사용할 때마다: `T_w_obj = T_w_kf(최신) · T_kf_obj`, `T_w_c(t) = T_w_kf(최신) · T_kf_c(t)`
- 왜 필요한가: 실시간 자세는 **다음 루프 클로저 전까지의 드리프트**를 안고 있다(260826 최대 11 cm, 260910 최대 84 cm). 월드 좌표로 물체를 굳혀 두면 그 오차가 영구히 남는다.
- 앵커 선택: 추정 시각을 감싸는 두 프레임 중 **가까운 쪽의 `ref_kf`**(`PoseBuffer.anchor_at`)
- 루프 클로저 ±1 s 이내의 추정은 표시는 하되 **깨끗한 앵커를 대체하지 않는다**(`near_loop` 플래그, `Fusion.add_estimate`)
- 키프레임을 주지 않는 스트리머(KISS-ICP, 라이브 ORB 노드)는 `kf=None` → 월드 앵커링으로 자동 폴백
- 효과(v3 월드 고정 → v4 키프레임 기준, 같은 조건)

| 지표 | 월드 고정 | 키프레임 기준 |
|---|---|---|
| 루프(86 s) 전후 같은 객체 위치 차 | 평균 5.4 cm (2.8–7.7) | **평균 0.8 cm (0.3–2.0)** |
| 정지 객체 흩어짐 | 중앙 1.5 / p90 7.1 cm | **중앙 0.8 / p90 2.2 cm** |

**그림·표 제안:** 루프 클로저 전후 지도 두 장 + 물체가 함께 이동하는 화살표.

**발표 노트:** 근거 문서 `slam_comparison_report/realtime_30fps/ORB_POSE_CONSISTENCY_FOR_SAM6D.md`의 권장 2번을 구현한 것. 이 장이 논문의 방법론 핵심 중 하나.

### P43. SE(3) 보간 — SAM 프레임 시각의 SLAM 자세 구하기
**핵심 한 줄:** SLAM은 30 Hz, SAM-6D는 ~1 Hz로 서로 다른 순간을 찍으므로, 자세는 항상 보간해서 얻는다.

**슬라이드 본문**
- `bracket(t_ns)`: 이진 탐색으로 t를 감싸는 두 샘플을 찾고, **간격이 `--max-gap`(기본 0.25 s) 이하일 때만** `(a, b, α)` 반환. 정확히 같은 시각이면 그 샘플.
- `at(t_ns)` → `(T, status)`:
  - 각 샘플을 먼저 `corrected()`로 통과 — `kf`가 있으면 `T_w_kf(최신) · T_kf_c`로 **보정된 자세**를 만든다
  - 회전은 `Slerp`(scipy), 평행이동은 선형 보간
  - `status`는 `"exact"` 또는 `"interp"`, 구할 수 없으면 `None`
- `Fusion.T_w_sam(t)` = `at(t + t_offset_ns) · X` — 레인별 τ 차이를 `t_offset_ns`로 흡수
- 보간 가정의 유효 범위(실측): 간격 ≤3 s에서 중앙 0.5 cm, 3–10 s 1.06 cm, 10–60 s 5.4 cm → 표시 지연 0.3 s 조건에서는 오차가 무시 가능
- 자세가 없으면 그 추정은 **버려진다**(`unplaced` 카운트) — P45의 대기 로직이 이를 최소화한다.

**그림·표 제안:** 시간 축에 SLAM 샘플(촘촘)과 SAM 프레임(듬성), 사이에 보간 화살표.

**발표 노트:** "보간이 왜 정당한가"는 데이터로 답한다 — 위 실측 표가 그 근거.

### P44. Fusion.add_estimate — 추정 한 건이 처리되는 전 과정
**핵심 한 줄:** 검출 하나가 들어오면 6단계를 거쳐 키프레임 기준 관측으로 저장된다.

**슬라이드 본문**
1. **입력 변환**: SAM-6D의 `R`(3×3)와 `t_mm`(3)을 4×4 `T_sam_obj`로 만들고 mm → m
2. **자세 조회**: `T_w_sam(t) = poses.at(t + t_offset)·X`. 없으면 `unplaced += 1`, `{"placed": False}` 반환
3. **월드 좌표 계산**: `T_w_obj = T_w_sam · T_sam_obj`
4. **앵커 결정**: `kf = poses.anchor_at(t)`, `T_w_kf = kfs.resolve(kf)` → `T_anchor = T_w_kf⁻¹ · T_w_obj` (키프레임이 없으면 월드 앵커)
5. **루프 근접 판정**: `near = poses.near_loop_closure(t, ±1 s)`
6. **트랙 갱신**: 이름별 `ObjectTrack`에 `Observation(t_ns, kf, T_anchor_obj, score, near_loop)` 추가
   - `current` 교체 조건: 시각이 더 최신이고, **(루프 근접이 아니거나 기존도 루프 근접일 때)**
   - `history`는 최근 500개만 보관
- 반환값은 그대로 `sam6d_estimates.jsonl` 한 줄로 기록(placed, slam_interp, anchor_kf, near_loop, T_w_obj, result_age_s, pose_wait_s, ms)

**그림·표 제안:** 6단계 플로차트 + 각 단계의 수식.

**발표 노트:** 여기까지가 "한 장의 인식 결과가 지도 위 한 점이 되는" 과정. 다음 장부터는 그것을 **여러 장에 걸쳐 종합**하는 이야기(객체 메모리).

### P45. 결과 대기(pose_wait) — 늦게 도착한 자세를 기다리는 장치
**핵심 한 줄:** SAM-6D 결과가 그 프레임의 SLAM 자세보다 먼저 도착하면 검출이 통째로 버려진다. 그래서 순서를 지켜 최대 2초까지 기다린다.

**슬라이드 본문**
- 문제(2026-09-17 관측): f3000 재생에서 **399건 중 258건이 자세 없음으로 소실**. 원인은 SLAM이 느리거나 큐가 밀려 자세가 늦게 온 것.
- 해결(`run_results`)
  - 수거한 결과를 `pending` 큐에 **도착 순서대로** 넣는다
  - 큐의 맨 앞부터: 모든 레인이 `poses.latest_t() ≥ fusion.slam_t(stamp)`가 되었거나, 레인이 종료됐거나, `--pose-wait-s`(기본 2.0 s)가 지났을 때만 처리
  - 통계 기록: `waited`(20 ms 초과 대기 건수), `timed_out`, `max_wait_s` → `summary.json`
- 부작용 관리: 대기 중에도 화면 렌더는 계속 돈다(표시는 최신 프레임, 객체는 직전 추정 유지). 즉 대기가 화면을 멈추지 않는다.
- 결과 나이(`result_age_s`)와는 별개 개념: 나이는 "프레임 촬영 → 결과 도착"이고, 대기는 "결과 도착 → 자세 확보".

**그림·표 제안:** 두 타임라인(자세 도착 / 결과 도착)과 대기 구간 표시.

**발표 노트:** 이런 종류의 버그는 지표에 "검출 수 감소"로만 나타나 원인을 찾기 어렵다 — 로그에 `pose_wait_s`를 남기도록 한 이유.

### P46. 표시 프레임 선택과 화면 지연 (`run_render`)
**핵심 한 줄:** 화면에는 일부러 0.3초 과거 프레임을 그린다 — 그래야 그 시각의 SLAM 자세를 **보간**으로 정확히 얻을 수 있다.

**슬라이드 본문**
- 루프(15 Hz)
  1. `target = replay_t_ns − display_delay(기본 0.3 s)`
  2. `frames` deque를 뒤에서부터 훑어 `t_ns ≤ target`인 첫 프레임 선택(없으면 가장 오래된 것)
  3. 레인마다 `lane_frame()` 실행 → 오버레이 JPEG + 객체 목록 + 궤적(1 s마다)
  4. SSE payload 구성 후 `broadcast()`
- 왜 지연을 두는가: SLAM 자세는 도착에 20~100 ms 걸리고, 보간은 **앞뒤 두 샘플**이 있어야 한다. 0.3 s면 대부분의 경우 양쪽 샘플이 확보된다.
- 표시 정책
  - `--overlay-max-age`(기본 60 s): 마지막 추정으로부터 이 시간 안의 객체만 영상에 그림
  - 객체가 SAM-6D 추정 시각 ±20 ms 안이면 `source="sam6d"`(굵은 선), 아니면 `slam_interp`(가는 선 + "interp +x.xs" 표기)
- 브로드캐스트 백프레셔: 클라이언트 큐가 4개를 넘으면 가장 오래된 payload를 버린다(느린 브라우저가 허브를 막지 못하게).

**그림·표 제안:** 시간 축에 재생 시각, 표시 시각(−0.3 s), SLAM 자세 도착 범위를 겹쳐 그린다.

**발표 노트:** "지연을 없애는 것이 아니라 **지연을 예산으로 관리**한다"는 관점을 설명. 0.3 s는 SAM-6D 결과 나이(0.8 s)와는 다른 축이다.

### P47. 영상 오버레이 그리기 (`draw_objects`, `project`)
**핵심 한 줄:** 3D 박스를 화면에 그릴 때, 왜곡 모델이 시야 밖 점을 화면 안으로 접어 넣는 현상까지 막아야 그림이 깨지지 않는다.

**슬라이드 본문**
- 그리는 것: CAD 바운딩 박스 12개 모서리 + 물체 원점 3축(길이 = 최대 치수 × 0.6) + 라벨(이름 + `SAM-6D` 또는 `interp +x.xs`)
- 투영: 핀홀 + Brown-Conrady(k1,k2,p1,p2,k3). 카메라 좌표 `T_cam_obj`로 점을 옮긴 뒤 투영.
- 세 가지 방어
  1. **뒤/옆 물체 제외**: 박스 8개 꼭짓점 중 하나라도 `z < 0.2 m`면 그리지 않음
  2. **왜곡 접힘 방지**: `r² > 1.3²`이면 왜곡 없이 투영 — 컬러 모델의 방사 다항식이 `r = 1.63` 너머에서 접혀, 65° 밖의 점이 화면 안 엉뚱한 곳(약 1000 px 오차)에 찍히고 화면을 가로지르는 선이 생겼다(이미지 모서리는 r = 1.06)
  3. **선 잘라내기**: `cv2.clipLine`으로 화면 밖 구간 제거, 중심이 화면 밖이면 통째로 생략
- 색: 물체별 고정 팔레트, 선 두께는 SAM-6D 원본 2 px / 보간 1 px. 좌상단에 레인 라벨을 레인 색으로.
- 인코딩: JPEG 품질 78 → base64 → SSE

**그림·표 제안:** 왜곡 접힘 버그의 before/after 스크린샷.

**발표 노트:** 사소해 보이지만 "화면이 이상하다"는 인상을 주는 대표적 요인이라 한 장 배정. 시연 중 질문이 나오기 쉬운 부분.

### P48. 출력 산출물 — 실행 하나가 남기는 것
**핵심 한 줄:** 모든 실행은 `output/<run>/`에 원시 로그 6종 + 요약 1종을 남기고, 이후 분석은 전부 이 파일들만으로 재현된다.

**슬라이드 본문**

| 파일 | 한 줄의 내용 |
|---|---|
| `slam_poses[_lane].jsonl` | 수신한 pose 메시지 원문 + `recv_lag_s`(+ 평활 레인은 `T_wc_raw`, `refine_lag_s`) |
| `kf_updates[_lane].jsonl` | kf_update 원문(키프레임 전체 자세 포함) |
| `sam6d_estimates[_lane].jsonl` | 검출 1건 = 1줄. `placed`, `slam_interp`, `anchor_kf`, `near_loop_closure`, `T_w_obj`, `result_age_s`, `pose_wait_s`, `ms` |
| `display_objects[_lane].jsonl` | 화면 프레임마다 그려진 객체와 `T_cam_obj` |
| `sam6d_frames.jsonl` | 허브가 받은 결과 프레임(검출 0건 포함) |
| `sam6d/frames.jsonl`, `detections.jsonl` | 추론 프로세스 자체의 프레임·검출 기록(단계별 ms, 진단) |
| `summary.json` | 전체 통계 + 레인별 통계 + 최종 객체 목록 + 모든 관측의 최종 월드 좌표 + 메모리 랜드마크 + depth 검사 기록 |
| `sam6d_infer.log`, `mac_slam[_lane].log`, `mac_command*.txt` | 자식 프로세스 로그와 실제 실행된 명령 |

- `summary.json`의 `observations_final`은 **모든 관측을 최종 키프레임 자세로 다시 계산한 위치** — "흩어짐" 지표가 여기서 나온다.
- 이 설계 덕분에 "로그만으로 허브 파이프라인을 mm 단위로 재현"하는 사후 분석이 가능했다(P81의 루프 분열 원인 규명).

**그림·표 제안:** 출력 디렉터리 트리 + 각 파일이 어느 분석에 쓰이는지 화살표.

**발표 노트:** 교수님이 "그 수치의 근거는?"이라고 물으면 열 파일이 정해져 있다는 점을 말씀드리면 좋다.

### P49. 추론을 별도 프로세스로 분리한 이유
**핵심 한 줄:** 고속 영상 수신과 무거운 추론을 같은 파이썬 인터프리터에 두면 GIL 때문에 추론이 초 단위로 굶는다.

**슬라이드 본문**
- 구조: `hub.py`(수신·재생·융합, ROS 있을 수 있음) ↔ 공유메모리 ↔ `sam6d_infer.py`(**ROS 전혀 없음**)
- 근거: 같은 인터프리터 구성에서 추론이 초 단위로 정지(NOTES 19–21절). ROS 밖 실측 상한 ISM 107 ms / PEM 156 ms.
- 추론 프로세스가 하는 일
  1. 설정 yaml 로드 → `Sam6DCore` 생성(모델 적재 8.7–10.8 s)
  2. `READY` 파일 생성 → 허브가 이를 보고 재생 시작
  3. 루프: 공유메모리에서 최신 프레임 1장 → `core.process()` → 결과를 공유메모리 JSON으로 → jsonl 기록
  4. 입력이 끊기면(`idle_exit_s`, 허브 실행 시 0 = 무한) 종료, `run_meta.json`에 요약 기록
- 허브가 만드는 실행 설정: 템플릿 yaml(`run_split_example.yaml`)에서 출력 디렉터리·`anchor.enabled=false`·속도 프리셋만 바꿔 `<out>/sam6d_config.yaml`로 저장 → **실행 조건이 산출물에 남는다**

**그림·표 제안:** 두 프로세스 박스 + 공유메모리 2채널 + READY 파일.

**발표 노트:** "실시간 시스템에서 파이썬 GIL을 프로세스 경계로 회피한 사례"로 소개.

### P50. Sam6DCore 적재 — 어떤 모델이 올라가는가
**핵심 한 줄:** YOLO-World + MobileSAM + DINOv2 + SAM-6D PEM 네 모델과 물체별 템플릿 자산이 한 번에 올라간다.

**슬라이드 본문**
- **YOLO-World**(`yolov8m-worldv2.pt`): 텍스트 프롬프트로 후보 박스 생성. 물체별 프롬프트를 모아 `set_classes(unique_prompts)`.
- **MobileSAM**(`mobile_sam.pt`): 박스 프롬프트 → 인스턴스 마스크.
- **DINOv2**: 크롭의 cls/patch 토큰 → 템플릿 특징과의 코사인 유사도(의미/외형 점수).
- **SAM-6D PEM**(`sam-6d-pem-base.pth`, `gorilla` config `base.yaml`): 관측 점군 + 템플릿 dense 특징 → 6D 자세.
- 물체별 자산 로드: `model_points/<n>.npy`(CAD 점, extent 계산에 사용), `pem_templates/<n>.pt`(`tp` 점, `tf` 특징, `tc` 색)
- 트릭: `ric.trimesh.load_mesh`를 물체 이름 → 미리 로드한 점군 스텁으로 치환해, 원본 SAM-6D 추론 코드를 고치지 않고 메모리 상의 CAD를 쓰게 한다.
- 예열(`_warmup`): 회색 이미지로 YOLO·ISM을 한 번 돌려 커널·캐시를 데운다.
- 속도 옵션은 전부 **opt-in**: 키가 없으면 예전 동작(fp32 / 캐시 off / 예산제 off) 그대로.

**그림·표 제안:** 네 모델 + 자산 파일을 한 그림에.

**발표 노트:** "SAM-6D 원본을 고치지 않고 붙였다"는 점을 다시 강조(비교 실험의 공정성).

### P51. ISM 1단계 — YOLO-World 후보 박스
**핵심 한 줄:** 한 번의 YOLO 추론으로 모든 물체의 후보를 뽑고, 물체별 임계값은 그 뒤에 적용한다.

**슬라이드 본문**
- 입력: BGR 프레임. `conf = min(모든 물체의 score_threshold)`(기본 0.02), `imgsz = 640`
- `multi_label_nms` 컨텍스트: 기본 YOLO NMS는 박스마다 top-1 클래스만 남기지만, 한 박스가 여러 프롬프트에 걸릴 수 있으므로 **임계 이상 모든 클래스를 유지**하도록 감싼다.
- 결과 정리: 프롬프트 인덱스별로 `[(box, conf), …]`를 conf 내림차순 정렬 → `pb` 사전. 박스 좌표는 이미지 경계로 클리핑.
- 물체별 후처리(`recognize`에서): 자기 `score_threshold` 이상만 남기고 `top_k`(기본 3)개까지 사용.
- 시간 비중: 전체 추론의 **6.4 %**(260910 pooled).

**그림·표 제안:** 프레임 위 YOLO 박스들과 프롬프트 라벨.

**발표 노트:** 프롬프트 공유·NMS 우회는 "여러 물체를 한 패스로"를 위한 엔지니어링. 물체 수가 늘어도 YOLO 비용이 늘지 않는다.

---

### P52. ISM 2단계 — 의미·외형 게이트와 마스크 (`recognize`)
**핵심 한 줄:** 후보 박스를 DINOv2 특징으로 템플릿과 비교해 두 단계 게이트(의미 → 마스크 기반 외형)를 통과해야 검출로 인정한다.

**슬라이드 본문**
- 절차(물체 1개 기준)
  1. 후보 박스마다 크롭 → 정규화 → DINOv2 forward(요청 블록의 cls + patch 토큰을 **한 번에**, 승자만 host 복사)
  2. `semantic_score(cls, tcls, match_topk)` — 템플릿 cls 특징과의 상위-k 코사인 평균. 최고값이 `similarity_threshold` 미만이면 `no-object(below-sim)`
  3. 승자 박스로 **MobileSAM** 분할 → 마스크
  4. 최적 템플릿 선택(`argmax(tcls @ cls)`) → `masked_appe`: 마스크 안의 patch 토큰만 평균해 그 템플릿의 patch 특징과 비교(블록 2+9 평균)
  5. `masked_appe ≥ appe_gate`이면 `detected`, 아니면 `no-object(below-appe)`
  6. **HSV 색 게이트**: 채택 후보에 대해 렌더 기준 HSV 히스토그램(H×S = 16×8 = 128차원)과 비교, 임계 0.1214 미만이면 탈락
- 게이트 조합의 근거(사람이 직접 라벨링한 959셀 기준): 블록11 단독 F1 .774 → 블록2+9(게이트 0.605) .789 → + cross-object NMS **.809**
- 시간 비중: 전체의 **36.6 %**

**그림·표 제안:** 한 후보가 4개 게이트를 통과/탈락하는 플로차트 + 각 단계 점수 표시.

**발표 노트:** "게이트와 임계값은 항상 **쌍으로** 움직인다"는 교훈(2026-07-15 실패 사례: 블록만 바꾸고 임계는 그대로 둬서 오검출 폭증).

---

### P53. ISM 3단계 — 물체 간 경쟁 (cross-object NMS)
**핵심 한 줄:** 한 박스에 여러 물체가 걸릴 때, 독립 임계값이 아니라 **서로 비교**해 주인을 정한다.

**슬라이드 본문**
- 문제: 비슷한 형상(상자류)에서 여러 물체가 같은 박스를 각자 통과 → 중복 검출.
- 해결: `relative_assignment` / `cross_object_nms` — 같은 영역을 주장하는 후보들 사이에서 순위 점수(`rank_appe`)를 비교해 하나만 남긴다. 형상이 구분되지 않는 쌍(`template_similarity ≥ τ`)은 색으로 타이브레이크.
- 효과(인간 검증 GT 959셀): FP 96 → **28**, F1 .789 → **.809**
- 남은 FP 28건 중 24건은 `choco_hazelnut`이 평범한 갈색 택배 상자에 붙는 것 — 별개의 오래된 문제로 분리해 기록.
- 이 단계까지 통과한 것만 PEM으로 넘어간다(`accepted && mask is not None`).

**그림·표 제안:** 같은 박스를 두 물체가 주장하는 그림 → 비교 후 1개 선택.

**발표 노트:** "임계값 튜닝"이 아니라 "상대 비교"로 바꾼 것이 요점. 임계값은 장면이 바뀌면 깨지지만 상대 비교는 덜 깨진다.

---

### P54. PEM 입력 만들기 — 마스크와 depth의 교집합
**핵심 한 줄:** 자세 추정은 마스크 안의 **유효 depth 점군**으로만 가능하므로, 그 점이 부족하면 조용히 버려진다. 그 조건을 진단으로 남겼다.

**슬라이드 본문**
- 입력 구성(`ric.prepare_frame`, `get_instance_data`)
  - `frame["pts"]`: depth와 K로 만든 화소별 3D 점
  - 검출마다 `{score: 1.0, mask, cad: 물체명}`
- 버려지는 두 조건(프레임 진단 `pem_candidates`에 기록)
  1. `valid_depth_px ≤ 32` — 마스크 ∩ (depth > 0) 화소가 32개 이하
  2. `radius_inliers < 4` — 점군 중심(평균/중앙값 둘 다 시도)에서 CAD 반경 ×1.2 안에 드는 점이 4개 미만
- 이 진단을 넣기 전에는 모든 후보가 걸러지면 `torch.stack([])` 예외만 나서 **어느 물체·어느 입력이 원인인지 알 수 없었다**.
- 기록되는 값: `mask_px`, `valid_depth_px`, `radius_inliers`, `input_rejection`, `used_by_pem`
- 관측 점 수는 `fine_npoint`(기본값 또는 1024)로 샘플링되며, `n_sample_observed_point`도 함께 바꿔야 한다(ViTEncoder가 둘의 일치를 단언).

**그림·표 제안:** 마스크 / depth 유효 영역 / 교집합 3장 + 반경 필터 그림.

**발표 노트:** "실패를 관측 가능하게 만든다"는 원칙의 사례. 디버깅 시간을 크게 줄였다.

### P55. PEM 추론 — coarse → fine → 검증
**핵심 한 줄:** 템플릿 dense 특징과 관측 점군을 대응시켜 자세를 내고, 마스크 IoU·텍스처·클러스터 점유로 **자체 검증**한 뒤에만 채택한다.

**슬라이드 본문**
- forward 입력: 관측 점군·RGB 크롭·`dense_po`(템플릿 점), `dense_fo`(템플릿 특징), `dense_co`(템플릿 색, 있으면), `obj_names`(대칭 조회용)
- 출력: `pred_R`, `pred_t`(m → mm 변환), `score`(coarse), `pred_pose_score` → 최종 점수 `ps = coarse × pose_score`
- 유효성 검사: R이 직교(‖RᵀR − I‖ ≤ 1e-2)이고 det > 0.99, 값이 유한할 것
- **검증 단계(Stage V)**: `verify` 결과의 `accepted`가 False면 그 검출은 버리고 `rejection_reason`을 남긴다
  - 지표: `rank_geo`(기하 후보 순위), `fine.mask_iou`, `fine.texture_score`, `cluster_occupancy`
- 채택된 행에 함께 저장되는 진단: `mask_px`, `depth_valid_frac`, `crop_sharpness`(라플라시안 분산), `z_med_mm`, `n_pts_in`, `coarse`, `pose_score`, `batch`
- 시간 비중: 전체의 **57.0 %** — 파이프라인에서 가장 무거운 단계

**그림·표 제안:** 관측 점군 ↔ 템플릿 점군 대응 그림 + 검증 지표 4종 아이콘.

**발표 노트:** 검증 임계값이 **fp32로 캘리브레이션**돼 있다는 점이 다음 장(속도 옵션)의 핵심 제약이 된다.

### P56. 속도 옵션 — 채택한 것과 기각한 것
**핵심 한 줄:** 권장 설정을 그대로 쓰지 않고 이 배치(9객체 + 검증 스택)에서 직접 재봤고, 절반은 기각했다.

**슬라이드 본문**

| 옵션 | 기대 효과 | 이 배치 실측 | 결정 |
|---|---|---|---|
| `fine_npoint 1024` | 관측 점 수 감소 | total −9 %, 검출 수·자세 유지(1.2 mm / 1.3°) | **채택** |
| `mask_cache`(IoU 0.90, 최대 5프레임, 30 간격) | 마스크 재사용 | 카메라가 움직이면 재사용률 2 %(이득 ≈ 0), 무해 | **채택** |
| `precision bf16` | 절반 정밀도 | 검출 채택률이 fp32 대비 **17~22 %로 붕괴** (검증 임계가 fp32 기준) | 기각 |
| `pem_schedule`(프레임당 예산 1) | PEM 호출 감축 | carried 자세가 카메라 이동만큼 낡아 **77~131 mm 오차** | 기각 |

- 프리셋으로 정리: `off`(2026-09-14 이전 동작) / `fast`(기본, 채택 2종) / `report`(문헌 권장 그대로, 재현용으로만 보존)
- 설계 원칙: 기각한 옵션도 **재현 가능한 형태로 남긴다** — 나중에 임계값을 재캘리브레이션하면 다시 평가할 수 있다.
- 근거 문서: `sam6d_realtime/_speed_opt_2026_09_13/REPORT.md` §9, `objpose/docs/sam6d_inference_speed_260914.md`

**그림·표 제안:** 위 표 + "채택/기각" 색 구분.

**발표 노트:** "권장값을 그대로 쓰지 않고 우리 조건에서 재측정했다"가 이 장의 메시지. 특히 bf16 붕괴는 검증 스택과의 상호작용이라 문헌에 없는 발견.

### P57. SAM-6D 처리량·지연 실측
**핵심 한 줄:** 초당 2.4~5.4 프레임을 처리하고, 결과는 촬영 시점으로부터 중앙 0.8~0.9초 뒤에 도착한다 — 이 값이 시스템 설계의 모든 지연 예산을 결정한다.

**슬라이드 본문**

| 항목 | 값 |
|---|---|
| 처리량(260910, 5회 평균) | **5.4 fps** (급전 9.0 fps 중 59.6 % 처리) |
| 처리량(260826) | 2.44 fps (급전 8.5 fps 중 28.9 %) |
| 프레임당 total(중앙/p90/p99) | 32 / 490 / 1,000 ms (260910) |
| 검출이 있는 프레임의 total 중앙 | 690–740 ms (260910), 407 ms (260826) |
| 단계별 비중 | YOLO 6.4 % · ISM 36.6 % · **PEM 57.0 %** |
| 결과 나이 `result_age_s` | 중앙 **0.82–0.90 s**, p99 1.3–1.6 s |
| 모델 적재 | 8.7–10.8 s |
| GPU | RTX 4090 ×4 중 **cuda:0 한 장만** 사용 |

- 함의 1: 결과 나이(0.8 s) > 표시 지연(0.3 s) → **화면에 보이는 박스는 거의 항상 보간된 자세**로 그려진다. 그래서 보간 품질이 곧 화면 품질이다.
- 함의 2: 검출 0건 프레임은 32 ms로 끝나고, 검출이 있으면 700 ms로 뛴다 — 처리량이 장면에 따라 크게 변한다.
- 개선 여지: GPU 1장만 쓰고 있으므로, 물체별 PEM 배치를 나누어 다중 GPU로 보내는 것이 다음 후보.

**그림·표 제안:** 프레임별 total 시간 히스토그램(두 봉우리: 검출 없음 / 있음).

**발표 노트:** "실시간"이라는 말의 실제 의미를 숫자로 제시하는 장. 교수님이 가장 많이 질문할 지점일 수 있다.

### P58. 인식 블록 요약 — 무엇이 SAM-6D의 책임인가
**핵심 한 줄:** 인식 블록은 "이 프레임에 무엇이 어디에 있는가"만 답하고, 시간·지도·누적은 전혀 모른다.

**슬라이드 본문**
- 입력: RGB(640×480) + 정렬된 depth(uint16 mm) + K + 타임스탬프
- 출력: `{stamp_ns, dets: [{object, score, R, t_mm}], ms}` — **카메라 좌표계**, 프레임 독립
- 모르는 것: 카메라가 어디 있는지, 이전 프레임에 무엇을 봤는지, 물체가 몇 개인지
- 알고 있는 것: 물체 9종의 CAD·템플릿·색·대칭 선언
- 이 경계 설정의 이점
  - SAM-6D를 **수정 없이** 교체·업그레이드할 수 있다
  - 같은 검출을 여러 SLAM 레인에 동시에 먹여 공정 비교가 가능하다
  - 인식 성능(검출률·자세 정확도)과 시스템 성능(지도 일관성)을 분리해 측정할 수 있다
- 한계: 프레임 독립이라 자세가 이봉/다봉으로 튄다(같은 면을 보고도 180° 뒤집힌 답) → 다음 6부(객체 메모리)가 이를 처리한다.

**그림·표 제안:** 입력/출력 상자 + "모름" 목록을 회색으로.

**발표 노트:** 이 장이 5부와 6부를 잇는 다리. "프레임 단위 인식의 한계"를 명시해야 메모리의 필요성이 자연스럽다.

# 6부. 객체 메모리 (P59–P68)

### P59. 왜 메모리가 필요한가
**핵심 한 줄:** 프레임 단위 추정은 흔들리고, 사라지고, 거짓으로 나타난다. 지도는 "지금 본 것"이 아니라 "지금까지 본 것의 종합"이어야 한다.

**슬라이드 본문**
- 프레임 단위 추정의 네 가지 문제
  1. **잡음**: 같은 정지 물체의 위치가 프레임마다 cm 단위로 흔들린다
  2. **회전 이봉성**: 같은 면을 보고도 180° 뒤집힌 자세가 섞여 나온다 → 단순 평균은 **한 번도 관측된 적 없는 중간 자세**를 만든다(실측: 우유팩이 모든 실제 관측과 24° 어긋난 유령 자세)
  3. **간헐적 미검출**: 잠깐 안 보인다고 물체가 사라지면 안 된다
  4. **거짓 양성**: 한 번 튄 검출이 지도에 영구히 남으면 안 된다
- 추가 요구: 같은 클래스의 물체가 **여러 개** 있을 수 있다(다중 인스턴스)
- 해결: `objectmemory_ws`의 `StreamingObjectMemory`를 **그대로** 사용하고, 키프레임 좌표계와 잇는 어댑터(`pc/memory.py`)만 새로 작성

**그림·표 제안:** 같은 물체의 관측 산포도(회색 점) 위에 메모리가 수렴시킨 한 점(빨강).

**발표 노트:** 이 네 가지가 각각 뒤 장의 연관·융합·존재확률·depth 검사에 대응한다고 예고하면 구조가 명확해진다.

---

### P60. 어댑터 — 키프레임 좌표계와 월드 기반 메모리 잇기 (`pc/memory.py`)
**핵심 한 줄:** 메모리는 월드 좌표로 동작하고 이 시스템은 키프레임 상대 좌표로 저장한다. 그래서 지도가 바뀌면 **메모리를 처음부터 다시 만든다**.

**슬라이드 본문**
- 보관 단위 `SamFrame`: `t_ns`, `kf`, `T_anchor_sam`(= `T_kf_sam`, 키프레임 없으면 `T_w_sam`), `dets`[(이름, 점수, `T_sam_obj`)], `depth`(다운샘플 depth)
  - **검출이 0건인 프레임도 보관한다** — 미검출은 존재확률을 낮추는 증거이므로 버리면 안 된다
- 평상시(`update()`): 새로 들어온 프레임만 순서대로 메모리에 먹인다(증분)
- 키프레임 자세가 바뀌면(`kfs.updates` 값 변화): **전체 재구성**
  1. 새 `StreamingObjectMemory` 인스턴스를 만든다
  2. 보관된 모든 프레임을 보정된 카메라 자세(`T_w_kf(최신) · T_kf_sam`)로 다시 재생
  3. 다 만든 뒤 원자적으로 교체 → 읽는 쪽(렌더 스레드)은 기다리지 않는다
- 비용: 한 실행이 수백 프레임 규모라 **308 프레임 재구성에 75 ms**. 0.2 s 주기 루프에서 충분히 감당.
- 이 구조의 의미: 루프 클로저가 일어나면 "과거의 모든 관측이 보정된 좌표로 다시 종합된" 메모리가 된다.

**그림·표 제안:** 프레임 보관 리스트 → (kf_update) → 전체 재생 → 새 메모리 교체 도식.

**발표 노트:** "증분 + 필요 시 전체 재계산"은 실시간성과 정확성을 모두 얻는 값싼 절충. 프레임 수가 수만이 되면 재고해야 할 지점이기도 하다(한계 장에서 언급).

### P61. 메모리 한 프레임 처리 흐름 (`StreamingObjectMemory.step`)
**핵심 한 줄:** 한 프레임은 측정 → 연관 → 수용/신규 → 미검출 감쇠 → 상태 전이의 다섯 단계를 거친다.

**슬라이드 본문**
- 입력: `dets`(`Sam6DDetection`: stamp, detection_id, object_name, `T_cam_obj`, score, weight), `pose`(`SlamCameraPose`: `T_map_cam`, tracking_status), `ts`, `frame_idx`, `depth`(옵션)
- 단계
  1. **측정 계산**: `T_meas = T_map_cam · T_cam_obj` (월드 좌표) + 점수 하한(`score_floor`) 검사
  2. **후보쌍 생성**: 같은 클래스의 살아 있는 인스턴스마다 위치 차·회전 차 계산, 게이트 통과한 쌍만 보관
  3. **탐욕적 1:1 배정**: 거리 오름차순으로 검출–인스턴스를 짝지음(각각 한 번만 사용)
  4. **수용**: 자세 융합 + 존재확률 상승 + 관측 수 증가 + 승격/재획득 판정
     **미배정**: 새 tentative 인스턴스 생성(`initiator`)
  5. **미검출 처리**(`deleter`): 이번 프레임에 안 잡힌 인스턴스마다 depth 검사 → 존재확률 감쇠 → 상태 전이/삭제
- 출력 `FrameResult`: 프레임별 결정 목록(`AssociationDecision`)과 모든 인스턴스의 스냅샷(시각화·진단용)
- 자세가 없는 프레임은 `step_no_pose()` — 검출을 전부 버리고 메모리를 얼린다(INV-008).

**그림·표 제안:** 5단계 플로차트.

**발표 노트:** 이 구조가 Stone Soup 계열 다중표적 추적의 initiator/deleter 패턴을 따른다는 점을 언급하면 학술적 위치가 분명해진다.

### P62. 연관(association) — 어떤 검출이 어떤 물체인가
**핵심 한 줄:** 같은 클래스 안에서 위치 거리로만 짝짓고, 회전은 게이트에서 **일부러 뺐다**.

**슬라이드 본문**
- 게이트
  - 위치: `assoc_trans_gate_m` — **0.15 m → 0.30 m로 상향**(2026-09-14, F2)
  - 회전: `assoc_rot_gate_deg` — 이 시스템에서는 **None(비활성)**
  - tentative 상태는 게이트 ×3(`TENTATIVE_GATE_MULT`)으로 완화 — 추정이 아직 수렴 중이므로
- 회전 게이트를 끈 이유: 상자형 물체에서 SAM-6D 자세가 180° 뒤집혀 나오는 일이 잦아, 45° 게이트가 **한 물체를 두 인스턴스로 쪼갰다**.
- 위치 게이트를 0.30 m로 올린 이유: 루프 클로저로 키프레임이 최대 0.29 m 변형되면서 같은 물체의 관측이 게이트 밖으로 나가 분열이 발생(`docs/loop_split_analysis_260914.md` F2).
- 매칭 실패 = 거부가 아니라 **신규 인스턴스 생성**: 진짜 두 번째 물체이거나, 오염된 첫 자세에 가려진 좋은 군집일 수 있기 때문. 가짜는 존재확률 필터가 정리한다.
- 배정은 프레임 안에서 1:1(탐욕, 거리 오름차순).

**그림·표 제안:** 검출 2개 × 인스턴스 3개의 거리 행렬과 탐욕 선택 순서.

**발표 노트:** "게이트를 끄고 올린" 두 결정 모두 **실패 사례에서 역산**된 것이라는 점이 중요. 근거 문서가 있다.

### P63. 자세 융합 (1) — 위치는 평균, 회전은 다수결
**핵심 한 줄:** 위치는 러닝 평균으로 잡음을 누르고, 회전은 평균 대신 **표가 가장 많은 자세(모드)**를 쓴다.

**슬라이드 본문**
- 위치: 증분 평균 `w = max(1/(n+1), MIN_FUSE_WEIGHT)`
  - `MIN_FUSE_WEIGHT = 0.05`(F2, 2026-09-14): 관측 50회면 새 관측의 영향이 2 %라 **루프 후 지도 변형을 따라가지 못해** 다음 관측이 게이트 밖으로 나가고 인스턴스가 쪼개졌다. 하한을 둬서 항상 5 %는 따라가게 함.
- 회전: **모드 다수결**(스트리밍 군집)
  - 대표 자세 목록 `[(quat, 표), …]`을 유지, 새 측정이 30°(`MODE_FUSION_TOL_DEG`) 안의 대표에 붙으면 그 대표를 nlerp로 갱신하고 표 +1, 아니면 새 봉우리 생성(최대 8개)
  - 출력 자세 = 표가 가장 많은 봉우리
  - `mode_occupancy` = 으뜸 봉우리의 표 점유율(신뢰도 지표)
- 왜 평균이 아닌가: SAM-6D 자세는 이봉/다봉이라 평균이 **관측된 적 없는 중간 자세**를 만든다.
- 실측 효과(운영 무변경 재생, 4 bag): 지도 배회 1470° → 714°(−51 %), milk 유령 자세 11° → 1°, 관측 일치율 6 % → 51 %. **비대칭 물체에도 효과**(Dinosaur −84 %, Bear −47 %)라는 점이 중요.

**그림·표 제안:** 회전 각도 히스토그램(이봉) + 평균값(골짜기)과 모드값(봉우리) 표시.

**발표 노트:** 이 부분이 객체 메모리에서 가장 논문성이 있는 기여. "대칭 선언보다 효과가 크고, 손으로 쓴 표에 의존하지 않는다"는 점을 강조.

### P64. 자세 융합 (2) — 대칭 물체 처리
**핵심 한 줄:** 원리적으로 각도가 정의되지 않는 축만 손으로 선언하고, 섞기 전에 동치 자세로 회전시켜 맞춘다.

**슬라이드 본문**
- 선언(`SYMMETRY_AXES`): `Sikhye_high (0,0,1)`, `Sauce_high (0,0,1)`, `Mugcup_high (0.106, 0.034, 0.994)`
- 판정 근거 = 모델점을 그 축으로 돌렸을 때의 자기정합 오차(지름 대비, 10° 간격 전 각도)
  - Sikhye 0.63 % · Sauce 1.54 % · Mugcup 2.22 % → 회전체로 인정
  - 대조군 choco 8.53 % → 불인정. **milk 1.93 %지만 제외** — 정사각 단면이라 연속이 아닌 90° 배수 대칭이고 면마다 인쇄가 다름
  - 인형류(Bear, Dinosaur)는 어떤 축으로도 자기정합 불가
- 자동 유도를 쓰지 않은 이유: 소각(10~20°) 자기정합이 절대 임계를 통과해 곰·공룡에 **가짜 대칭**을 만들어 결과가 악화됐다.
- 사용: `align_to_symmetry(prev_R, meas_R, name)` — 10° 간격 동치 회전군 중 이전 자세에 가장 가까운 것으로 측정을 돌린 뒤 융합.

**그림·표 제안:** 원통형 물체의 동치 자세 여러 개 + 가장 가까운 것 선택.

**발표 노트:** "자동보다 보수적인 수동 표가 나았다"는 결론은 방어가 필요할 수 있으니, 자기정합 오차 수치를 준비해 둘 것.

### P65. 존재확률 — 베르누이 필터
**핵심 한 줄:** 각 물체는 "존재할 확률 r"을 갖고, 검출되면 오르고 **볼 수 있었는데 못 봤을 때만** 내려간다.

**슬라이드 본문**
- 갱신식(`core/existence.py`)
  - 검출 수용: `r' = r·P_D / (r·P_D + (1−r)·c)`
  - 미검출(시야 안): `r' = r(1−P_D) / (1 − r·P_D)`
  - 미검출(시야 밖): `P_D = 0` → `r' = r` (**벌점 없음**)
- 파라미터: `P_D = 0.5`(실측 재현율 기반 캘리브레이션 — 0.6에서는 정상적인 검출기 실패를 과벌해 실물이 lost로 깜빡였다), 클러터 비 `c = 0.1`, 상한 `R_MAX = 0.99`(상한을 1로 두면 미검출이 아무 증거도 못 주는 고정점이 된다)
- `P_D` 계산(`core/visibility.py`): 랜드마크를 카메라 좌표로 옮겨 `z > 0` 확인 후 K로 재투영, 이미지 안쪽(경계 5 % 여유)에 들어오면 `P_D = P_D_base`, 아니면 0. 내부 파라미터가 없으면 광축 기준 35° 원뿔로 폴백.
- 품질 가중(옵션, 기본 off): 로그 우도비 형태로 일반화해 "낮은 품질 검출은 증거를 거의 주지 않게" 할 수 있다(`core/features.py`).
- 의미: **시야 밖에서 보낸 시간은 물체를 죽이지 않는다** — 넓은 공간을 도는 주행에서 필수.

**그림·표 제안:** 시간에 따른 r 곡선(검출 시 상승, 시야 안 미검출 시 하강, 시야 밖은 평평).

**발표 노트:** IPDA/베르누이 트랙 존재확률을 그대로 쓴 것 — 표준 기법을 6D 물체에 적용한 사례로 소개.

### P66. 상태 기계 — tentative에서 remembered까지
**핵심 한 줄:** 존재확률 r의 임계값이 상태를 정하고, 상태가 표시 방식과 삭제 정책을 정한다.

**슬라이드 본문**
- 상태: `tentative → active → lost → remembered`, 어디서든 `deleted`, 병합 시 `merged`
- 전이 규칙

| 조건 | 결과 |
|---|---|
| 미배정 검출 | `tentative` 생성, `r = R_INIT 0.7` |
| 관측 수 ≥ 2(`PROMOTE_HITS`) **및** r > 0.6(`R_PROMOTE`) | `active`로 승격 |
| `active`이고 r < 0.3(`R_LOST`) | `lost` |
| `tentative`이고 r < 0.05(`R_RETIRE`) | **삭제**(유령 FP) |
| `tentative`가 100 프레임(`TENTATIVE_MAX_AGE`) 초과 | 삭제(시야 밖 유령 안전장치) |
| `lost`이고 r < 0.05 | 관측 수 ≥ 5(`MIN_OBS_LONGTERM`)면 `remembered`, 아니면 삭제 |
| `lost`/`remembered`가 다시 검출됨 | `active`로 복귀(같은 id 유지) |
| depth 검사 FREE 3프레임 연속 | **삭제**(`depth_free_space`, remembered 포함) |

- `remembered`의 의미: 장기 기억. 미검출 벌점을 더 이상 받지 않고, 뷰어에는 흐리게 표시된다.
- 삭제된 인스턴스는 클래스의 살아 있는 목록에서 빠지지만 store에는 묘비로 남는다(id는 재사용 금지, INV-002).
- 모든 전이는 이유 문자열과 함께 기록(`transition_history`) → `summary.json`에서 사후 추적 가능.

**그림·표 제안:** 상태 전이도(원과 화살표, 화살표마다 조건).

**발표 노트:** "지운다"는 결정이 가장 위험하므로 조건을 두 겹(확률 + 관측 수, 또는 depth 3연속)으로 뒀다는 점을 말한다.

### P67. depth 일관성 검사 — "이제 없는 물체"를 지우는 법
**핵심 한 줄:** 존재확률만으로는 "안 보이는 것"과 "없어진 것"을 구분할 수 없다. depth 영상이 그 자리를 **꿰뚫어 보는지**로 직접 답한다.

**슬라이드 본문**
- 동기: 시야 안 미검출은 r을 천천히만 깎고, `remembered`는 아예 안 깎인다. SLAM 점프·루프 클로저 후 월드 앵커 지도에서는 **옛 사본이 영구히 남는다**.
- 판정(`core/depth_check.py`): 랜드마크 중심(CAD 원점 기준)을 현재 프레임에 투영하고 작은 패치의 측정 depth를 본다
  - 측정이 **더 멀다**(랜드마크 + 0.15 m 이상, 유효 화소의 80 % 이상) → **FREE** (꿰뚫어 봄 = 없어짐)
  - 측정이 **더 가깝다**(−0.10 m 이하, 50 % 이상) → **OCCLUDED** (앞에 뭔가 있음, 증거 없음 → 미검출 벌점도 면제)
  - 비슷하다 → **SURFACE** (무언가 있음)
  - 유효 화소 부족·화면 밖·거리 범위 밖(0.25~6.0 m) → **UNKNOWN**
- FREE 이중 확인: 3 cm 패치가 FREE여도, **15 cm 반경 창**의 95 % 이상이 멀 때만 FREE로 인정
  - 이유: 회전 오차 몇 도만 있어도 패치가 물체 옆의 4 m 뒤 벽을 보게 되어, ORB-SLAM3 f2000에서 **실제 물체 9개를 전부 삭제**한 사고가 있었다(2026-09-17)
- 속도 게이트: 카메라 속도 > 0.6 m/s 또는 회전 > 45°/s면 그 프레임은 검사 생략(자세 오차가 마진을 넘음)
- 입력 비용: 급전 프레임의 depth를 `[::8, ::8]`(640×480 → 80×60, 약 10 kB)로만 보관, 최대 600장(약 60 s)

**그림·표 제안:** 세 판정(FREE/OCCLUDED/SURFACE)의 단면도(카메라 광선과 측정 depth).

**발표 노트:** "안전장치의 안전장치"(창 확인·속도 게이트·3프레임 확인)가 어떻게 추가됐는지를 사고 사례와 함께 설명하면 설득력이 크다.

### P68. 메모리 출력과 화면 반영
**핵심 한 줄:** 화면에 그려지는 것은 원시 추정이 아니라 **메모리의 랜드마크**이며, 상태와 신뢰도가 함께 표시된다.

**슬라이드 본문**
- `ObjectMemory.landmarks()` → `{object_id, name, status, T_w_obj(평활 우선), confidence, n_obs, first/last_seen_ns, score}`
- `Hub.memory_rows()`가 표시용 행으로 변환
  - `active`, `lost`, `remembered`만 표시(`tentative`·`deleted` 제외)
  - 같은 클래스에 인스턴스가 2개 이상이면 `multi=True` → 라벨에 `이름#id` 표기
  - `age_s = (표시 시각 − last_seen)/1e9`, `source`는 20 ms 이내면 `sam6d`, 아니면 `slam_interp`
  - `T_cam_obj = (T_w_sam)⁻¹ · T_w_obj` — 영상 오버레이용
- `--no-memory` 옵션을 주면 메모리를 끄고 **원시 최신 추정**을 그대로 표시(비교·디버깅용)
- 상태 통계는 뷰어 카드에 실시간 표시: `활성 n · 놓침 n · 기억 n · 삭제 n`, 재구성 횟수와 소요 ms 포함

**그림·표 제안:** 뷰어의 객체 표 스크린샷(상태·신뢰도·관측 수 열 강조).

**발표 노트:** "메모리를 껐다 켤 수 있다"는 점이 실험 설계상 중요 — 메모리의 기여를 분리 측정할 수 있다.

### P70. 브라우저 뷰어 (`pc/web/index.html`)
**핵심 한 줄:** 레인마다 영상 패널과 상태 카드가 생기고, 3D 지도는 **하나**에 모든 레인을 색으로 겹쳐 그린다.

**슬라이드 본문**
- 3D 지도(three.js)
  - 좌표 변환: 카메라 SLAM 월드는 광학 좌표(x 오른쪽, y 아래, z 전방)라 X축 180° 회전해 "위"를 위로; 라이다 기준일 때는 z-up 그대로
  - 그리는 것: 월드 3축 + 라벨, 카트 이동 평면에 맞춘 그리드(궤적의 최소 주성분으로 법선 계산), 레인별 궤적 선, SLAM/SAM 카메라 프러스텀 2개, 객체 박스(테두리 = 레인 색, 채움 = 물체 색), 관측 이력 점군, 물체 라벨
  - OrbitControls로 회전·확대·이동, 레인별 표시 토글
- 영상 패널: 레인마다 JPEG + 레인 태그(색), 상태 배지
- 상태 카드: SLAM 카드(상태, 포즈 수, 추적 ms, 지연, 키프레임 수·갱신·최대 보정, 정렬 정보, 메모리 상태별 개수) + SAM-6D 카드(처리 프레임, 마지막 결과, 결과 나이, 처리 ms, 화면 지연, 시계 기준)
- 객체 표: 이름(한글 병기)·레인·상태·신뢰도·관측 수·나이·소스·앵커 키프레임·좌표
- 견고성: WebGL 컨텍스트 실패 시 지도 패널만 안내 문구로 대체하고 영상·표는 계속 동작; 렌더 루프는 `requestAnimationFrame` 안에서 시작(Firefox 소프트웨어 WebGL에서 첫 셰이더 컴파일이 스크립트 시간 초과를 내 모듈이 죽던 문제)

**그림·표 제안:** 뷰어 전체 스크린샷에 번호를 달아 각 영역 설명.

**발표 노트:** 시연이 가능하면 이 장에서 실제 화면을 띄우는 것이 가장 효과적이다.

### P71. 레인 정렬 — 두 SLAM을 한 지도에 겹치기
**핵심 한 줄:** 서로 다른 월드를 가진 두 SLAM을 비교하려면 강체 정렬이 필요하고, 그 정렬이 **퇴화하지 않도록** 조건을 걸어야 한다.

**슬라이드 본문**
- 기준 레인: 첫 라이다 레인(z-up·절대 스케일), 없으면 레인 0
- 정렬 계산(`update_alignment`, 0.5 s마다)
  1. t0부터 현재까지 0.2 s 간격으로 두 레인의 **SAM 카메라 위치**를 쌍으로 모은다(같은 SAM 프레임 시각 → 공정 비교)
  2. Kabsch(SVD)로 강체 변환 `T_ref_lane` + RMSE 계산
  3. 조건을 만족하면 채택: 쌍 ≥ 25, 겹침 ≥ 4 s, **경로 길이 ≥ 1 m**, **공간 퍼짐(2번째 고유값 √) ≥ 0.15 m**
  4. 겹침 ≥ 15 s이고 경로 ≥ 2 m이면 **동결**(이후 갱신 안 함) → 그 뒤의 차이는 두 SLAM의 실제 차이로 보인다
  5. 조건 미달이면 현재 자세 한 점으로만 맞춘다(`mode: single`)
- 왜 경로·퍼짐 조건이 필요한가: 260910은 **처음 35초 동안 카트가 정지**해 있어 76쌍이 사실상 한 점이었고, RMSE 0.04 cm로 "완벽해 보이는" 퇴화 정렬이 나왔다. 회전이 임의로 정해져 이후 비교 수치(3.9–11.3 cm)가 의미를 잃었다.
- 진단 정보 `align_info`: `pairs`, `rmse_cm`, `span_s`, `path_m`, `frozen`, `mode` → 뷰어 카드와 summary에 노출

**그림·표 제안:** 퇴화 사례(한 점) vs 정상 사례(궤적 전체) 두 그림.

**발표 노트:** "RMSE가 작다고 정렬이 좋은 것이 아니다"라는 교훈. 지표의 함정 사례로 쓸 수 있다.

### P72. 런처 — 한 번에 하나씩 (`pc/launcher.py`)
**핵심 한 줄:** 브라우저에서 데이터셋 탭과 백엔드 버튼을 누르면, 런처가 기존 허브를 정리하고 새 허브를 띄운다.

**슬라이드 본문**
- 구조: 브라우저 ── 8765 ── `launcher.py` ──프록시──► `hub.py`(127.0.0.1:8766)
- API: `GET /api/state`(현재 데이터셋·백엔드·실행 여부·선택지), `POST /api/run?dataset=D&backend=B&features=…&thdepth=…`, `POST /api/stop`
- 자식 허브는 **항상 1개**: 다른 버튼을 누르면 현재 허브에 SIGINT(요약 저장) → 종료 확인 → 새 허브 시작. `run_one.sh`도 다른 hub.py가 살아 있으면 시작을 거부(공유메모리·포트가 단일 사용자 자원).
- 페이지는 허브의 `index.html`을 **디스크 수정 없이** 그대로 받아 응답에 모드 바(`launcher-bar` + `web/launcher.js`)를 끼워 넣는다.
- 모드 바 구성: 데이터셋 탭(실행 중 표시) → 백엔드 카드(ORB: f2000/f3000/f4000 · ThDepth 40/70, LiDAR: KISS-ICP / hdl_graph_slam) → 멈춤·결과 디렉터리 링크
- 실행이 바뀌면 페이지가 스스로 새로고침해 이전 레인이 남지 않는다.
- CLI 대응: `bash objpose/pc/launcherctl.sh status|start [<dataset>] <backend>|stop|restart`

**그림·표 제안:** 런처 모드 바 스크린샷 + API 흐름 화살표.

**발표 노트:** "실험을 많이 돌려야 하는 연구"에서 UI가 실험 속도를 결정했다는 점 — 백엔드 전환이 25초로 줄었다.

### P73. 실행 스크립트 — 녹화본 재생 (`run_one.sh`)

- `run_one.sh live …` → `run_live.sh`로 전달

**그림·표 제안:** 인자 → hub.py 옵션 매핑 표(예시 1개 전개).

**발표 노트:** "실험 조건이 스크립트에 문서화돼 있다"는 점 — 재현 시 이 파일만 보면 된다.

### P74. 실행 스크립트 — 라이브 센서 (`run_live.sh`)
**핵심 한 줄:** 라이브 모드는 카메라 드라이버 기동·시계 측정·원격 스트리머 점검까지 스크립트가 책임진다.

**슬라이드 본문**
- 단계
  1. **노트북 주소 탐색**: 케이블 프로파일에 따라 192.168.2.1 또는 192.168.240.1 — 응답하는 쪽을 선택
  2. **원격 파일 점검**: 백엔드별 필요한 스크립트·워크스페이스가 노트북에 있는지 ssh로 확인
  3. **RealSense 드라이버 확보**: 토픽 목록이 아니라 **실제 프레임이 오는지**로 판단(죽은 드라이버가 토픽만 광고하는 경우가 있음). 없으면 `ros2 launch realsense2_camera`(640×480×30, align_depth, enable_sync)로 기동. 첫 시도는 `initial_reset:=false`(리셋 직후 스트림 시작이 실패한 사례), 실패 시 리셋 1회 재시도. 드라이버는 `setsid`로 분리해 **백엔드 전환에도 살아남는다**(전환 25 s vs 45 s)

- 정리: `bash objpose/stop_live.sh`가 드라이버까지 모두 종료

**그림·표 제안:** 5단계 체크리스트 형태.

**발표 노트:** 라이브 시연 전에 이 스크립트가 무엇을 자동으로 확인하는지 말해 두면, 시연 중 문제가 생겨도 설명이 된다.

**핵심 한 줄:** 시스템을 실제로 돌리면서 만난 함정들 — 대부분 성능이 아니라 **환경·수명주기** 문제였다.

**슬라이드 본문**

| 문제 | 원인 | 대응 |
|---|---|---|
| ssh가 "OpenSSL version mismatch"로 실패 | conda의 `LD_LIBRARY_PATH`가 시스템 OpenSSH에 conda libcrypto를 물림 | ssh 실행 시 환경변수에서 제거 |
| hdl 재생이 1 스캔/s로 붕괴 | rclpy MultiThreadedExecutor가 GIL 점유 | SingleThreadedExecutor 고정 |
| 시작 직후 91 스캔 유실 | DDS·fast_gicp 초기화 ~10 s | hello 전 예열(`--warmup-s 20`) |
| 결과 채널이 낡은 세그먼트에 부착 | 이전 실행의 공유메모리 잔존 | `READY` 갱신 후 1 s 경과 조건 |
| 브라우저에서 지도만 빈 화면 | CDN 접근 불가 / WebGL 컨텍스트 소실 | three.js 로컬 서빙 + 실패 시 안내 표시 |
| 라이브에서 가짜 +0.5 s 지연 | t0에 start 오프셋을 더함 | 라이브에서는 오프셋 제거 |
| 정지 시작 구간에서 정렬 퇴화 | Kabsch 입력이 사실상 한 점 | 경로 길이·퍼짐 조건 추가 |
| 카메라 죽은 채 토픽만 남음 | 드라이버 UVC 스트림 정지 | 프레임 수신으로 생존 판정 + 리셋 재시도 |

**그림·표 제안:** 위 표. 왼쪽에 아이콘(네트워크/ROS/브라우저/시계).

**발표 노트:** 연구 시스템에서 "실제로 시간을 잡아먹는 것"이 무엇인지 보여 주는 장. 솔직하게 넣으면 신뢰를 준다.

# 8부. 실험 결과 (P76–P84)

### P76. 평가 지표의 정의
**핵심 한 줄:** 네 가지 지표로 평가한다 — 흩어짐, 보간 오차, 루프 전후 일치, 레인 간 차이. 모두 **정지 물체**라는 사실을 이용한다.

**슬라이드 본문**
- **정지 객체 흩어짐(spread)**: 한 물체의 모든 관측을 최종 키프레임 자세로 환산한 뒤, 중앙 위치로부터의 거리 분포(중앙값·p90). *지도+RT+시계의 종합 일관성*
- **보간 예측 오차**: 시각 t의 추정으로 Δt 뒤를 예측하고 실제 추정과 비교. 구간별(≤3 s / 3–10 s / 10–60 s). *보간 가정의 유효 범위*
- **루프 전후 같은 객체 위치 차**: 루프 클로저 전에 관측된 위치와 후에 관측된 위치의 거리. *키프레임 앵커링의 효과*
- **레인 간 객체 위치 차 / 궤적 RMSE**: 두 SLAM을 강체 정렬한 뒤의 차이. *SLAM 품질 비교*
- 부가 지표: 포즈 OK/버림, 추적 시간, 도착 지연, 키프레임 수·보정량, SAM-6D 처리 프레임·결과 나이, 메모리 상태별 개수
- 모든 지표는 `summary.json`과 `pc/compare_runs.py`로 자동 산출 — 수작업 없음

**그림·표 제안:** 각 지표를 그림 하나씩(4칸).

**발표 노트:** "정지 물체를 기준으로 삼는다"는 가정이 모든 평가의 토대임을 명시. 움직이는 물체 평가는 향후 과제.

### P77. 결과 1 — 시계·RT 교체와 키프레임 앵커링

- KISS-ICP vs hdl_graph_slam: 짧은 세션에서는 KISS-ICP가 더 매끄러움(흩어짐 1.06 vs 1.56 cm). hdl의 이점(루프 보정·키프레임 재배치)은 긴 주행에서.

**그림·표 제안:** 두 궤적 탑뷰 겹침(정렬 후) + 같은 물체의 두 위치 표시.

**발표 노트:** "라이다를 기준(정답 대용)으로 쓸 수 있는 근거"가 이 표. 동시에 "스케일 3.8 %"는 카메라 SLAM의 알려진 한계로 논의거리.

### P81. 결과 5 — 루프 클로저 후 객체 분열 사건과 수정
**핵심 한 줄:** 물체가 둘로 쪼개지는 현상의 원인은 허브가 아니라 **SLAM 지도 자체의 갈라짐**이었고, 두 가지 수정(F1·F2)으로 실전에서 해소했다.

**슬라이드 본문**
- 현상: 260910 실행에서 같은 물체가 메모리에 2개 인스턴스로 남음
- 원인 규명: 로그만으로 허브 파이프라인을 mm 단위로 재현 → ORB-SLAM3의 두 번째 루프(85.5 s)가 드리프트를 남긴 채 닫혀 **지도가 0.58 m + 17.5°로 갈라진 것**을 확인. 허브 버그 아님.
- **F1**(`pc/fusion.py`): kf_update 목록의 최대 id보다 큰 키프레임은 컬링이 아니라 "메시지 이후 생성"으로 판정 → 거짓 컬링·잘못된 재앵커 제거(결과 무회귀)
- **F2**: 연관 게이트 0.15 → 0.30 m, 융합 가중치 하한 0.05 도입
- 검증
  - 오프라인 재생: 정상 ORB 실행 4개 + 라이다 2개 모두 **8 = 8종, 클래스당 1개**(이전에는 머그컵 2개). 지도가 갈라진 실행만 여전히 2개씩
  - 실기 재실행(Mac f3000): 루프 2회(1.42 m, 2.52 m)에도 8 = 8종, 라이다 대비 객체 오차 중앙 4.8 cm
- 기각한 대안: **루프 전 관측 가중치** `w = 1/(1+(d/d0)²)` (d = 앵커 키프레임 누적 보정)
  - 구현했으나 기본 off. 오프라인 4개 실행에서 어떤 d0에서도 라이다 대비 오차 악화(4.3–4.8 → 4.7–5.9 cm)
  - 이유: 최종 지도에서도 ORB 지도가 국소적으로 5–9 cm 뒤틀려 있어 "루프 전 = 나쁨"이 성립하지 않는다

**그림·표 제안:** 갈라진 지도 도식(같은 물체 두 곳) + F1/F2 적용 후 하나로 합쳐진 그림.

**발표 노트:** "증상은 하류에서, 원인은 상류에서"의 전형. 로그만으로 재현할 수 있었던 것이 결정적이었다는 점을 강조.

### P82. 결과 6 — 객체 메모리의 최종 상태
**핵심 한 줄:** 여러 실행에서 일관되게 "8개 인스턴스 = 8종", 각 인스턴스가 그 물체 관측 중앙값과 0.1–1.3 cm 이내.

**슬라이드 본문**
- v5 결과(260826): 남은 인스턴스 **8개 = 8종**, 각 인스턴스 위치가 관측 중앙값과 **0.1–1.3 cm**
- 1.84 m 떨어진 **가짜 `milk` 관측 4건은 전부 삭제** — 존재확률 필터가 유령을 정리
- 시야 밖으로 나간 물체는 `remembered`로 남아 지도에만 흐리게 표시
- 재구성 비용: 308 프레임 75 ms (kf_update마다)
- 다른 실행들: hdl 단독 실행에서 활성 4 · 놓침 4 · 삭제 1, 두 레인 동시 실행에서 ORB 활성 7 / hdl 활성 6·잃음 2·미배치 1 — 레인 품질이 메모리 상태에 그대로 반영된다
- depth 검사(2026-09-17 도입) 이후: 실제 물체 오삭제를 막기 위해 창 확인·속도 게이트를 추가한 상태로 운용 중

**그림·표 제안:** 최종 지도 상단뷰 + 8개 박스 + 관측 산포.

**발표 노트:** "8 = 8"이라는 단순한 수치가 사실은 연관·존재확률·융합·재구성이 모두 맞아야 나오는 결과임을 설명.

# 9부. 한계·향후 과제·부록 (P85–P92)

### P85. 알려진 한계 (1) — 방법론
**핵심 한 줄:** 가정 네 가지가 깨지면 이 시스템의 정확도 보장이 사라진다.

**슬라이드 본문**
1. **정지 물체 가정**: 평가 지표(흩어짐)와 융합(러닝 평균)이 모두 물체가 움직이지 않는다는 전제. 움직이는 물체는 현재 다룰 수 없다.
2. **평면 주행 가정**: RT 추정 1단계(궤적 평면 = 중력)와 2단계(SE(2) hand-eye)가 카트의 평면 운동에 의존. 계단·경사에서는 재설계 필요.
3. **리그 고정 가정**: X가 고정이라고 본다. 실제로 260915에서 리그가 바뀌어 5 cm 오차가 났고, 사람이 알아채 재추정했다 — **자동 감시 장치가 없다**.
4. **프레임 독립 인식**: SAM-6D가 시간 정보를 쓰지 않아 자세가 이봉으로 튄다. 메모리가 사후 수습할 뿐, 인식 자체가 개선되지는 않는다.

**그림·표 제안:** 네 가정과 각각이 깨지는 상황 그림.

**발표 노트:** 피드백을 받고 싶은 지점을 여기서 명시적으로 열거하면 논의가 생산적이다.

### P86. 알려진 한계 (2) — 구현·규모
**핵심 한 줄:** 현재 설계는 "수 분 주행, 수백 프레임" 규모에 맞춰져 있다.

**슬라이드 본문**
- **메모리 전체 재구성**: kf_update마다 전체 프레임을 다시 재생한다(308 프레임 75 ms). 프레임이 수만 개가 되면 선형 비용이 문제 — 증분 보정 또는 키프레임별 부분 재구성이 필요.
- **GPU 1장만 사용**: 4090 4장 중 cuda:0만. PEM이 전체 시간의 57 %이므로 병렬화 여지가 크다.
- **단일 허브 제약**: 공유메모리 이름과 포즈 포트가 고정이라 한 기계에서 하나만 실행 가능. 동시 실험이 안 된다.
- **표시 지연 0.3 s vs 결과 나이 0.8 s**: 화면의 박스는 거의 항상 보간값 — 빠른 움직임에서는 오차가 보인다.
- **라이브 모드의 시계**: UDP 왕복의 대칭 경로 가정에 의존. 무선·혼잡 구간에서는 재검토 필요.
- **다중 인스턴스 검증 부족**: 같은 클래스가 여러 개인 실제 데이터로 충분히 시험하지 못했다(현재는 클래스당 1개가 정답인 세션 위주).

**그림·표 제안:** 규모 축(프레임 수)에 따른 비용 곡선 예상도.

**발표 노트:** "지금 구조로 얼마까지 가는가"를 미리 답해 두면, 확장 계획 질문에 대응이 쉽다.

### P87. 향후 과제
**핵심 한 줄:** 남은 오차의 주범이 지도 뒤틀림이므로, 다음 작업은 SLAM 쪽 품질 관리와 융합 쪽 이상 탐지에 집중한다.

**슬라이드 본문**
- **F3 — 지도 갈라짐 탐지**: kf_update 사이의 키프레임 이동 패턴으로 "잘못 닫힌 루프"를 자동 감지하고, 그 구간의 관측을 격리
- **F4 — SLAM 측 루프 검증**: 루프 클로저 후보를 기하 검증으로 한 번 더 거르기(현재는 ORB-SLAM3 기본값)
- **ThDepth 스윕 확장**: 40 → 70에서 흩어짐 −15 %(실행 간 분산 이내)였으므로, 더 넓은 범위와 데이터셋으로 재확인
- **다중 GPU PEM**: 물체 배치를 나눠 처리량 개선(현재 57 %가 PEM)
- **인식 쪽 시간 일관성**: 이전 프레임의 자세를 사전 정보로 쓰는 구조(단, `pem_schedule` 실험처럼 낡은 자세를 그대로 물려주면 안 됨 — 카메라 이동 보정 필요)
- **움직이는 물체 지원**: 상태 기계에 "이동됨" 상태 추가, 융합을 평균에서 필터(칼만/IMM)로 교체
- **리그 자동 감시**: 실행 중 두 카메라 궤적의 상대 움직임 잔차를 모니터링해 X 변화를 자동 경보
- **장시간 주행 평가**: hdl_graph_slam의 이점이 드러나는 조건(수십 분, 반복 방문)에서 재비교

**그림·표 제안:** 과제를 "SLAM 품질 / 융합 견고성 / 처리량 / 확장" 4사분면에 배치.

**발표 노트:** 교수님께 우선순위 의견을 구하기 좋은 장. 각 항목에 예상 소요를 붙여 두면 더 좋다.

### P88. 논문화 관점에서의 기여 정리
**핵심 한 줄:** 개별 알고리즘이 아니라 "실시간 객체 지도를 위한 정합·앵커링·메모리 설계"가 기여다.

**슬라이드 본문**
1. **분해형 리그 외부 파라미터 추정**: 중력(궤적 평면) + 평면 hand-eye(상대 움직임) + depth 바닥면으로 X와 시간 오프셋 τ를 동시 추정. 두 대안(AX=ZB, 공유지도 재측위) 대비 객체 일관성 0.85 cm vs 1.82–2.46 cm.
2. **키프레임 앵커링 융합**: 물체를 월드가 아닌 키프레임 기준으로 저장해 루프 클로저 보정을 전 이력에 전파. 루프 전후 위치 차 5.4 → 0.8 cm.
3. **회전 모드 다수결 융합**: 프레임 독립 6D 추정의 다봉 분포를 평균이 아닌 모드로 종합. 지도 배회 −51 %, 비대칭 물체에도 유효.
4. **depth 기반 소멸 판정**: 미검출과 부재를 구분하는 free-space 증거(창 확인·속도 게이트 포함).
5. **백엔드 교체 가능한 평가 틀**: 같은 검출을 여러 SLAM에 동시에 먹여 *하위 작업 기준*으로 SLAM을 비교(궤적 ATE가 놓치는 차이를 드러냄).

**그림·표 제안:** 5개 기여를 파이프라인 그림 위의 위치와 함께 표시.

**발표 노트:** 이 장이 사실상 논문 초록의 뼈대다. 교수님께 "어느 것을 주 기여로 세울지" 의견을 구하는 것이 이 발표의 목적 중 하나.

### IMG-01. 입력 이미지 전체 지도 — 어떤 이미지가 몇 장, 어디로 가는가
**핵심 한 줄:** 이 시스템에 들어오는 이미지는 두 카메라에서 나오며, 서로 **다른 기계에서 다른 목적**으로 소비된다. 한 장도 섞이지 않는다.

**슬라이드 본문**
- **SLAM 카메라 이미지**(color + depth) → SLAM 호스트에서만 소비 → 결과는 이미지가 아니라 **4×4 자세 행렬 한 개**로 축약되어 네트워크로 전달. 이미지 자체는 네트워크를 건너지 않는다.
- **SAM 카메라 이미지**(color + depth) → 워크스테이션에서만 소비 → 세 갈래로 분기
  1. **추론용**: RGB + 정렬 depth + K → 공유메모리 → SAM-6D (10 Hz로 급전)
  2. **표시용**: color만 → 프레임 버퍼(최근 120장) → 오버레이 → JPEG → 브라우저 (30 Hz 적재, 15 Hz 송출)
  3. **검증용**: depth를 1/64로 축소한 사본 → 객체 메모리의 depth 일관성 검사
- 규모 감각(260826 전체 실행 기준): SAM 카메라 프레임 약 7,000장 중 **표시 7,000장 / 급전 2,429장 / 실제 추론 691장**. 급전과 추론의 차이는 공유메모리가 최신 한 장만 유지하기 때문(의도된 드롭).

**그림·표 제안:** 두 카메라에서 나온 화살표가 각각 다른 기계로 가고, SAM 쪽에서 3갈래로 분기하는 그림. 각 화살표에 장수/주기 표기.

**발표 노트:** "이미지가 네트워크를 건너지 않는다"는 점이 이 설계의 핵심 — 640×480 RGB-D를 30 Hz로 보내면 약 370 Mbps라 LAN이 버티지 못하고, 자세(수백 바이트)로 축약하면 무시할 수 있는 수준이 된다.

### IMG-04. `rgbd_timestamp_associations.json` — "프레임"의 정의
**핵심 한 줄:** 이 파일이 color 한 장과 depth 한 장을 묶어 **프레임 인덱스**를 정의하고, 이 인덱스가 시스템 전체의 공용 좌표가 된다.

**슬라이드 본문**
- 구조
```json
{"associations": [
   {"color_message_id": 123, "depth_message_id": 124,
    "associated_host_epoch_timestamp_ns": 1756...},
   ...]}
```
- 리더가 만드는 배열 3개(`RsSession.__init__`)
  - `color_ids[i]`, `depth_ids[i]` — i번째 프레임의 메시지 id
  - `t_ns[i]` — i번째 프레임의 시각(기본은 연관 호스트 시각 + 오프셋, 실제로는 **프레임 시계로 교체**)
- 이 인덱스가 쓰이는 곳
  - SLAM 스트리머의 `frame_idx` 필드 → 허브가 시각을 다시 매길 때 쓰는 키(`Lane.on_msg`)
  - 재생 루프의 위치(i), 건너뛴 프레임 수 계산
  - 프레임 시계 테이블(`clock.py`)의 행 번호
- **주의점**: 연관 스탬프(`associated_host_epoch_timestamp_ns`)는 인덱스 기반 정책으로 붙은 값이라, SLAM 세션처럼 컬러가 드롭되면 실제 촬영 시각에서 −2.1 ~ +3.8 s 표류한다. 그래서 **짝짓기 정보로만 쓰고 시각으로는 쓰지 않는다.**

**그림·표 제안:** color 메시지 열과 depth 메시지 열을 선으로 잇는 그림 + 드롭 구간에서 스탬프가 밀리는 모습.

**발표 노트:** "프레임이 무엇인가"를 파일 하나가 정의한다는 점, 그리고 그 파일의 시각 필드를 신뢰하지 않기로 한 결정이 1부의 핵심 사건이다.

### IMG-05. 컬러 이미지 메시지 바이트 해부 (`_image()` / `parse_image()`)
**핵심 한 줄:** CDR 바이트열을 직접 파싱해 **복사 없이** numpy 배열 뷰로 만든다.

**슬라이드 본문**
- 원본 세션용 파서(`rs_session._image`) 진행 순서
  1. offset 4 — CDR 인캡슐레이션 헤더 건너뜀
  2. +8 — 헤더 스탬프(sec, nsec)
  3. frame_id 문자열: 길이 4바이트 + 내용, 이후 **4바이트 정렬**
  4. `height`, `width` (uint32 ×2)
  5. `encoding` 문자열(길이 + 내용 + 널), 4바이트 정렬
  6. `is_bigendian` 1바이트, 정렬
  7. `step`(행 바이트 수) 4바이트
  8. `data` 길이 4바이트 + 실제 화소 바이트
- numpy 변환
  - 컬러: `np.frombuffer(data, np.uint8).reshape(h, w, 3)` (변환본 파서는 `step`을 고려해 `reshape(h, step)[:, :w*3]`)
  - `rgb8`이면 `[:, :, ::-1]`로 BGR화, `bgr8`이면 그대로, 그 외 인코딩은 **예외로 중단**(조용히 잘못 읽는 것을 막음)
  - depth: `np.frombuffer(..., np.uint16).reshape(h, w)`, 크기·인코딩이 예상과 다르면 예외
- 성능 설계: 헤더만 필요한 경우(스탬프 인덱싱) `substr(data, 1, 64)`로 **앞 64바이트만** 읽는다 — 13 GB bag 전체를 읽지 않기 위한 장치(`bag_io.Bag.stamps`).

**그림·표 제안:** 바이트 레이아웃 막대 그림(필드별 색과 오프셋).

**발표 노트:** 이 수준까지 직접 파싱한 이유는 ROS 의존 제거와 속도 둘 다다. 동시에 "예상 밖 인코딩은 즉시 실패"라는 방어가 들어가 있다.

### IMG-06. depth 이미지와 depth_units
**핵심 한 줄:** depth는 uint16 정수이고, 실제 거리로 바꾸려면 세션에 기록된 `Depth_Units`를 곱해야 한다.

**슬라이드 본문**
- 저장 형식: `16UC1`(또는 `mono16`), 화소당 2바이트, 0 = 무효(측정 실패)
- 물리값: `Z[m] = depth_raw × depth_units`, `depth_units`는 `/device_0/sensor_0/option/Depth_Units/value`에서 읽는다(보통 0.001).
- 정렬 후 출력은 다시 **uint16 mm**로 되돌린다(`round(Zc × 1000)`) — 하위 단계(SAM-6D, depth 검사)가 모두 mm uint16을 기대하기 때문.
- 유효성 처리
  - 정렬 단계: `Z > 0`인 화소만 변환, 변환 후 `Zc > 0`인 것만 기록
  - PEM 입력 단계: 마스크 ∩ (depth > 0) 화소가 32개 이하면 그 검출은 버림
  - depth 검사 단계: 0.25 m ~ 6.0 m 범위 밖은 `UNKNOWN`(D455f의 원거리 depth는 free space 판정에 쓸 만큼 정확하지 않다)
- 구멍(hole) 문제: 무효 화소가 패치의 50 % 이상이면 depth 검사는 판단을 포기한다(`min_valid_fraction`).

**그림·표 제안:** depth 원본(회색조) + 무효 화소 마스크(검정) + 거리 컬러맵 3장.

**발표 노트:** depth가 "이미지처럼 생겼지만 물리량"이라는 점, 그리고 0의 의미가 "가깝다"가 아니라 "모른다"라는 점을 분명히 하면 뒤의 depth 검사 설명이 쉬워진다.

### IMG-07. depth → color 정렬의 수학 (`RsSession.align`)
**핵심 한 줄:** depth 센서 격자의 모든 화소를 3D로 펴서 컬러 카메라로 다시 투영한다 — 다섯 단계, 전부 벡터 연산.

**슬라이드 본문**
1. **역투영(depth 내부 파라미터)** — 미리 계산해 둔 격자 사용
   `x_n = (u − ppx_d)/fx_d`, `y_n = (v − ppy_d)/fy_d`, `Z = depth_raw × depth_units`
   → `X = x_n·Z`, `Y = y_n·Z`
2. **강체 변환(depth → color 외부 파라미터)**
   `[Xc, Yc, Zc]ᵀ = R_d2c·[X, Y, Z]ᵀ + t_d2c` (R, t는 bag의 `tf/ref_0`에서)
3. **정규화 + 왜곡(컬러 왜곡 계수)**
   `x = Xc/Zc`, `y = Yc/Zc`, `r² = x²+y²`
   `f = 1 + k1r² + k2r⁴ + k3r⁶`
   `x_d = x·f + 2p1xy + p2(r²+2x²)`, `y_d = y·f + 2p2xy + p1(r²+2y²)`
4. **컬러 화소 좌표로 투영 + 반올림**
   `u' = round(fx_c·x_d + ppx_c)`, `v' = round(fy_c·y_d + ppy_c)`
5. **기록**: 화면 안(0 ≤ u' < W, 0 ≤ v' < H)이고 유효한 것만 `out[v'·W + u'] = round(Zc×1000)`
- 결과: 컬러 화소 격자 위의 uint16 mm depth. **컬러 이미지와 화소 대 화소로 대응**한다.

**그림·표 제안:** depth 격자 → 3D 점군 → color 격자 재투영의 3단 그림, 각 단계에 쓰이는 파라미터 표시.

**발표 노트:** 여기서 쓰는 파라미터가 총 3묶음(depth 내부, depth→color 외부, color 내부+왜곡)이고 전부 bag 안에 있다는 점을 짚으면, 별도 캘리브레이션이 필요 없는 이유가 설명된다.

### IMG-08. 정렬 구현의 세부와 검증
**핵심 한 줄:** 여러 depth 화소가 같은 컬러 화소로 떨어질 때 **가까운 값이 이기도록** 정렬 순서를 정했고, 결과가 기존 변환기와 비트 단위로 같음을 확인했다.

**슬라이드 본문**
- **충돌 처리**: 재투영 후 여러 화소가 같은 `(u', v')`에 모일 수 있다(경사면·물체 경계).
  - 구현: 거리 내림차순으로 정렬해 기록 → 마지막에 쓰인 값(= 가장 가까운 값)이 남는다
  - `order = np.argsort(-zmm)` 후 `out[flat[order]] = zmm[order]`
  - 의미: 물체 뒤 배경이 물체 앞으로 새는 것을 막는다(occlusion을 올바르게 처리)
- **비어 있는 화소**: 컬러 격자에서 대응되는 depth가 없으면 0(무효). 보간이나 구멍 메우기를 **하지 않는다** — 없는 측정을 지어내면 PEM과 depth 검사가 오판하기 때문.
- **성능**: 화소별 루프 없이 numpy 전 배열 연산. `_xnd`, `_ynd`(정규화 격자)는 생성자에서 한 번만 만든다.
- **검증 3중**
  1. 이 함수는 `sam6d_realtime/data/convert_recording.py`의 `align()`을 **그대로 이식**한 것 — SAM-6D 학습·검증에 쓰인 변환본을 만든 바로 그 코드
  2. 원본 세션을 이 함수로 정렬한 결과가 변환본 bag과 **비트 단위 동일**함을 확인
  3. Mac/Linux 스트리머(`raw_session.h`의 `Aligner::align`)도 같은 함수를 C++로 이식 — 두 호스트가 동일 입력을 본다
- 변환본 bag은 이미 정렬돼 있으므로 `align()`이 항등 함수(`ConvSession.align`, `depth_to_color`의 `depth_aligned` 분기).

**그림·표 제안:** 충돌 처리 그림(두 depth 화소 → 한 컬러 화소, 가까운 쪽 채택) + "비트 동일" 검증 도식.

**발표 노트:** "같은 전처리를 세 구현이 공유한다"는 점이 실험 신뢰성의 기반. 전처리가 호스트마다 다르면 SLAM 비교가 무의미해진다.

### IMG-09. 변환본 bag의 이미지 — 짝짓기와 인덱스 캐시 (`conv_session.py`)
**핵심 한 줄:** 변환본은 표준 ROS 토픽이라 정렬이 필요 없지만, **color와 depth를 헤더 스탬프로 정확히 짝지어야** 한다.

**슬라이드 본문**
- 토픽: `/camera/camera/color/image_raw`(bgr8), `/camera/camera/aligned_depth_to_color/image_raw`(16UC1), `/camera/camera/color/camera_info`
- 짝짓기 규칙: color 스탬프와 **완전히 같은** depth 스탬프만 인정. 짝이 없는 color 프레임은 버리고 개수를 로그에 남긴다.
  - 근사 매칭을 쓰지 않는 이유: 변환기가 이미 동기화해 저장했으므로, 불일치는 데이터 문제이지 허용 오차 문제가 아니다.
- `camera_info` 파싱: CDR 정렬 규칙(페이로드 기준 8바이트 정렬)을 지켜 `D`(왜곡 5개)와 `K`(3×3)를 읽는다.
- **인덱스 캐시**: 모든 이미지 메시지의 헤더를 훑어야 스탬프 목록이 나오는데, 로컬 디스크에서 1초인 작업이 NFS에서는 13 GB bag 기준 **약 3분**(4 KB 페이지마다 1 MB 미리읽기). 그래서 `color_ids/depth_ids/t_raw/W/H/K/D`를 `.npz`로 캐시하고, bag 파일의 **크기와 mtime**을 키로 유효성을 검사한다.
- 시각: `t_ns = 헤더 스탬프 + offset_ns(τ)`. 정렬 후 시각 오름차순으로 재배열.

**그림·표 제안:** 두 토픽의 스탬프 열을 잇는 그림 + 캐시 히트/미스 흐름.

**발표 노트:** NFS 3분 문제는 "실험을 돌리는 속도"에 직접 영향을 준 부분이라, 시스템 논문이라면 언급 가치가 있다.

### IMG-10. 라이브 이미지 — ROS 토픽 동기화 (`live_session.py`)
**핵심 한 줄:** 라이브에서는 타임라인이 없으므로 "가장 최신 한 쌍"만 붙잡고, 나머지는 버린다.

**슬라이드 본문**
- 구독: `color/image_raw`, `aligned_depth_to_color/image_raw`, `color/camera_info` (QoS: RELIABLE, KEEP_LAST, depth 10)
- 짝짓기: `message_filters.ApproximateTimeSynchronizer(queue_size=10, slop=0.02 s)` — sam6d_receiver_node와 동일한 방식
- 콜백에서 하는 일
  - 인코딩 처리: `bgr8`/`rgb8`은 `step`을 고려해 reshape 후 필요 시 채널 뒤집기, `16uc1`/`mono16`은 `<u2`로 뷰
  - 시각: `color.header.stamp + offset_ns` (드라이버가 `global_time_enabled`라 호스트 시계)

- 인터페이스 호환: `K, kc, W, H, dir, t_ns, __len__, latest(), align()` — 허브는 녹화본과 동일하게 다룬다

**그림·표 제안:** 드라이버 → 동기화기 → 최신 한 쌍 슬롯 → 허브 그림(버려지는 프레임 표시).

**발표 노트:** "큐를 쌓지 않는다"가 실시간 시스템의 일관된 원칙이며, 여기서도 같은 원칙이 적용된다.

### IMG-11. 이미지가 SAM-6D로 가는 경로
**핵심 한 줄:** 프레임 한 장은 약 1.5 MB이고, 공유메모리에 **덮어쓰기 방식**으로 전달된다 — 직렬화도, 큐도, 복사 체인도 없다.

**슬라이드 본문**
- 급전 시점: 재생 루프에서 `now ≥ next_feed`인 프레임만(기본 10 Hz). 그 프레임만 depth를 읽고 정렬한다(비용 절약).
- 쓰기(`FrameWriter.write`)
  - 컬러는 **RGB로 뒤집어서** 전달: `np.ascontiguousarray(color_bgr[:, :, ::-1])`
  - 인자: `rgb, depth, K, stamp_ns, recv_wall(=time.time()), slam_context, depth_stamp_ns`
  - `slam_context`는 일부러 `tracking_state="TRACKING_LOST"`, `map_id="primary_sam_camera"` — 추론 쪽 앵커 기능을 **끄기 위한** 값(순수 per-frame 추정만 받기 위해)
  - 메모리 레이아웃: 헤더 384 B + RGB(640×480×3 = 921,600 B) + depth(640×480×2 = 614,400 B) ≈ **1.54 MB** (버퍼 상한 12 MB)
- 읽기(`FrameReader.read_new`): seqlock으로 새 프레임만 집어오고, 읽는 도중 덮어써졌으면 그 장을 버린다
- 추론 쪽 첫 동작: `cv2.cvtColor(rgb, COLOR_RGB2BGR)` — 내부 파이프라인(YOLO·MobileSAM)이 BGR을 기대하므로 다시 뒤집는다
- 결과적으로 버려지는 프레임: 급전 2,429 중 처리 691 (나머지는 다음 프레임에 덮여 사라짐) — **의도된 동작**

**그림·표 제안:** 프레임 메모리 레이아웃 막대(헤더/RGB/depth) + seqlock 타이밍.

**발표 노트:** RGB↔BGR을 두 번 뒤집는 것이 비효율로 보일 수 있으나, 공유메모리 규약을 기존 receiver 노드와 동일하게 유지하기 위한 선택이다(파리티 검증 도구가 존재).

### IMG-12. 이미지가 화면으로 가는 경로
**핵심 한 줄:** 표시용 이미지는 추론과 무관하게 흐르며, 최근 120장을 버퍼에 두고 **0.3초 과거**를 골라 그린다.

**슬라이드 본문**
- 적재: 재생 루프가 모든 표시 프레임을 `frames` deque에 `(t_ns, index, color_bgr)`로 넣는다. `maxlen=120` ≈ 30 fps에서 4초.
- 선택(렌더 스레드, 15 Hz): `target = replay_t_ns − 0.3 s` 이하인 **가장 최신** 프레임을 뒤에서부터 탐색.
- 그리기: 원본을 `img.copy()`한 캔버스에 레인별로 객체 박스·3축·라벨·레인 태그를 그린다(레인이 2개면 **같은 원본에서 캔버스 2장**이 만들어진다).
- 인코딩: `cv2.imencode(".jpg", canvas, JPEG_QUALITY=78)` → base64 → SSE payload의 `lanes[].jpeg`
- 대역폭 감각: 640×480 JPEG 품질 78 ≈ 40–60 KB, 15 Hz × 레인 수 → 레인 1개에서 약 6–9 Mbps (LAN에서 문제 없음)
- 백프레셔: 클라이언트 큐가 4개를 넘으면 오래된 payload부터 버린다 — 느린 브라우저가 허브를 막지 못한다.
- 밀릴 때: 재생 루프가 표시 프레임을 건너뛴다(`dropped_display` 카운트). 즉 **화면이 느려지는 대신 시간이 정확**하다.

**그림·표 제안:** deque 그림(최근 120장) + 표시 시각 화살표(현재 −0.3 s) + JPEG/SSE 흐름.

**발표 노트:** 표시 경로와 추론 경로가 **완전히 분리**돼 있어서, 추론이 느려져도 화면은 30 Hz로 흐른다는 점이 체감 품질의 핵심이다.

### IMG-13. depth 축소본 — 객체 메모리 전용 사본
**핵심 한 줄:** depth 검사를 위해 급전 프레임의 depth를 1/64로 줄여 보관한다. 원본을 들고 있으면 메모리가 감당되지 않는다.

**슬라이드 본문**
- 보관 시점: SAM-6D에 급전한 바로 그 프레임의 **정렬된 depth**를 `depth[::8, ::8]`로 축소(`remember_depth`)
  - 640×480 → 80×60, uint16 → **9,600 B**(원본 614,400 B의 1/64)
- 자료구조: `OrderedDict[stamp_ns] → 축소 depth`, 최대 600개(약 60초분). 초과하면 가장 오래된 것부터 제거.
- 소비: SAM-6D 결과가 도착하면 그 `stamp_ns`로 꺼내(`pop`) 객체 메모리의 프레임 기록에 첨부 → depth 검사에 사용
- 내부 파라미터 보정: 축소했으므로 K도 같이 줄인다(`DepthFrame.from_full`)
  - `fx' = fx·sx`, `cx' = (cx + 0.5)·sx − 0.5` (sx = 80/640 = 0.125) — 반 화소 규약을 지켜야 투영이 어긋나지 않는다
- 왜 축소해도 되는가: depth 검사는 랜드마크 중심 주변 3 cm 패치와 15 cm 창의 **통계**(먼 화소 비율)만 보므로, 화소 수보다 범위가 중요하다.
- 끄는 법: `--no-depth-check` → 축소본도 만들지 않는다(메모리·CPU 절약).

**그림·표 제안:** 원본 depth와 80×60 축소본을 나란히 + 패치/창 반경 표시.

**발표 노트:** "무엇을 얼마나 기억할 것인가"의 예 — 60초, 1/64 해상도라는 선택이 각각 어떤 요구에서 나왔는지 설명하면 좋다.

### IMG-14. SLAM 호스트 쪽 이미지 경로 (`slam_stream.cc` / `raw_session.h`)
**핵심 한 줄:** SLAM 카메라 이미지는 같은 정렬을 거쳐 ORB-SLAM3에 들어가고, 그 결과만 네트워크로 나간다.

**슬라이드 본문**
- 프레임 1장 처리(`process()`)
  1. sqlite에서 color/depth blob 조회(`Bag::by_id`)
  2. `read_image_msg()`로 CDR 파싱 — **기하와 크기를 검증**(예상과 다르면 즉시 예외)
  3. 인코딩 처리: `bgr8`이면 clone, `rgb8`이면 화소 루프로 BGR 변환(ROS 노드와 동일하게 BGR을 넘기기 위함)
  4. depth: `mono16`/`16UC1`만 허용, uint16 버퍼로 복사
  5. `depth_to_color()` — 변환본이면 그대로 복사, 원본이면 `Aligner::align()`(파이썬과 동일 알고리즘)
  6. `slam.TrackRGBD(color, depth_aligned, t_ns × 1e−9)`
- 시간 측정 분리: `prep_ms`(1–5단계, 디코딩·정렬) / `track_ms`(6단계, ORB-SLAM3) — 병목 진단용으로 포즈 메시지에 함께 실린다
- 네트워크로 나가는 것: `pose` 메시지 한 줄(수백 바이트). **이미지는 나가지 않는다.**
- 라이브 구성(`orb_live_stream.py`)에서는 이미지가 ROS 토픽으로 rgbd_node에 들어가고, 브리지는 `/orbslam3/pose`만 받는다 — 이미지 경로가 브리지를 거치지 않는다.

**그림·표 제안:** 6단계 파이프라인 + 각 단계 시간(prep/track) + 네트워크 경계선(이미지는 넘지 않음).

**발표 노트:** 두 호스트의 전처리가 같아야 하는 이유(IMG-08)와 이 장을 연결하면 "왜 C++로 한 번 더 구현했는가"가 자연스럽게 답된다.

### IMG-15. 이미지와 내부 파라미터·왜곡이 만나는 4곳
**핵심 한 줄:** 같은 K와 왜곡 계수가 네 군데에서 쓰이며, 어느 하나만 틀려도 증상이 전혀 다르게 나타난다.

**슬라이드 본문**

| 쓰이는 곳 | 무엇에 쓰나 | 틀렸을 때의 증상 |
|---|---|---|
| depth→color 정렬 | 역투영·재투영 | depth가 컬러와 어긋나 물체 경계가 밀림 → PEM 점군이 오염 |
| SAM-6D(PEM) | 마스크 화소 → 3D 점군 | 자세의 거리(z) 성분이 계통 오차 |
| 영상 오버레이 | 3D 박스 → 화면 투영 | 박스가 물체와 어긋나 보임(계산은 정상) |
| 객체 메모리 P_D·depth 검사 | 랜드마크 → 화면 투영 | 시야 판정 오류 → 존재확률 오감쇠, 오삭제 |

- 출처는 하나: 세션 bag의 `camera_info`. yaml이나 URDF가 아니라 **데이터에 붙어 온 값**을 쓴다.
- ORB-SLAM3 설정도 실행 시각에 덮어쓴다(`settings_with_camera`) — 데이터셋마다 yaml을 만들지 않는다.
- 오버레이 전용 방어: 왜곡 다항식이 `r = 1.63` 너머에서 접히므로 `r² > 1.3²`이면 왜곡을 적용하지 않는다(이미지 모서리가 r = 1.06). 이 규칙은 **표시에만** 적용되고 정렬·PEM에는 적용되지 않는다.

**그림·표 제안:** K를 중심에 두고 네 갈래로 뻗는 그림, 각 갈래에 증상 아이콘.

**발표 노트:** "같은 파라미터의 오류가 네 가지 다른 증상으로 보인다"는 점은 디버깅 경험담으로 쓰기 좋다.

### IMG-16. 입력 이미지 관련 검증과 실패 사례
**핵심 한 줄:** 이미지 경로에서 생긴 문제는 대부분 "조용히 잘못된 값"이라, 검증 장치를 명시적으로 넣었다.

**슬라이드 본문**

| 사례 | 증상 | 원인 | 대응 |
|---|---|---|---|
| 연관 스탬프 표류 | 융합 결과가 통째로 어긋남 | 컬러 드롭 + 인덱스 기반 스탬프 | 프레임 시계(메타데이터) 채택 |
| 변환본 vs 원본 불일치 우려 | 두 입력의 결과가 다를 수 있음 | 정렬 구현 차이 가능성 | 비트 단위 동일성 검증 |
| 짝 없는 컬러 프레임 | 조용한 프레임 손실 | 변환본의 스탬프 불일치 | 버리고 **개수를 보고** |
| 예상 밖 인코딩 | 색이 뒤집히거나 깨짐 | rgb8/bgr8 혼재 | 인코딩 명시 확인 + 그 외는 예외 |
| depth 기하 불일치 | 엉뚱한 배열 형태 | 해상도 설정 변경 | 크기·인코딩 검증 후 예외 |
| 죽은 카메라의 토픽 잔존 | 라이브에서 무한 대기 | 드라이버 UVC 정지 | **프레임 수신**으로 생존 판정 |
| 왜곡 접힘 | 화면을 가로지르는 선 | 시야 밖 점의 재투영 | `r² > 1.3²` 가드 |
| NFS 인덱싱 3분 | 실행 준비가 느림 | 페이지 미리읽기 | 크기·mtime 키 캐시 |

- 공통 원칙 3가지
  1. **모르는 입력은 즉시 실패**(조용한 오독 금지)
  2. **버린 것은 세어서 보고**(손실을 관측 가능하게)
  3. **같은 전처리를 모든 호스트가 공유**(구현은 3개, 알고리즘은 1개)

**그림·표 제안:** 위 표 + 세 원칙을 하단 배너로.

**발표 노트:** 이 장은 "데이터 파이프라인의 신뢰성을 어떻게 확보했는가"에 대한 답이며, 실험 결과를 방어할 때 근거가 된다.
