## 0. 결론 (요약)

**허브(fusion/memory/hub)와 스트리머의 키프레임 앵커링에는 이 분할을 만든 버그가 없다.**
분할의 원인은 **ORB-SLAM3가 만든 지도 자체가 내부적으로 어긋난 것**이다.

- 162947 런의 최종 보정 궤적은 t ≈ 85 s 까지는 정상 런들과 **3–14 cm** 이내로 일치하다가,
  두 번째 루프 클로저(85.5 s) 직후부터 끝까지 **0.6–1.2 m** 벌어진다.
- 그 결과 같은 물체를 1차 통과(34–64 s)와 2차 통과(99–145 s)에서 본 관측이 **최종 키프레임 포즈로 풀어도**
  0.65–1.05 m 떨어진 곳에 놓인다. 8개 클래스 전부가 **하나의 강체변환**(t = (0.337, 0.008, 0.472), |t| = 0.58 m,
  회전 17.46°, 잔차 평균 2.8 cm / 최대 4.7 cm)으로 정확히 설명된다 → 물체별 추정 오차가 아니라 **지도의 강체 어긋남**.
- 두 클러스터 중 **오래된(remembered) 쪽이 정답**이다. 정상 런 143755의 단일 인스턴스 위치와 2–5 cm
  (최대 12.5 cm, Sikhye) 이내로 일치한다. active(최신) 쪽이 틀린 위치다.
- 연관 게이트 0.15 m로는 0.65–1.05 m 떨어진 두 관측군을 하나로 묶을 수 없다 → 메모리는 **입력대로 정확히**
  두 인스턴스를 만들었다. (게이트를 1.2 m로 키우면 8개로 합쳐지지만, 융합 위치가 두 클러스터의 평균이 되어
  milk가 (0.609, 0.428, 1.368) — 정답 (0.097, 0.421, 1.099) 대비 0.6 m 오차 → **게이트 확대는 해법이 아니다**.)

부차적으로, **게이트 0.15 m가 루프 후 국소 지도 변형(0.15–0.3 m)보다 작아서 생기는 별개의 분할**이 확인된다
(162947의 t = 61.01 s 미세 분할 3건, 125210의 Mugcup 분할). 이쪽은 게이트 0.30 m로 완전히 해소된다(§6 검증).

## 5. 가설 검증

오프라인 하네스로 라이브 파이프라인을 **비트 단위로 재현**했다
(`slam_poses.jsonl` + `kf_updates.jsonl` + `sam6d_frames.jsonl` → 실제 `fusion.py` / `memory.py` / `objectmemory_ws`):

```
kf updates 166  culled 4  max_corr 227.8 cm  frames 854
landmarks 20  {'remembered': 9, 'deleted': 3, 'active': 7, 'lost': 1}
```
→ 라이브 `summary.json`의 20개 landmark와 **id·상태·관측수·위치가 mm 단위까지 동일**.
따라서 결과는 로그된 SLAM 데이터만으로 결정되며 라이브 허브의 스레드 경합 요소는 없다.

| 가설 | 판정 | 근거(수치) |
|---|---|---|
| **(a)** add_frame 시점 앵커가 보정 중간값으로 계산됨 | **기각** | 루프 창(71–77 s, 84–91 s)에 **SAM-6D 검출이 0건**. 검출 공백은 64.28 s → 99.42 s. `near_loop_estimates = 0`. 또 `T_kf_sam`은 상대량이라 이후 보정에 불변 |
| **(b)** cull redirect가 pre/post 보정 혼합 스냅샷을 통과 | **기각(이 런에서는 무영향, 잠재 버그는 실재)** | redirect 4건 = {51→49, 79→41, 121→20, 218→38}. 모두 **거짓 cull**(§7)이며 다음 kf_update에서 id가 되살아나 `resolve()`가 redirect를 쓰지 않음. 패치 후 재생 시 culled 0, landmark 결과 **완전 동일** |
| **(c)** remembered 상태가 인스턴스를 고정해 재구축이 병합하지 못함 | **기각** | remembered도 연관 후보에 그대로 남는다(`object_memory_runner.py:389-402, 491-494`). 게이트를 1.2 m로 키우면 실제로 8개로 병합됨 → 막은 것은 상태가 아니라 **0.65–1.05 m 라는 실거리** |
| **(d)** pose 메시지의 T_w_kf 와 kf_update 표가 루프 창에서 불일치 | **기각** | 4743개 pose의 `T_w_kf` vs 직전 kf_update 표: median 0.0000 m, p99 0.0157 m, **max 0.0391 m**, 5 cm 초과 0건. 루프 창만 보면 71.5–76.5 s max 0.0070 m, 85–90 s max 0.0000 m |
| **(추가)** 허브 앵커링이 이상적 앵커링과 다른가 | **기각** | 프레임별 `ObjectMemory._camera(f)` vs 메시지 단위로만 계산한 이상적 앵커(`T_w_kf_final(ref_kf)·T_w_kf(msg)⁻¹·T_wc(msg)·X`): n=854, median 0.0000 m, p99 0.0017 m, max 0.1214 m |

**남는 설명은 하나뿐: 최종 지도 자체가 두 통과 구간 사이에서 0.58 m + 17.5° 어긋나 있다.**

## 6. 부차 메커니즘 — 게이트 0.15 m < 루프 후 국소 변형

지도가 전체적으로 정상인 런에서도 분할이 난다.

- 162947: t = 61.01 s 에 milk id=11, Mugcup id=9, choco id=10 이 **동시에** 새로 생성. 이 프레임의 앵커는 kf49이고
  kf49는 61.2 s 이후 최종까지 **0.291 m** 이동(같은 시기 kf14는 0.029 m) → 정지 물체의 월드 좌표가 한 통과 안에서
  0.2 m 흘렀다.
- 융합이 러닝 평균 w = 1/(n+1)(`core/fusion.py:167-172`)이라 n=20이면 새 관측 1개는 랜드마크를 0.7 cm 밖에 못 옮긴다.
  → 랜드마크가 느린 지도 변형을 따라가지 못하고 결국 게이트(0.15 m)를 넘어 새 인스턴스가 생성된다.
- 125210의 Mugcup 분할(id 2 / 9 / 10, 간격 0.16 m)도 동일 메커니즘. **지도는 정상(≤11 cm)** 이었다.

**오프라인 게이트 스윕:**

| 게이트 | 162947 | 125210 |
|---:|---|---|
| 0.15 (현재) | 20 landmarks (클래스당 2–3) | 10 (Mugcup 3개) |
| **0.30** | **17** (클래스당 정확히 2 = 지도 어긋남만 남음) | **8 = 클래스당 1개, 위치 정상 런과 수 cm 일치** |
| 0.60 | 17 (동일) | – |

→ **0.30 m 가 최적 구간**: 국소 변형에 의한 허위 분할은 없애고, 진짜 지도 오류(0.65 m 이상)는 여전히 두 개로 노출.

## 7. 발견된 잠재 버그 — `KeyframeMap.apply_update` 의 거짓 cull

`objpose/pc/fusion.py:93`

```python
gone = [k for k in old_same_map if k not in new]
```

`self.T` 에는 **pose 메시지로만 알게 된 최신 키프레임**도 들어 있다(`fusion.py:171`). 스트리머가 kf_update를
만든 시점에는 아직 없던 키프레임이므로, 그 id는 목록에 없다 → **컬링된 것으로 오인**되어 공간상 최근접 생존자로
redirect 된다.

실제 발생(재생 결과):

| 런 | t_rel | reason | update의 n | 거짓 cull id | redirect 대상 |
|---|---:|---|---:|---:|---|
| 162947 | 62.21 | periodic | 51 (id 0–50) | 51 | 49 |
| 162947 | **72.65** | **map_changed** | 79 (0–78) | 79 | 41 |
| 162947 | **85.55** | **map_changed** | 121 (0–120) | 121 | **20** |
| 162947 | 140.40 | periodic | 218 | 218 | 38 |
| 125210 | (9건) | – | – | 18,72,76,88,120,122,125,129,189 | 16,49,**45(0.605 m)**,36,**14**,16,15,**13**,116 |

두 가지 위험: ① redirect 대상이 시간적으로 100 KF 떨어진 엉뚱한 키프레임(121→20, 129→13)일 수 있고,
② **루프 보정 창에서 일어나면**(72.65 / 85.55) `old_same_map` 이 "이전 스냅샷(보정 전) + pose 메시지(보정 후)"를
섞으므로 redirect 변환에 보정량(이 런에서는 kf41이 0.38 m 이동)이 그대로 오차로 들어간다.
이번 런은 해당 창에 검출이 없어 결과에 영향이 없었지만, 검출이 있었다면 수십 cm 오차가 났을 것이다.

## 8. 수정 제안

### F1 (필수, 즉시) — 거짓 cull 제거 · `objpose/pc/fusion.py:93`

```python
newest = max(new) if new else -1
gone = [k for k in old_same_map if k not in new and k < newest]
```

kf_update는 항상 현재 맵의 전체 키프레임을 보내므로(`slam_stream.cc:461-474`), 목록의 최대 id보다 큰 id는
"컬링된 것"이 아니라 "메시지 생성 후 만들어진 것"이다.
**기대 효과**: 162947 4건, 125210 9건의 거짓 cull과 잘못된 redirect가 사라진다.
**검증 완료**: 두 런 오프라인 재생에서 `culled 0`, redirect 없음, landmark 결과는 기존과 **완전히 동일**(무회귀).

추가로 `fusion.py:94-101`의 최근접 생존자 선택을 "공간 최근접" 대신 **id 거리 우선(공변 그래프 이웃)**으로
바꾸는 것을 권장한다(121→20 같은 시간적으로 먼 재앵커 방지).

### F2 (권장) — 연관 게이트 0.15 → 0.30 m + 융합 가중치 하한

- `objpose/pc/hub.py:1089` 기본값 `--assoc-gate-m 0.30`.
- `objectmemory_ws/.../core/fusion.py:167-172` 의 `w = 1.0/(n_prev+1)` → `w = max(1.0/(n_prev+1), 0.05)`
  (랜드마크가 느린 지도 변형을 따라가게 함; 옵션 플래그로 노출 권장).

**기대 효과**: 125210 Mugcup 분할 소멸(8 = 클래스당 1개, 위치는 정상 런과 수 cm), 162947의 61 s 미세 분할 3건 소멸.
지도가 진짜로 깨진 0.65 m 이상 분할은 그대로 노출된다(그게 옳다).
**검증 완료**: §6 게이트 스윕.

### F3 (권장) — 지도 불일치 자동 탐지 · `objpose/pc/memory.py` + `hub.py` 통계

같은 클래스에 살아 있는 인스턴스가 2개 이상인 클래스들을 모아, **구 클러스터 → 신 클러스터의 강체변환**을
Kabsch로 적합한다. 3개 클래스 이상이 잔차 ≤5 cm 로 같은 SE(3)를 공유하면 "객체가 늘어난 것"이 아니라
**SLAM 지도가 갈라진 것**이다(이번 런: 7/7, 잔차 2.8 cm).

- `ObjectMemory.stats()`에 `map_split: {n_classes, t_m, rot_deg, residual_m}` 추가,
  `hub.py:492-497` lane stats와 `summary.json`에 기록, 웹 UI에 경고 배지.
- 정책 옵션 `--map-split-policy {report|prefer_new|prefer_old}`: 기본 report(현행 동작 유지 + 경고),
  prefer_new/old 는 중복 인스턴스를 한쪽만 표시.
- **게이트 확대로 병합하지 말 것** — §0에서 보였듯 평균값이 되어 0.6 m 오차가 된다.

### F4 (SLAM 측, 진짜 원인) — 루프 보정 결과 검증 · `slam_stream.cc` / `LoopClosing.cc`

1. **계측 추가(저비용, 즉시)**: `LoopClosing.cc:288` (`LOOP_GAP` 출력 직후, `CorrectLoop()` 전후)에
   보정 결과를 `LOOP_CORR|cur_id=..|moved_max_m=..|moved_id_lo=..|moved_id_hi=..|n_moved_5cm=..` 로 남긴다.
   정상 보정은 **새 구간이 크게 이동**(143755: kf110–119가 3.2 m), 실패 보정은 **옛 구간만 조금 이동**
   (162947: kf28–73가 ≤0.43 m)이라는 §2의 판별식을 로그만으로 즉시 확인할 수 있다.
2. **루프 후 정합 검사**: 보정 후 `cur`와 `matched` 키프레임의 상대 포즈가 Sim3 측정값과 임계치 이상 다르면
   경고를 내고 `map_changed` kf_update에 `"suspect": true` 를 실어 보낸다(허브는 F3 경고와 연결).
3. **초기 루프 억제 실험**: 72 s 루프(matched_id = 2, 세션 시작 1–2 s 구간의 부트스트랩 키프레임)를
   `bGoodLoop = false`(`LoopClosing.cc:260` 부근)로 거부하도록 임시 게이트
   (matched KF가 세션 첫 N초/첫 N개 키프레임에 속하면 거부)를 넣고 동일 bag을 5회 재생해
   85 s 루프 보정이 3 m급으로 회복되는지 확인. **회복되면 이것이 근본 수정**이고, 아니면 원인은
   에센셜 그래프/GBA 타이밍 쪽이므로 2번의 검증 경로로 간다.

### F5 (선택) — 재구축 시 2-패스 클러스터링

`memory.py:108-132`의 전면 재구축은 이미 전 프레임을 다시 재생한다. 재생 전에 클래스별 관측 월드 좌표를
한 번 클러스터링해서 초기 인스턴스 수/시드를 정하면, 순차 필터가 만든 "드리프트 꼬리" 분할이 구조적으로 사라진다.
F2보다 큰 변경이므로 F1·F2·F3 이후 검토.

## 9. 라이브 시스템 손대기 전 오프라인 검증 절차

1. 아래 하네스를 `/tmp` 작업 디렉터리에 두고 **현재 코드**로 실행 → `summary.json`의 landmark 20개와
   id/상태/관측수/위치가 일치하는지 확인(기준선 확보). 162947과 125210 두 런 모두.
2. F1 패치 적용 후 재실행 → `culled 0`, landmark 결과 무변화 확인.

   추가로 143755·144806(정상 런)에서 landmark 수가 줄지 않는지(과병합 없음) 확인.
4. F3 탐지기 단위 확인: 162947에서 `map_split.n_classes = 7`, `residual ≈ 0.028 m`, `|t| ≈ 0.58 m`;
   143755에서는 발동하지 않아야 한다.
5. 전부 통과하면 실기 재생 1회(`run_one.sh orb-mac`)로 회귀 확인. **현재 8766 포트 허브는 건드리지 않는다.**

```python
# offline_replay.py — 기록된 로그만으로 허브 메모리 파이프라인 재현
import json, sys, numpy as np
sys.path.insert(0, '/home/jucpark/DeepLearning/CLI_environment/objpose/pc')
from fusion import Fusion, PoseBuffer
from memory import ObjectMemory
RUN = sys.argv[1]; GATE = float(sys.argv[2]) if len(sys.argv) > 2 else 0.15
X = np.array(json.load(open('/home/jucpark/DeepLearning/CLI_environment/objpose/rt/260910/'
                            'X_slam_sam_260910.json'))['T_slam_sam'], float)
K = [[386.708, 0, 322.784], [0, 386.137, 250.280], [0, 0, 1]]
S = json.load(open(RUN + '/summary.json')); t0 = S['t0_ns']
poses  = [json.loads(l) for l in open(RUN + '/slam_poses.jsonl')]
ups    = [json.loads(l) for l in open(RUN + '/kf_updates.jsonl')]
frames = [json.loads(l) for l in open(RUN + '/sam6d_frames.jsonl')]
pb = PoseBuffer(); fu = Fusion(X, pb, 0)
mem = ObjectMemory(fu, K, (640, 480), assoc_trans_gate_m=GATE, assoc_rot_gate_deg=None)
ev = ([(p['t_ns'], 0, p) for p in poses] + [(u['t_ns'], 1, u) for u in ups]
      + [(f['t_ns'] + 600_000_000, 2, f) for f in frames])          # 결과 도착 지연 0.6 s
ev.sort(key=lambda e: (e[0], e[1]))
for t, kind, m in ev:
    if kind == 0:
        pb.add(int(m['t_ns']), m.get('state', '?'), m.get('T_wc'), m.get('map_id'),
               kf=m.get('ref_kf'), T_w_kf=m.get('T_w_kf'), kf_map_id=m.get('kf_map_id'),
               map_changed=bool(m.get('map_changed')))
    elif kind == 1:
        pb.apply_kf_update(m.get('map_id'), m.get('kfs', [])); mem.update()
    else:
        mem.add_frame(int(m['t_ns']),
                      [(d['object'], d.get('score', 0.0), d['R'], d['t_mm']) for d in m['dets']])
        mem.update()
mem.update()
print('culled', pb.kfs.culled, 'redirect', {k: v[0] for k, v in pb.kfs.redirect.items()})
print(mem.stats())
for m in sorted(mem.landmarks(), key=lambda m: (m['name'], m['first_seen_ns'])):
    P = np.asarray(m['T_w_obj'])[:3, 3]
    print(f"{m['name']:20s} id={m['object_id']:>3} {m['status']:11s} n={m['n_obs']:3d} "
          f"first={(m['first_seen_ns']-t0)/1e9:7.2f} last={(m['last_seen_ns']-t0)/1e9:7.2f} "
          f"p=({P[0]:7.3f},{P[1]:6.3f},{P[2]:6.3f})")
```
