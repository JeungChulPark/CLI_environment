## 1. 측정 환경과 데이터 출처

- 워크스테이션 GPU: `NVIDIA GeForce RTX 4090` 4장 (드라이버 575.57.08 / CUDA 12.9).
  SAM-6D 설정은 `runtime.device: cuda:0` 이므로 **한 장만** 쓴다. 분석 시점에 관련
  프로세스는 실행 중이 아니었다(4장 모두 0% util).
- 원시 데이터
  - `<run>/sam6d/frames.jsonl` — 처리된 **모든** 프레임의 `ms{yolo,ism,pem,total}`,
    `n_boxes`(YOLO 박스 수), `n_accept`(최종 채택 검출 수), `stamp_ns`, `t_done_ns`.
    가장 정보량이 많은 소스라서 지연 통계의 기준으로 삼았다.
  - `<run>/sam6d_estimates.jsonl` — 허브가 받은 **검출 1건마다** 한 줄, `result_age_s` 포함.
  - `<run>/sam6d_frames.jsonl` — 허브가 받은 프레임 수(결과 채널 기준).
  - `<run>/summary.json` — `sam6d_fed`, `sam6d_frames`, `sam6d_age_median_s`, `display_delay_s`.
  - `<run>/sam6d_infer.log`, `<run>/sam6d/run_meta.json` — 로드 시간·프레임별 콘솔 라인.
- 타이머 정의 (`sam6d_realtime/realtime/sam6d_core.py:218/224/241/467-470`,
  각 지점 앞에 `torch.cuda.synchronize()`):
  - `yolo` = BGR→RGB 변환 + YOLO-World predict
  - `ism` = 박스 정리 + `recognize_frame_auto` (MobileSAM → DINOv2 → 42템플릿 매칭 → HSV/NMS)
  - `pem` = PEM 스케줄러 선택 + PEM forward + 후처리 + 라벨영상 + 앵커 로직
    (본 실행들은 `anchor.enabled=false` 라 앵커 비용은 사실상 0)
  - `total` = `t3 - t0`. 세 구간이 `[t0,t3]`를 빈틈없이 덮으므로
    **total ≈ yolo+ism+pem** (반올림 오차 1–2 ms).
  - `total`에 **포함되지 않는 것**: 공유메모리 read/write, jsonl 기록, 마스크 PNG 저장.
    이 부분은 아래 "shm 대기"로 따로 뽑았다.

## 2. 처리량 (Throughput)

`replay` = 허브의 `replay_t_rel_s`(실제 재생 길이). `fed` = 허브가 공유메모리에 써 넣은
프레임 수(`--sam-feed-hz 10` 목표). `processed` = SAM-6D가 실제로 추론한 프레임 수.
공유메모리는 seqlock 기반 **최신 1장 덮어쓰기** 채널이라, 추론이 바쁘면 그 사이 프레임은
큐에 쌓이지 않고 **그냥 사라진다**.

| run | 데이터셋 | replay [s] | fed | 급전 [Hz] | processed | **처리 [fps]** | **처리/급전** | GPU 점유율(duty) |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| one_hdl-mac_260914_123836 | 260910_object | 159.1 | 1,427 | 8.97 | 845 | **5.31** | **59.2%** | 62.9% |
| one_orb_260914_124614 | 260910_object | 159.1 | 1,427 | 8.97 | 852 | **5.36** | **59.7%** | 62.7% |
| one_orb-mac_260914_125210 | 260910_object | 159.1 | 1,432 | 9.00 | 854 | **5.37** | **59.6%** | 62.9% |
| one_260910_object_orb-mac_260914_143755 | 260910_object | 159.1 | 1,443 | 9.07 | 863 | **5.42** | **59.8%** | 62.8% |
| one_260910_object_orb_260914_144104 | 260910_object | 159.1 | 1,442 | 9.07 | 862 | **5.42** | **59.8%** | 62.8% |
| one_260826_etri_eightcircle_dark_orb_260914_140800 | 260826_eightcircle_dark | 284.7 | 2,407 | 8.46 | 696 | **2.44** | **28.9%** | **99.2%** |
| smoke_hdl_100722 (스모크, 조기 종료) | 260910_object | 40.0 | 373 | 9.33 | 334 | **8.35** | **89.5%** | 27.9% |

- **급전이 10 Hz에 못 미치는 이유**: 허브 재생 루프가 `now >= next_feed` 로만 급전 시점을
  판정하기 때문에 실효 8.5–9.1 Hz가 된다(`objpose/pc/hub.py:592` 부근).
- **duty(GPU 점유율)** = Σ`ms.total` / 처리 구간 길이. 260910 계열은 63%로 아직 여유가
  있으나, 물체가 상시 보이는 **260826_eightcircle_dark는 99.2%로 완전 포화**다. 이 런에서
  드롭률이 71%로 뛰는 이유가 이것이다.
- 스모크 테스트는 93%가 빈 프레임이라 8.35 fps가 나왔다. 즉 **처리량은 GPU가 아니라
  "장면에 물체가 몇 개 보이느냐"가 결정한다.**
- `sam6d_frames`(허브 수신)가 `processed`(추론)보다 매번 0–9 프레임 적은 것은 종료 시점에
  마지막 결과 몇 장을 허브가 받기 전에 세션이 끝나서다. 유의미한 손실은 아니다.

### 6.3 표시 지연(0.3 s) 및 오버레이 로직과의 비교

- 허브 렌더러는 `target = replay_t_ns − display_delay(0.3 s)` 인 가장 최신 프레임을 골라
  화면에 띄운다(`hub.py:773`). 즉 **결과가 0.3 s 안에 오면 그 프레임 자체에 정합**된다.
- 그런데 검출이 있는 프레임의 age 중앙값이 **0.82–0.90 s (260910)**, **0.55 s (260826)**
  이라, 검출 결과의 **99% 이상이 0.3 s 창을 넘긴다**. 표시 지연을 늘리지 않는 한
  "이 프레임의 검출을 이 프레임 위에 그리는" 일은 사실상 일어나지 않는다.
- 실사용상 문제가 되지 않는 이유는 오버레이가 프레임 로컬이 아니라 **월드 앵커 방식**이기
  때문이다. `Fusion.add_estimate()`가 SLAM 포즈로 `T_w_obj`를 만들어 저장하고,
  `lane_frame()`이 표시 시점 `t_ns`의 카메라 포즈로 **재투영**한다
  (`hub.py:727-733`, `overlay_max_age_s = 60.0`). 즉 age는 "박스가 잘못된 위치에 뜨는 양"이
  아니라 **"객체 상태가 얼마나 낡았는가"**이며, 카메라가 빠르게 움직여도 SLAM 포즈가
  보정한다. 대신 **움직이는 물체**에는 그대로 0.8 s 만큼의 위치 오차로 나타난다.
- 정리하면: 0.3 s 표시 지연은 **SLAM 포즈 도착 지연**에는 충분하지만
  (`slam_lag_s ≈ 0.058`), **SAM-6D 결과 지연에는 3배 부족**하다.

## 7. 허브가 실제로 쓴 설정 — 속도 옵션은 전부 꺼져 있다

`hub.py:551-560 start_sam6d()`은 `sam6d_realtime/realtime/run_split_example.yaml`을 읽어

| **`mask_cache`** | **없음 → 비활성** |
| **`pem_schedule` (PEM budget)** | **없음 → 비활성** |

로그에서도 확인된다. 7개 런 모두 `sam6d_infer.log`에 `mask_cache on` / `scheduler on` /

**구조적 이유**: 세 옵션은 `Sam6DCore.__init__(mask_cache=, pem_schedule=, precision=)`

"config/preset 체계"가 미완 항목으로 남아 있다.

## 9. 병목 진단

> **병목은 PEM의 point matching이고, 그 다음이 ISM의 MobileSAM 이미지 인코더다.
> 두 단계 모두 "객체 수"보다 "프레임당 고정비"가 지배한다. YOLO는 무관하다.**

근거를 정리하면:

1. **누적 시간의 57–68%가 PEM, 31–37%가 ISM, YOLO는 2–6%.**
   (§3.3) 저장소 벤치마크의 모듈 분해와도 일치한다 — PEM 내부에서 coarse+fine
   point matching이 73%(§8.3).
2. **고정비 지배.** `pem ≈ 230 ms + 92 ms × n_det` (260910), `143 ms + 94 ms × n_det`
   (260826). 객체 1개짜리 프레임도 PEM에 293 ms를 쓴다. 마찬가지로 MobileSAM은
   박스 1개에도 35 ms.
3. **처리량 한계의 실체.** 물체가 안 보이면 7 ms(=140 fps 상당), 1개 보이면 410 ms
   (=2.4 fps). 260910에서 5.4 fps가 나오는 건 프레임의 87%가 빈 프레임이라 평균이
   희석된 결과다. **물체가 상시 보이는 260826은 2.44 fps, GPU duty 99.2%로 완전 포화**
   → 급전의 71%를 버린다. 즉 **실질 상한은 2.4–2.8 fps**이다.
4. **IPC/네트워크는 병목이 아니다.** shm 대기 중앙값 1 ms(260910), 54 ms(260826 포화 시).
   허브 급전도 목표 10 Hz 대비 9 Hz로 충분하다.
5. **낭비되는 계산이 있다.** 260826에서 `n_accept=0`인 109프레임이 PEM에 중앙값 96 ms를
   쓴다 — verify 단계에서 기각될 후보를 끝까지 풀고 있다.
6. **GPU가 3장 놀고 있다.** `runtime.device: cuda:0` 하드코딩으로 4090 4장 중 1장만 쓴다.

## 10. 더 빠르게 만드는 방안

### 방안 A — 이미 구현된 opt-in 옵션을 실제로 켤 수 있게 배선 (최우선, 저위험)

`sam6d_infer.py:116-121`이 `runtime.precision` / `runtime.mask_cache` /
`runtime.pem_schedule`을 `Sam6DCore`에 전달하도록 3줄을 추가하고,
`run_split_example.yaml`에 보고서 §9 권장값을 넣는다.

```yaml
runtime:
  precision: bf16
  fine_npoint: 1024        # 2048 → 1024
  coarse_npoint: 196       # 건드리지 말 것
  mask_cache:   {enabled: true, iou_thresh: 0.90, max_age: 5, interval: 30}
  pem_schedule: {enabled: true, budget: 1, max_age: 4}
```

기대 효과 (저장소 실측 기반, RTX 3080 Ti 측정치의 **상대 개선율**을 본 워크스테이션의
260826 실측 중앙값 total 383 ms에 적용):

| 옵션 | 저장소 근거 | 260826 기준 예상 |
|---|---|---|
| BF16 + fine_npoint 1024 | PEM 254.6 → 144.4 ms (**−43%**, 정확도 20/20 유지) | PEM 275 → ~157 ms |
| mask cache (정지/저속 장면) | MobileSAM 38.8 → 19.5 ms (**−49%**), ISM의 77%가 MobileSAM | ISM 95 → ~58 ms |
| PEM budget=1 | PEM 87.2 → 48.0 ms (4객체 기준) | 다객체 프레임에서 추가 −30~45% |

- 합산 예상: **383 → 약 220 ms (1.7배, ≈ 4.5 fps)**. BF16+fn1024만 켜도 383 → ~265 ms.
- 비용: BF16은 공짜가 아니다 — 회전 오차 중앙값 0.24° → 1.31°(5.5배). mask cache 이득은
  **장면 의존적**이며 12 px/frame 이상 움직이면 0%. PEM budget의 carried 포즈 오차는
  **저장소가 측정하지 않았다** — 본 시스템은 SLAM 월드 앵커로 융합하므로 영향이 완화될
  가능성이 있으나 별도 검증이 필요하다.

### 방안 B — verify 기각 후보를 PEM 앞으로 당기기 (중간 위험, 저장소 벤치마크 없음 = 추정)

현재 `verify`(mask IoU 0.421 / texture 0.450 / cluster)는 PEM으로 포즈를 푼 **뒤** 적용된다.
260826에서 `n_accept=0`인 프레임이 PEM에 96 ms를 태우고 있고, 검출 프레임에서도 상당수
후보가 최종 기각된다. ISM 점수 + texture 사전 게이트를 PEM 호출 **전에** 적용하면
낭비를 줄일 수 있다.

- **기대 효과 (추정, 저장소 측정 없음)**: 260826에서 PEM 호출 후보를 20–30% 줄이면
  전체 total 중앙값 **−8~15%**. 260910처럼 검출이 드문 장면에서는 이득이 거의 없다.
- 위험: 사전 게이트가 진짜 양성을 자르면 검출률이 떨어진다. `mask_iou_min`/
  `texture_min_score`가 이미 캘리브레이션된 값이라 임계 재조정 실험이 필요하다.

### 방안 C — 4090 4장 중 나머지 3장 활용 (중간 위험, 저장소 벤치마크 없음 = 추정)

`runtime.device: cuda:0` 고정이라 24 GB 4090 3장이 완전히 놀고 있다.

1. **파이프라인 분할** — ISM(MobileSAM+DINOv2)을 `cuda:1`, PEM을 `cuda:0`에 올려 2단
   파이프라인으로 겹친다. 260826 기준 stage-limited throughput은
   `max(ISM 95, PEM 275) + YOLO 6 ≈ 281 ms` → **2.44 → 3.5 fps (+44%, 추정)**.
   지연(latency)은 줄지 않고 오히려 조금 늘지만 **드롭률이 크게 개선**된다.
2. **프레임 라운드로빈** — 프로세스 2개를 `cuda:0`/`cuda:1`에 띄우고 허브가 번갈아 급전.
   구현이 가장 단순하고 **처리량 거의 2배(추정)**, 지연은 그대로. 대신 결과 순서가
   섞이므로 허브 `run_results`가 stamp 기준 정렬/최신 우선 처리를 해야 한다.
   GPU 메모리도 프로세스당 전체 모델 셋을 중복 적재한다.

- 두 방안 모두 **저장소에 측정치가 없는 순수 추정**이다. 다만 stage 비용(§3.3)과
  duty 99.2%라는 실측에서 산술적으로 도출된다.

### 우선순위

1. **A** — 코드가 이미 있고 벤치마크도 있다. 3줄 배선 + YAML. 가장 확실.
   단, 도입 후 반드시 정확도(회전 오차 / 배치 성공률) 회귀 측정을 같이 돌릴 것.
2. **C-2 (프레임 라운드로빈)** — 알고리즘을 건드리지 않고 정확도 손실 0으로
   처리량을 늘리는 유일한 방안. 놀고 있는 GPU 3장이 있으니 비용도 없다.
3. **B** — A/C로 부족할 때. verify 임계 재캘리브레이션이 선행되어야 한다.

### 하지 말아야 할 것 (저장소 벤치마크 근거)

- PEM 백본(ViT-Base) 교체나 TensorRT 변환 — 전체의 7–9%뿐.

## 11. 실측 결과 (2026-09-14 배선 후)

§10 방안 A(옵션 배선)를 실제로 구현하고, 같은 데이터셋·같은 백엔드(`260910_object` /
`hdl-mac`)로 다시 돌려 §0~§6 과 동일한 방법으로 측정했다. 기준선은 §2 의
`one_hdl-mac_260914_123836`(fp32, 옵션 전부 off)이다.

### 11.1 배선하면서 드러난 것 — §9 권장값은 이 배치에서 그대로 쓸 수 없다

배선 자체는 §10 A 가 말한 대로 3줄이 아니었다.

1. `fine_npoint` 는 `Sam6DCore` 생성자에 **없었다**. `coarse_npoint_override` 만 있었고,
   `fine_npoint` 는 `ViTEncoder` 가 `rgb_choose.size(1) == fine_npoint` 를 단언하므로
   `pcfg.model.fine_npoint` 와 `pcfg.test_dataset.n_sample_observed_point` 를 **같이**
   바꿔야 한다. `fine_npoint_override` 를 새로 넣었다.
2. **BF16 은 이 배치에서 그냥 죽는다.** verify 스택(`independent_candidate_verify` /
   `_candidate_shape_metrics`)은 저장소 벤치(`bench_pem_modules.py`)가 타지 않는 경로라
   반정밀도 검증이 된 적이 없다. 세 군데를 고쳐야 예외 없이 돈다.
   - `texture_by_original[b, subset] = einsum(...)` → 목적지 fp32 / 소스 bf16 dtype 불일치
   - `torch.linalg.det(R)` → LU 분해에 BFloat16 CUDA 커널이 없다
   - `out["pred_R"].cpu().numpy()` → 반정밀도 텐서는 `.numpy()` 가 막힌다

### 11.2 옵션별 오프라인 A/B (검출이 있는 실제 프레임 60장, 같은 프레임·같은 순서)

### 11.5 결론 / 배선 결과

- 허브에 `--sam6d-speed {off,fast,report}` 를 넣었다(기본 **fast**). 선택한 모드는
  `summary.json` 의 `sam6d_speed` 에 남는다.
  - `off` — 2026-09-14 이전과 완전히 같다(fp32 / 캐시 off / 예산 off).
  - `fast` — `fine_npoint 1024` + `mask_cache`. **실측으로 정확도가 확인된 부분만** 켠다.
  - `report` — §9 권장값 그대로(bf16 + PEM budget 1 포함). 재현·재측정용으로만 남긴다.
- **fast 의 실이득은 검출 프레임 −11%(692 → 614 ms), 결과 지연 −13%(0.834 → 0.722 s),
  처리량 +3.4%(5.31 → 5.49 fps)** 다. §10 A 가 기대한 1.7배와는 거리가 멀다. 기대치의
  대부분이 BF16(−43%)과 PEM budget 에 걸려 있었는데 둘 다 못 쓰기 때문이다.
- **BF16 을 쓰려면 `verify` 임계값(`mask_iou_min` / `texture_min_score`)을 bf16 에서
  다시 캘리브레이션해야 한다.** 이게 선행되지 않으면 BF16 은 순손실이다.
- **PEM budget 을 쓰려면 carried 포즈를 "그 포즈를 푼 프레임의 카메라 자세" 로 월드에
  꽂아야 한다.** 지금은 도착 시점 자세로 꽂아서 카메라 이동분이 그대로 오차가 된다.
  `pose_source == "carried"` 와 `carried_age` 가 이미 결과에 실려 오므로 허브 쪽에서
  해당 프레임 stamp 로 포즈를 되짚으면 해결 가능하다 — 별도 작업.
- §10 우선순위는 그대로 유효하되, **A 의 기대 효과는 −11%로 내려 잡아야 한다.**
  놀고 있는 4090 3장을 쓰는 **C-2(프레임 라운드로빈)** 가 정확도 손실 0 으로 처리량을
  올리는 유일한 카드라는 결론은 오히려 더 강해졌다.
