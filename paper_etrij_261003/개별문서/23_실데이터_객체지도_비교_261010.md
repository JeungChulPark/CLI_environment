# 23. 공간 객체 상태 지도 비교 4단계 — 실 데이터 녹화 5개 (제안 대 FM-Fusion 대 DualMap, 2026-10-10)

> 20 문서(YCB-V)와 21 문서(ObChange-Kitchen)에 이어, 우리 로봇으로 찍은 실 데이터 녹화 5개로 세 방법의 객체 지도를 비교했습니다. 장비는 Mac ORB-SLAM3(특징점 2000) + 노트북 RTX 3080 Ti Laptop 이고 확인용입니다(최종 수치는 RTX 5090). 코드는 `src/objmap/`(real_prep.py, real_score.py, run_real_compare.sh, 그리고 세 방법 변환기의 `--dataset real`), 결과는 `src/objmap/out/real_scores.json` 입니다. 끝에 세 데이터의 비교표를 함께 정리했습니다(5절).

## 0. 요약

- **녹화 5개, 물체 40개(녹화마다 8개) 합계, 최종 지도 맞음 / 잘못:** 제안 **39 / 1**, FM-Fusion 33 / 174, DualMap 14 / 12(공개 설정) · 19 / 18(BGR 수정). 점수(맞음 ÷ (8 + 잘못))는 제안 **95.1%**, FM-Fusion 15.4%, DualMap 26.9% · 32.8% 입니다.
- **FM-Fusion 은 물체를 많이 찾지만(33/40) 잘못 올린 물체가 녹화당 11~51개입니다.** 잘못의 86%(150/174)가 8개 물체 어디에도 가깝지 않은 자리, 즉 배경의 다른 물건입니다. "brown snack box"(초코) 문구가 실험실의 상자들에, "pink mug"·"blue spray bottle" 이 비슷한 물건들에 붙었습니다.
- **DualMap 은 잘못은 적지만 대부분 못 찾습니다(14~19/40).** 물체를 2D 상자로 찾지 못한 덩어리는 'unknown' 으로만 남고(녹화당 9~67개), 이름이 붙은 물체는 녹화당 2~10개뿐입니다. 샤프란·초코·우유·식혜는 거의 못 찾았습니다.
- **식혜("gold drink can")는 두 기준 방법 모두 다섯 녹화에서 한 번도 찾지 못했습니다.** 글 문구 선택의 영향일 수 있어 아래 6절에 한계로 적었습니다.
- **조건:** 세 방법 모두 같은 영상과 같은 카메라 궤적(제안 방법의 실시간 실행에서 Mac ORB-SLAM3 가 낸 궤적)을 씁니다. 제안 방법은 1배속 실시간(인식 1.9~3.5 Hz)이고, 두 기준 방법은 오프라인으로 10프레임마다 처리했습니다(FM-Fusion 검출 장당 1.2~2.0 초).

## 2. 실행 구성

### 2.1 공통 입력 (`real_prep.py`)
- **영상:** 허브가 읽는 방식 그대로 인식 카메라 RGB-D 를 꺼냈습니다. 같은 시각 보정을 쓰고, 녹화 2 는 원시 SDK 녹화라 깊이를 컬러 화면에 맞춰 옮겼습니다.
- **카메라 궤적:** 제안 방법 실행이 기록한 Mac ORB-SLAM3 자세(`slam_poses.jsonl`)를 쓰고, 실행 끝의 키프레임 자세로 루프 보정을 반영했습니다. 식으로는 T_w_c' = T_w_kf(끝) · T_w_kf(그때)⁻¹ · T_w_c 이고, 키프레임 고정 지도가 받는 보정과 같습니다. 기준 키프레임이 지워진 자세(녹화 1 은 26%, 녹화 3 은 25%)에는 시간상 가장 가까운 자세의 보정을 썼습니다. 이 자세를 인식 카메라로 옮기는 데는 실행의 T_slam_sam 을 썼습니다.
- **궤적 확인:** 물체 기준 위치를 영상에 투영해 깊이와 맞는지 10초 구간별로 봤습니다. 대부분 구간에서 90~100% 맞았습니다. 녹화 4 의 80~95초 구간만 43% 인데, SLAM 자세가 2.4 m 틀어졌다가 나중에 바로잡힌 구간입니다(프레임 몇 장). 제안 방법이 받은 SLAM 출력과 같은 것이므로 그대로 두었습니다.

### 2.3 채점 (`real_score.py`)
- 물체 정답(점군, 6D 자세)은 없습니다. 기준은 `realdata/eval_real.py` 와 같고, 각 물체 위치는 이전 실행들의 중앙값입니다.
- **맞음:** 8개 중 하나의 종류이고, 그 물체 기준 위치에서 20 cm 안이면 맞음입니다. 종류마다 하나만 셉니다.
- **잘못:** 이름이 붙은 나머지 물체는 모두 잘못입니다. 다시 세 가지로 나눴습니다.
  - 중복: 이미 찾은 물체 위에 하나 더 올린 것
  - 라벨: 8개 중 다른 물체 자리에 다른 이름을 붙인 것
  - 엉뚱한 자리: 8개 어디에도 가깝지 않은 것
- **위치:** 제안 방법은 최종 지도의 물체 자세 위치이고, 기준 방법은 물체 점군에서 가장 큰 연결 덩어리의 중심입니다.
- **제외:** DualMap 의 'unknown' 덩어리는 어떤 물체라고 주장하지 않으므로 세지 않았습니다.

## 4. 해석

- **글 문구로 찾는 방법은 "무엇이 그 물체인지"를 등록된 모델 없이 정해야 해서, 실제 공간의 비슷한 물건을 구별하지 못합니다.** FM-Fusion 은 문구에 맞는 것은 거의 다 지도에 올려 재현율은 높지만(33/40) 정밀도가 낮습니다. DualMap 은 검출기 문턱을 넘는 것만 올려 반대로 재현율이 낮습니다. 제안 방법은 등록한 CAD 모델과 비교하고 6D 자세로 한 번 더 검증하므로 배경의 비슷한 물건을 거의 올리지 않았습니다(잘못 1/40).
- **YCB-V·ObChange 와 같은 경향이 실 데이터에서도 나옵니다.** 세 데이터 모두 순위가 같습니다(5절).
- **처리 조건의 차이:** 제안 방법은 실시간으로 처리할 수 있는 프레임만 썼고(녹화당 인식 프레임 수백 장), 기준 방법들은 오프라인으로 10프레임마다 전부 처리했습니다. 기준 방법에 유리한 조건인데도 결과가 위와 같습니다.

## 5. 세 데이터 비교표 (20·21·23 문서)

### 5.1 방법

| 항목 | **제안 방법** | FM-Fusion (RA-L 2024) | DualMap (RA-L 2025) |
|---|---|---|---|
| 물체 찾기 (2D) | FastSAM-x 분할 → ViT-S 특징을 CAD 모델 템플릿과 비교 | GroundingDINO 가 글 문구로 2D 상자 → SAM 분할 | YOLO-World 가 글 문구로 2D 상자 → MobileSAM 분할 |
| 이름 정하기 | 등록한 CAD 모델과의 특징 유사도 | 검출기 라벨을 확률로 누적 | MobileCLIP 특징 |
| 3D 자세 | **PEM 자세 추정기로 6자유도 자세 + 자세 검증** | 없음 (복셀 덩어리) | 없음 (점군 덩어리) |
| 3D 표현 | CAD 모델 또는 관측 점군 | 물체별 TSDF 복셀 재구성 | 물체별 관측 점군 |
| 지도 기준 | **SLAM 키프레임에 고정** (루프 보정 시 함께 이동) | 세계 좌표 | 세계 좌표 |
| 물체 삭제·변화 반영 | **존재확률(log-odds) + 상태 T/A/L/M/D** | 없음 (누적만) | 구체 지도의 수명 상태 |
| 사전 등록 | 물체 CAD 모델 필요 | 필요 없음 (글 문구) | 필요 없음 (글 문구) |

## 6. 한계와 남은 확인

- **기준 위치가 제안 방법의 이전 실행에서 나왔습니다.** 물체 정답이 없어 이전 실행들의 중앙값을 기준으로 썼습니다. 반경을 20 cm 로 넉넉히 잡아 위치 표현 차이(CAD 모델 원점 대 관측 점군 중심, 수 cm)는 흡수되지만, 독립 정답은 아닙니다.
- **글 문구는 한 번 정한 것만 썼습니다.** 식혜는 "gold drink can" 으로 두 기준 방법 모두 한 번도 찾지 못했습니다. 문구를 바꾸면 기준 방법의 재현율이 오를 수 있습니다. 다만 잘못의 대부분(FM-Fusion 150개)은 문구가 너무 일반적이어서 생긴 것이라, 문구를 넓히면 잘못도 늘어나는 관계입니다.
- **처리 조건이 다릅니다:** 제안은 실시간, 기준 방법은 오프라인입니다(2.2절).
- **물체를 치운 장면이 없습니다.** 실 데이터 5개 모두 한 번 지나가며 지도를 만드는 장면이라, 변화 반영은 ObChange(21 문서)로만 확인했습니다.
- **녹화 4 의 SLAM 오차 구간**(80~95초)은 세 방법 모두 같은 궤적을 받았으므로 비교에는 영향이 없지만, 기준 방법은 이 구간의 프레임을 틀린 자리에 융합합니다. 제안 방법은 키프레임 고정이라 보정 뒤 함께 옮겨집니다.

### 7.3 해석

- **순위와 차이가 그대로 재현됩니다.** 제안 90.5% ≫ DualMap BGR 31.2% > DualMap 공개 24.1% > FM-Fusion 15.0%. 23 문서(95.1 / 32.8 / 26.9 / 15.4%)와 24 문서(100 / 32.8 / 23.6 / 15.3%)에 이어 세 번째 실행인데, 제안 방법은 매번 40개 중 38~40개를 맞히고 기준 방법은 14~20개(DualMap)·33~34개(FM-Fusion, 잘못 174~186개)에 머뭅니다.
- **제안 방법의 잘못 2개는 모두 경계 사례입니다.** 녹화 3 은 23 문서와 같은 우유(기준 위치에서 20 cm 를 조금 넘는 자리), 녹화 5 는 곰 인형을 공룡 인형 자리의 라벨로 올린 것 1개입니다. 24 문서 5절의 결론대로 논문 수치는 반복 실행 평균으로 내는 것이 맞습니다.
- **기준 방법은 .41 에서 다시 검출·융합했는데도 노트북과 거의 같습니다.** FM-Fusion 의 엉뚱한 자리 잘못은 150 → 158 개로 여전히 잘못의 85%이고, 식혜는 이번에도 다섯 녹화 모두 못 찾았습니다. DualMap 은 중복이 조금 늘었습니다(공개 6 → 8, BGR 14 → 17). 궤적이 바뀌고(.192 ORB-SLAM3, 인식 2.5배 빠름) 검출을 새로 돌려도 기준 방법의 특성(FM-Fusion 은 배경에 붙는 문구, DualMap 은 못 찾음)은 변하지 않습니다.
- **인식 빈도 6.7 Hz 에서도 최종 지도는 노트북(2.7 Hz)과 같은 수준입니다.** 빠른 인식이 잘못을 늘리지는 않았습니다(20·21 문서의 FP 증가는 GT 궤적 오프라인 실행에서 처리 프레임이 늘어난 경우였고, 실시간 실행에서는 나타나지 않습니다).

### 7.4 실행에서 고친 것 (기록)

- **.41 의 DualMap 환경에 `mobileclip` 모듈이 없어 10-13 첫 실행의 DualMap 10회가 전부 실패했습니다.** DualMap 은 CLIP 로드가 실패하면 검출기 초기화를 그 자리에서 끝내서 YOLO-World·MobileSAM·FastSAM 도 안 올라가고, 로그에는 `'Detector' object has no attribute 'yolo'` 로만 남습니다. .192 의 `mobileclip 0.1.0`(DualMap 3rdparty, `pip install -e . --no-deps` 한 것)을 .41 dualmap 환경(python 3.10)에 복사해 해결했습니다.
- **.41 의 DualMap 소스에 26 문서 ② 패치(YOLO 검출이 0개인 프레임 건너뛰기)가 빠져 있었습니다.** 녹화 2(어두운 조건)·녹화 3 공개 설정은 첫 프레임 검출이 0개라 `curr_detections` 속성 오류가 나고, 작업 스레드만 남아 25분 timeout 까지 멈춥니다. .192 의 `utils/object_detector.py`(BGR 패치 + ② 패치)를 그대로 복사해 두 머신의 DualMap 코드를 같게 맞췄습니다. 그 뒤 10회(두 판 × 5녹화)가 녹화당 0.6~2.8분에 끝났습니다(노트북 2~6분).
- 24 문서 4.1절은 BGR 수정이 YOLO-World·MobileSAM·FastSAM 세 모델에 BGR 영상을 넘긴다고 적었는데, 두 머신의 실제 패치는 **YOLO-World 검출 한 곳만** 바꿉니다(MobileSAM 은 YOLO 상자로 분할하고 FastSAM 은 이름 없는 덩어리만 내므로 결과에 영향이 거의 없지만, 문서 표현은 "YOLO-World 입력만 BGR" 로 읽어야 합니다).
