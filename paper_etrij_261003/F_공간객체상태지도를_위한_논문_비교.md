## 25. 공간 객체 상태 지도 논문 비교 — 요약 (2026-10-11)

> F 묶음(공간 객체 상태 지도를 위한 논문 비교)의 첫 장입니다. 공간 객체 상태 지도를 두고 제안 방법과 기존 논문 두 편(FM-Fusion, DualMap)을 세 데이터에서 비교한 개별 문서 20 · 21 · 23 · 24 를 요약하고, 관련된 22 문서(실 데이터 반복 측정, C 묶음)와 19 문서(원고 v0.3 상태 전이 수식, A 묶음)의 내용도 함께 적었습니다. 장비는 모두 노트북 RTX 3080 Ti Laptop 이고 확인용입니다. 최종 수치는 RTX 5090 에서 다시 냅니다. 각 절 끝에 출처 문서를 적었습니다.

### 1. 비교 대상 논문과 방법

| 항목 | **제안 방법** | FM-Fusion (RA-L 2024, HKUST) | DualMap (RA-L 2025, arXiv 2506.01950) |
|---|---|---|---|
| 물체 찾기 (2D) | FastSAM-x 분할 → ViT-S 특징을 CAD 모델 템플릿과 비교 (개선안 3 + 군집 먼저) | GroundingDINO 가 글 문구로 2D 상자 → SAM 분할 | YOLOv8l-World 가 글 문구로 2D 상자 → MobileSAM 분할 (+FastSAM-s) |
| 이름 정하기 | 등록한 CAD 모델과의 특징 유사도 | 검출기 라벨을 확률로 누적 | MobileCLIP 특징 |
| 3D 자세 | **PEM 자세 추정기로 6자유도 자세 + 자세 검증** | 없음 (복셀 덩어리) | 없음 (점군 덩어리) |
| 3D 표현 | CAD 모델 또는 관측 점군 | 물체별 TSDF 복셀 재구성 | 물체별 관측 점군 |
| 지도 기준 | **SLAM 키프레임에 고정** (루프 보정 때 함께 이동) | 세계 좌표 | 세계 좌표 |
| 물체 삭제·변화 반영 | **존재확률(로그 오즈) + 상태 T/A/L/M/D** | 없음 (누적만) | 구체 지도의 수명 상태 |
| 사전 등록 | 물체 CAD 모델 필요 | 필요 없음 (글 문구) | 필요 없음 (글 문구) |

#### 2.2 처리 조건

- **제안:** 실제 허브를 1배속 실시간으로 돌려, 처리할 수 있는 인식 프레임만 씁니다(인식 1.5~3.5 Hz). YCB-V·ObChange 에서는 SLAM 대신 정답 궤적을 흘려 넣었습니다.
- **FM-Fusion · DualMap:** 오프라인으로 10프레임마다 처리했습니다. 기준 방법에 유리한 조건입니다.
- 출처: 20 문서 1절, 21 문서 1~2절, 23 문서 1~2절.

#### 2.3 기존 방법을 원 설정과 다르게 돌린 부분 (논문 각주용)

**FM-Fusion**
1. 라벨: RAM 태그 대신 고정 글 문구, 닫힌 클래스를 대상 물체로 바꾸고, 라벨 혼동 행렬은 단위 행렬로 둠(이 문구에 대한 혼동 통계가 없음).
2. 크기: 복셀 0.02 → 0.01, sdf_trunc 0.04 → 0.02, 최소 점 500 → 50. 기본값으로는 YCB 물체가 모두 걸러져 지워집니다. 민감도는 아직 보지 않았습니다.
3. ObChange 누적 입력(4,484~8,974장)을 위해 지도 생성 프로그램의 "4,000프레임 초과 시 종료" 상한을 20,000 으로 올려 다시 빌드(알고리즘은 같음).

**DualMap**
1. 찾을 물체 목록을 대상 물체 글 문구 + `unknown` 으로 바꾸고, 실행 화면 표시(rerun)를 끔. 나머지는 저장소 기본 설정(구체 지도만).
2. 입력을 Replica 형식으로 변환(PNG → JPEG q95).
3. **두 판을 싣습니다.** "공개 설정"은 공개 코드 그대로(재현성 기준)이고, "BGR 수정"은 색 순서 하나만 고친 판입니다. DualMap 은 영상을 RGB 순서로 넘기는데 YOLO-World · MobileSAM · FastSAM 을 돌리는 ultralytics 는 BGR 로 읽어, 공개 코드 그대로면 빨강과 파랑이 뒤바뀐 영상으로 찾습니다. 고치면 YCB-V F1 이 0.091 → 0.168 로 오릅니다. 20 문서는 BGR 수정 판을 주 행, 공개 판을 각주로 두기를 권했습니다.
4. 지도에 `unknown` 으로 남은 물체는 어떤 물체라고 주장하지 않으므로 채점에서 뺌.

- 출처: 20 문서 4절, 21 문서 5절, 23 문서 2.2절.

- **물체를 맞게 찾는 능력은 제안이 가장 높습니다**(재현율 0.76~0.88, 정밀도 0.46~0.54). YCB-V 와 같은 경향입니다.
- **3D IoU 0.25 기준으로는 세 방법 모두 낮습니다**(제안 0.24~0.27, 나머지 0~0.06). 정답 점군이 카메라 궤적과 프레임마다 cm 단위로 흔들려서이고, 3D 일치도 비교는 YCB-V 결과를 주로 씁니다.
- **치운 물체는 세 방법 모두 거의 지우지 못했습니다.** 제안 방법은 보이는데 못 찾으면 존재확률이 내려가지만, 확정 물체가 놓침이 되려면 연속 46~66번 미검출이 필요합니다. 3080 에서 인식 약 1.9 Hz 로 50초 방문에 인식 프레임이 74~121장뿐이라 채우지 못했습니다. 지금 값은 "시야 밖 물체를 잊지 않는 것"에 맞춰져 있습니다.
- **새 물체를 올리는 쪽은 제안이 가장 낫습니다**(15/21). 후보에서 확정까지 두 번의 검출만 필요하기 때문입니다.

- **식혜("gold drink can")는 두 기준 방법 모두 다섯 녹화에서 한 번도 찾지 못했습니다.** 글 문구 선택의 영향일 수 있어 한계로 적었습니다.
- **제안 방법의 잘못 1개**(녹화 3)는 우유를 기준에서 22.9 cm 떨어진 자리에 올린 것입니다(반경 20 cm 를 조금 넘음).

**하루 뒤 재실행 (2026-10-11, 24 문서).** 같은 설정으로 제안 방법을 다시 실시간으로 돌리고, 그 궤적으로 기준 방법도 다시 돌렸습니다.

| 방법 | 23 문서 맞음 / 잘못 (점수) | 24 문서 맞음 / 잘못 (점수) |
|---|---|---|
| **제안** | 39 / 1 (95.1%) | **40 / 0 (100%)** |
| FM-Fusion | 33 / 174 (15.4%) | 33 / 176 (15.3%) |
| DualMap 공개 설정 | 14 / 12 (26.9%) | 13 / 15 (23.6%) |
| DualMap BGR 수정 | 19 / 18 (32.8%) | 20 / 21 (32.8%) |

- 순위와 차이는 그대로입니다. 제안 방법의 녹화 3 우유가 4.3 cm 안으로 들어와 잘못이 0 이 됐습니다(경계 사례).
- 녹화 1 첫 실행은 ORB-SLAM3 루프 오결합(2.97 m)으로 다시 돌렸습니다. 같은 녹화에서 22 문서(3.10 m)에 이어 두 번째입니다.

#### 3.4 실 데이터 반복 측정 — 260901, 3회 (22 문서, C 묶음)

| 구성 | 인식 빈도 | 최종 지도 맞음 / 잘못 (3회) | 평균 점수 |
|---|---|---|---|
| 원본 SAM-6D 0.5 (FastSAM-x → ViT-L → 판정 0.5 → PEM 기하 1위) | 0.87 Hz | 7/2, 6/3, 6/3 (평균 6.3 / 2.7) | 53.6% |

- **정확도는 GPU 와 관계없이 재현됩니다.** RTX 4090 에서도 개선안 3 은 세 번 모두 8 / 0(평균 점수 78.9%)이었습니다.
- **속도 이득은 작은 GPU 에서 더 큽니다.** 개선안 / 원본 인식 빈도가 노트북에서 4.0배, 4090 에서 2.1배입니다. 원본의 ViT-L 특징 단계가 GPU 에 민감하기 때문입니다.

### 4. 원고에 반영한 것 (19 문서, A 묶음)

- **원고 v0.3 (영문 8쪽, 국문 10쪽):** 인식기를 개선안 3 + 군집 먼저로 바꿨습니다. 실시간 표를 3회 반복(260901 8/0 ×3 대 6.7/2.3)으로 바꾸고, 한 장 평가 표에 GigaPose · FoundationPose 행과 BOP 데이터셋 3개를 더했습니다. 개선안 3 구조 그림은 새로 그려야 합니다.
- **5.1절 객체 상태 지도를 식 (5)~(12)로 전개했습니다.**

| 식 | 내용 |
|---|---|
| (5) | 검출 확률 P_D,k = P_D · 1[0 < z ≤ 1.5 m] · 1[화면 안, 가장자리 5% 제외] |
| (6)~(9) | 베이즈 갱신과 로그 오즈 덧셈: 검출 +ln(P_D/c) = +2.079, 보이는데 미검출 +ln(1 − P_D) = −0.083 |
| (10) | 유지 조건 q* = 3.86% (이보다 자주 검출되면 물체가 유지됨) |
| 본문 | 상태 T/A/L/M/D 와 전이 조건 (연속 미검출 46·46·66·26프레임) |
| (11) | 연결 기준 ‖t − t_z‖ ≤ 0.15 m · m(s) |
| (12) | 중복 억제 ρ · n_i ≥ max n_j, ρ = 5 |

- 이 수식이 3.2절의 "치운 물체를 못 지운 이유"를 설명합니다. 연속 미검출 46~66번이 필요한데 짧은 방문에서는 인식 프레임이 모자랍니다.

### 5. 논문에서의 쓰임

1. **7장에 "객체 지도 비교" 절을 넣습니다.** 0절의 세 데이터 비교표와 1절의 방법 비교표가 본문 표의 후보이고, 2.3절이 각주입니다.
2. **주장할 수 있는 것:** 최종 지도의 정확도(맞게 올린 물체가 많고 잘못이 적음), 6D 자세를 가진 지도, 3D 일치도(YCB-V), 새 물체를 올리는 속도(ObChange).
3. **아직 주장하지 않는 것:** 치운 물체를 지우는 변화 반영. 존재확률 설정을 확인하기 전에는 쓰지 않습니다.
4. **실시간 정확도의 재현성:** 22 문서의 3회 반복(두 GPU 에서 6번 모두 8 / 0)을 본문이나 각주로 덧붙일 수 있습니다. 녹화 실행의 인식 장치가 이 노트북이라 실제 운용 조건을 보여 줍니다.

### 6. 한계

- **실 데이터의 기준 위치가 제안 방법의 이전 실행에서 나왔습니다.** 물체 정답이 없어서이고, 반경 20 cm 로 위치 표현 차이(수 cm)는 흡수되지만 독립 정답은 아닙니다.

## 20. 공간 객체 상태 지도 비교 — 제안 방법 대 FM-Fusion 대 DualMap (YCB-V, 2026-10-09 ~ 10-10)

> 2026-10-09 에 요청한 "최종 객체 지도의 정확도 비교" 실험의 2단계 결과입니다. 최종 지도에 대상 물체가 맞게 올라갔는지(물체 단위 F1)와, 지도 좌표계에 등록된 3D 점군이 정답과 얼마나 일치하는지(3D IoU, 표면 거리)를 비교합니다. 장비는 노트북 RTX 3080 Ti Laptop 이고 확인용입니다. 최종 수치는 RTX 5090 에서 다시 냅니다. 코드·정답·채점 규칙은 `src/objmap/`(README.md)에 있습니다.

### 1. 실험 구성

|---|---|---|---|

### 3. 틀린 원인 (`src/objmap/fn_fp_breakdown.py`)

FN 은 정답 물체를 짝짓지 못한 경우입니다. 다음 기준으로 나눴습니다.
- **같은 종류 근처(위치):** 20 cm 안에 같은 종류의 예측이 있지만 짝지어지지 않음.
- **라벨 오류:** 5 cm 안에 다른 종류의 예측이 있음.
- **놓침:** 둘 다 아님.

FP 는 짝이 없는 예측입니다. 다음 기준으로 나눴습니다.
- **배경:** 20 cm 안에 정답 물체가 없음.
- **라벨 오류:** 5 cm 안에 다른 종류의 정답 물체가 있음.
- **중복/어긋남:** 그 밖.

| 방법 | FN: 라벨 오류 / 위치 / 놓침 | FP: 배경 / 라벨 오류 / 중복·어긋남 |
|---|---|---|
| 제안 ours_cad | 1 / 0 / 0 | 6 / 14 / 6 |
| 제안 ours_obs `--clean` | 1 / 1 / 0 | 4 / 11 / 9 |
| FM-Fusion | 20 / 2 / 5 | **73** / 21 / 12 |
| DualMap, 공개 설정 | 20 / 11 / **19** | 11 / 27 / 12 |
| DualMap, BGR 수정 | 15 / 13 / 17 | 15 / 21 / 18 |

- **FM-Fusion:** 물체가 있는 자리에 인스턴스는 생기지만 이름이 틀립니다(FN 의 74%). 예를 들어 참치캔을 potted meat 캔으로, 커피캔을 다른 캔으로 붙입니다. FP 의 69% 는 책상 위 다른 물건·화이트보드 같은 배경에 YCB 라벨이 붙은 것입니다. 열린 어휘 검출기가 서로 비슷한 YCB 물체를 구분하지 못하는 것이 원인입니다.
- **DualMap:** 놓침이 가장 많고(19), 같은 종류 예측이 근처에 있어도 짝지어지지 않는 경우가 11~13 입니다. 물체 점군이 다른 물체·배경과 섞이거나 쪼개진 것으로 보입니다. 라벨 오류도 FM-Fusion 수준(15~20)입니다.
- **제안:** FN 은 1~2개뿐입니다(장면 48 의 물체 20). FP 24~26 개는 대부분 그 장면에 없는 종류(7 pudding box, 8 gelatin box, 17 scissors, 21 foam brick)의 답이 다른 물체 자리에 올라간 것입니다(라벨 오류 11~14). 15 문서 §4-4 의 "YCB-V 에서는 없는 물체에 대한 그럴듯한 답이 검증을 통과한다"와 같은 현상이며, 원고 7.5절 한계에 적혀 있습니다.

### 4. 기존 방법을 원 설정과 다르게 돌린 부분 (논문에 밝혀야 함)

**FM-Fusion** (`~/DeepLearning/baselines/FM-Fusion`, 스크립트 `fmfusion_prep.py`, `fmfusion_detect.py`, `fmfusion_export.py`)
1. 라벨: RAM 태그 대신 21개 고정 프롬프트를 쓰고, 닫힌 클래스를 YCB 21종으로 바꿨습니다. 라벨 융합 혼동 행렬은 단위행렬로 두었습니다. 이 프롬프트에 대한 혼동 통계가 없기 때문입니다.
2. 크기: voxel 0.02 → 0.01, sdf_trunc 0.04 → 0.02, shape_min_points 500 → 50 으로 바꿨습니다. 기본값으로는 YCB 물체가 모두 걸러져 지워집니다. **민감도는 아직 보지 않았습니다**(논문 값 0.015 등).
3. 입력: 같은 정답 궤적, YCB-V 의 K, 깊이 배율 10000.
4. 속도(3080): 검출은 검출한 프레임당 약 1.2초, 지도 생성은 CPU 로 장면당 19~109초입니다. 5090 에서 돌리려면 GroundingDINO CUDA 연산을 CUDA 12.8 이상으로 다시 빌드해야 합니다.

**DualMap** (`~/DeepLearning/baselines/DualMap`, 스크립트 `dualmap_prep.py`, `dualmap_run.sh`, `dualmap_export.py`)
1. 클래스 목록: 21개 YCB 프롬프트 + `unknown`(공개 목록과 같은 형식). rerun 시각화는 껐습니다. 나머지는 저장소 기본값입니다.
2. 입력: Replica 형식으로 변환했습니다(PNG → JPEG q95, 깊이 배율 10000, 같은 정답 궤적).
3. **BGR 판:** DualMap 은 RGB 배열을 넘기는데, ultralytics(YOLO-World, MobileSAM, FastSAM)는 배열을 BGR 로 읽습니다. `DUALMAP_ULTRALYTICS_BGR=1` 로 색 순서를 바로잡은 판을 따로 돌렸고, F1 이 0.091 에서 0.168 로 올랐습니다. 공개 코드 그대로인 판과 고친 판 중 무엇을 표에 넣을지 정해야 합니다. 공정성 면에서는 고친 판을 주 행으로 두고 각주에 공개 판을 적는 것을 권합니다.
4. 지도에 `unknown` 으로 남은 물체는 채점 전에 뺍니다(장면 59: 12개 중 YCB 4개).

**제안 방법** (`run_ours.py`, `gt_pose_stream.py`)
- 실제 허브를 재생하되 ORB-SLAM3 대신 정답 궤적을 흘려 넣었고, 외부 파라미터는 단위 행렬입니다.
- 설정은 `OBJPOSE_LIVE_MODE=hybrid`, `--cluster-occupancy 0.3`, `--verify-cluster-first` 입니다.
- ours_obs 점군은 실행 뒤 같은 종류의 가장 가까운 지도 물체(0.15 m 안)에 붙였습니다(검출 2,841 개 중 2,811 개).
- 처리 속도는 0.42~1.86 Hz 였는데, 다른 프로세스와 GPU 를 같이 쓴 시간이 있어 믿을 수 없습니다.

### 5. 남은 일

1. DualMap 주 행으로 공개 판과 BGR 수정 판 중 어느 쪽을 쓸지 결정.
2. FM-Fusion 크기 설정 민감도(voxel 0.015 등) 확인.
3. 3단계: ObChange-Kitchen 정답 생성과 6회 방문 연속 지도 실험(지도의 변화 반영 비교).
4. RTX 5090 에서 최종 실행(FM-Fusion 은 GroundingDINO 를 다시 빌드해야 함). 처리 속도도 그때 같은 GPU 로 잽니다.
5. 원고 반영: 7장에 "객체 지도 비교" 절과 표 추가(이 문서 2절 표, 4절 각주).

### 4. 해석

1. **물체를 맞게 찾는 능력(방문별, 중심 5 cm):** 제안이 재현율(0.76~0.88)과 정밀도(0.46~0.54) 모두 가장 높습니다. FM-Fusion 은 FP 가 많고(67, 대부분 배경과 이름 오류), DualMap 은 놓침이 많습니다. YCB-V(20 문서)와 같은 경향입니다.
2. **3D 일치도:** 이 데이터에서는 정답 점군 자체가 로봇 위치 추정과 ElasticFusion 재구성에서 나와 카메라 궤적과 프레임마다 cm 단위로 흔들립니다. 그래서 IoU 0.25 짝짓기는 세 방법 모두 거의 실패하고, mIoU·SD 도 YCB-V 보다 나쁩니다. 3D 일치도 비교는 YCB-V(20 문서) 결과를 주로 쓰는 것이 맞습니다.
3. **상태 지도(치운 물체 반영):** 이 실험의 핵심 질문인데, **세 방법 모두 방문 한 번 안에 치운 물체를 지우지 못했습니다.**
   - DualMap 기본 설정(구체 지도만)은 안정된 물체를 지우지 않는 구조라 예상대로입니다. FM-Fusion 은 상태 개념이 없습니다.
   - 제안 방법은 보이는데 못 찾으면 존재확률이 내려가는 구조지만, 지금 값(P_D 0.08, 유지 조건 q* 3.86%)은 "시야를 벗어난 물체를 잊지 않는 것"에 맞춰져 있어, 1.9 Hz 인식으로 50초 방문 안에 66번 연속 미검출을 채우지 못했습니다.
   - 새 물체를 올리는 쪽(15/21)은 제안이 가장 낫습니다. 후보 → 확정에 두 번의 검출만 필요하기 때문입니다.
4. **논문에서의 쓰임:** 방문별 중심 거리 결과(F1 0.67 대 0.25 / 0.35)는 2단계와 같은 주장을 다른 데이터로 뒷받침합니다. 연속 지도의 "치운 물체 반영"은 지금 설정으로는 우위를 주장할 수 없으므로, 아래 6절의 확인 없이 쓰지 않습니다.

### 5. 원 설정과 다르게 돌린 부분 (논문 각주용)

- **공통:** 같은 정답 카메라 궤적(데이터셋 `/tf`), YCB 21종 고정 문구, 프라이팬·접시 자리 예측 채점 제외.
- **FM-Fusion:** 20 문서 4절의 변경(고정 문구, YCB 21종 클래스, 단위 우도 행렬, voxel 1 cm · sdf_trunc 2 cm · 최소 점 50)에 더해, **지도 생성 프로그램의 "4,000프레임 초과 시 종료" 상한을 20,000 으로 올려 다시 빌드**했습니다(`IntegrateInstanceMap.cpp` 71행, 원본은 `.orig_4000cap` 으로 보관). 방문 1~3 이상 누적 입력(4,484~8,974장)을 처리하기 위한 입력 크기 제한 변경이며 알고리즘은 같습니다. 깊이 배율 1000(mm).
- **DualMap:** 20 문서 4절과 같음(클래스 목록 21종 + unknown, rerun 끔, 공개 판 / BGR 수정 판). 구체 지도만 쓰는 저장소 기본값(`run_local_mapping_only: True`)이라 추상 지도의 변화 반영은 동작하지 않았습니다.
- **제안:** 정답 궤적을 SLAM 대신 흘려 넣음(키프레임 없음, 단위 외부 파라미터). 연속 지도는 방문 1~6 을 한 번 재생하고 방문 끝 시각마다 메모리 상태를 저장.

### 6. 남은 확인

1. **제안 방법 존재확률 민감도:** 메모리는 기록된 인식 결과를 재생해 지도를 만드는 구조라, GPU 없이 P_D·c 만 바꿔 같은 입력으로 연속 지도를 다시 만들 수 있습니다. 9월 19일 전 값(0.15 / 0.03)이나 더 큰 P_D 에서 치운 물체가 지워지는지, 대신 시야 밖 물체를 잘못 지우지 않는지 확인.
2. **DualMap 전체 설정(추상 지도 포함)** 으로 연속 지도를 다시 돌려 변화 반영이 동작하는지 확인.
3. RTX 5090 에서 최종 실행(인식 빈도가 오르면 방문당 인식 프레임이 늘어 제안 방법의 변화 반영도 달라질 수 있음).

### 2. 실행 구성

#### 2.1 공통 입력 (`real_prep.py`)
- **영상:** 허브가 읽는 방식 그대로 인식 카메라 RGB-D 를 꺼냈습니다. 같은 시각 보정을 쓰고, 녹화 2 는 원시 SDK 녹화라 깊이를 컬러 화면에 맞춰 옮겼습니다.
- **카메라 궤적:** 제안 방법 실행이 기록한 Mac ORB-SLAM3 자세(`slam_poses.jsonl`)를 쓰고, 실행 끝의 키프레임 자세로 루프 보정을 반영했습니다. 식으로는 T_w_c' = T_w_kf(끝) · T_w_kf(그때)⁻¹ · T_w_c 이고, 키프레임 고정 지도가 받는 보정과 같습니다. 기준 키프레임이 지워진 자세(녹화 1 은 26%, 녹화 3 은 25%)에는 시간상 가장 가까운 자세의 보정을 썼습니다. 이 자세를 인식 카메라로 옮기는 데는 실행의 T_slam_sam 을 썼습니다.
- **궤적 확인:** 물체 기준 위치를 영상에 투영해 깊이와 맞는지 10초 구간별로 봤습니다. 대부분 구간에서 90~100% 맞았습니다. 녹화 4 의 80~95초 구간만 43% 인데, SLAM 자세가 2.4 m 틀어졌다가 나중에 바로잡힌 구간입니다(프레임 몇 장). 제안 방법이 받은 SLAM 출력과 같은 것이므로 그대로 두었습니다.

### 4. 해석

- **글 문구로 찾는 방법은 "무엇이 그 물체인지"를 등록된 모델 없이 정해야 해서, 실제 공간의 비슷한 물건을 구별하지 못합니다.** FM-Fusion 은 문구에 맞는 것은 거의 다 지도에 올려 재현율은 높지만(33/40) 정밀도가 낮습니다. DualMap 은 검출기 문턱을 넘는 것만 올려 반대로 재현율이 낮습니다. 제안 방법은 등록한 CAD 모델과 비교하고 6D 자세로 한 번 더 검증하므로 배경의 비슷한 물건을 거의 올리지 않았습니다(잘못 1/40).
- **YCB-V·ObChange 와 같은 경향이 실 데이터에서도 나옵니다.** 세 데이터 모두 순위가 같습니다(5절).
- **처리 조건의 차이:** 제안 방법은 실시간으로 처리할 수 있는 프레임만 썼고(녹화당 인식 프레임 수백 장), 기준 방법들은 오프라인으로 10프레임마다 전부 처리했습니다. 기준 방법에 유리한 조건인데도 결과가 위와 같습니다.

### 5. 해석

- **최종 지도 정확도는 하루 뒤 다시 돌려도 유지됩니다.** 다섯 녹화 40개 물체가 23 문서에서 39개, 오늘 40개 맞았고, 잘못은 1개에서 0개가 됐습니다. 기준 방법도 오늘 궤적으로 다시 돌렸는데 FM-Fusion 15.3%, DualMap 23.6~32.8% 로, 23 문서의 순위와 차이(제안 95.1%, FM-Fusion 15.4%, DualMap 26.9~32.8%)는 바뀌지 않습니다.
- **실행마다 달라지는 부분은 SLAM 루프 보정과 실시간 처리에서 나옵니다.** 실시간 실행이라 처리되는 인식 프레임이 매번 조금씩 다르고(녹화당 ±5% 안팎), ORB-SLAM3 루프 결합도 실행마다 다릅니다. 녹화 1 은 이번까지 3.10 m · 2.97 m 오결합이 두 번 나왔습니다.
- **논문 수치에는 반복 실행을 쓰는 것이 좋습니다.** 23 문서의 실 데이터 표를 실행 한 번으로 내면 녹화 3 같은 경계 사례 때문에 95~100% 사이에서 달라집니다. RTX 5090 최종 측정에서는 녹화마다 반복 실행을 하고, 루프 오결합 실행을 버리는 기준(예: 키프레임 보정 1 m 이상)을 정해 두는 것이 좋습니다.

### 6. 남은 일

- 기준 방법의 글 문구는 23 문서와 같습니다. 식혜 문구를 바꿔 보는 것은 하지 않았습니다.

## 27. 객체 지도 비교 — 제안 방법을 RTX 4090 에서 다시 돌림 (YCB-V · ObChange-Kitchen, 2026-10-12)

### 0. 요약

- **맞게 찾은 물체(TP)는 두 장비가 같고, 잘못 올린 물체(FP)만 4090 에서 늘었습니다.** YCB-V 는 TP 54 · FN 1 로 같고 FP 가 26 → 44, F1 이 0.800 → 0.706 입니다(제안 CAD 모델 지도). ObChange 방문별 지도는 TP 22 · FN 3 으로 같고 FP 가 19 → 34, F1 이 0.667 → 0.543 입니다(제안 관측 점군 지도, 중심 5 cm).

### 6. 논문에서의 쓰임과 다음 일

- **본문 표는 20 · 21 문서(노트북) 값을 그대로 둡니다.** 세 방법을 같은 장비에서 돌린 것이 그 표이기 때문입니다. 이 문서는 "제안 방법의 TP 는 장비와 무관하게 재현되고, FP 는 인식 빈도에 따라 는다"는 재현성 근거로 각주나 보충에 씁니다. 22 문서(실데이터 3회 반복)의 "정확도는 GPU 와 관계없이 재현된다"는 TP 쪽 이야기이고, 없는 물체의 FP 는 빠른 GPU 에서 더 늘어난다는 점을 함께 적어야 합니다.
- **FP 가 인식 프레임 수에 비례한다**는 것은 없는 물체를 거르는 단계(자세 검증 · 합의)가 병목이라는 뜻입니다. 두 가지를 확인할 수 있습니다. (1) 기록된 인식 결과(`sam6d/detections.jsonl`)를 재생해 GPU 없이 존재확률 c 와 확정 조건(후보 → 확정 검출 2번)을 바꿔 보기(25 문서 7절의 재생 실험과 같은 방법). (2) 인식 빈도를 노트북 수준으로 제한한 실행(허브의 인식 간격 옵션)으로 FP 가 노트북 값으로 돌아오는지 보기.
- 기준 방법 코드가 오면 YCB-V · ObChange 기준 방법을 이 PC 에서 돌려 세 방법을 같은 장비(4090)에서 비교한 표를 만들고, 그 뒤 5090 에서 최종 수치를 냅니다(26 문서).
- **파일:** 결과 `src/objmap/out_4090/{ours_cad,ours_obs}/metrics_*.json`, `out_4090/obchange_scores.json`, `out_4090/ours_runs/export_stats_*.json`, 비교표 `out_4090/compare_4090.md`, 로그 `out_4090/logs/`, 스크립트 `src/objmap/{chain_ours_4090.sh, fixup_ycbv_4090.sh, fixup2_export_4090.sh, compare_4090.py}`. 실행 폴더(`out_4090/ours_runs/<scene>/`)와 지도(`ours_*/ycbv/`, `ours_*/obchange_*/`)는 git 에 넣지 않습니다(노트북과 같음).
