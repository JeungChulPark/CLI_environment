2.3 기존 방법을 원 설정과 다르게 돌린 부분 (논문 각주용)

FM-Fusion 1. 라벨: RAM 태그 대신 고정 글 문구, 닫힌 클래스를 대상 물체로 바꾸고, 라벨 혼동 행렬은 단위 행렬로 둠(이 문구에 대한 혼동 통계가 없음). 2. 크기: 복셀 0.02 → 0.01, sdf_trunc 0.04 → 0.02, 최소 점 500 → 50. 기본값으로는 YCB 물체가 모두 걸러져 지워집니다. 민감도는 아직 보지 않았습니다. 3. ObChange 누적 입력(4,484~8,974장)을 위해 지도 생성 프로그램의 "4,000프레임 초과 시 종료" 상한을 20,000 으로 올려 다시 빌드(알고리즘은 같음).

DualMap 1. 찾을 물체 목록을 대상 물체 글 문구 + unknown 으로 바꾸고, 실행 화면 표시(rerun)를 끔. 나머지는 저장소 기본 설정(구체 지도만). 2. 입력을 Replica 형식으로 변환(PNG → JPEG q95). 3. 두 판을 싣습니다. "공개 설정"은 공개 코드 그대로(재현성 기준)이고, "BGR 수정"은 색 순서 하나만 고친 판입니다. DualMap 은 영상을 RGB 순서로 넘기는데 YOLO-World · MobileSAM · FastSAM 을 돌리는 ultralytics 는 BGR 로 읽어, 공개 코드 그대로면 빨강과 파랑이 뒤바뀐 영상으로 찾습니다. 고치면 YCB-V F1 이 0.091 → 0.168 로 오릅니다. 20 문서는 BGR 수정 판을 주 행, 공개 판을 각주로 두기를 권했습니다. 4. 지도에 unknown 으로 남은 물체는 어떤 물체라고 주장하지 않으므로 채점에서 뺌.

  1. 7장에 "객체 지도 비교" 절을 넣습니다. 0절의 세 데이터 비교표와 1절의 방법 비교표가 본문 표의 후보이고, 2.3절이 각주입니다.

  4. 실시간 정확도의 재현성: 22 문서의 3회 반복(두 GPU 에서 6번 모두 8 / 0)을 본문이나 각주로 덧붙일 수 있습니다. 녹화 실행의 인식 장치가 이 노트북이라 실제 운용 조건을 보여 줍니다.

FN 은 정답 물체를 짝짓지 못한 경우입니다. 다음 기준으로 나눴습니다. - 같은 종류 근처(위치): 20 cm 안에 같은 종류의 예측이 있지만 짝지어지지 않음. - 라벨 오류: 5 cm 안에 다른 종류의 예측이 있음. - 놓침: 둘 다 아님.

FP 는 짝이 없는 예측입니다. 다음 기준으로 나눴습니다. - 배경: 20 cm 안에 정답 물체가 없음. - 라벨 오류: 5 cm 안에 다른 종류의 정답 물체가 있음. - 중복/어긋남: 그 밖.

4. 기존 방법을 원 설정과 다르게 돌린 부분 (논문에 밝혀야 함)

FM-Fusion (~/DeepLearning/baselines/FM-Fusion, 스크립트 fmfusion_prep.py, fmfusion_detect.py, fmfusion_export.py) 1. 라벨: RAM 태그 대신 21개 고정 프롬프트를 쓰고, 닫힌 클래스를 YCB 21종으로 바꿨습니다. 라벨 융합 혼동 행렬은 단위행렬로 두었습니다. 이 프롬프트에 대한 혼동 통계가 없기 때문입니다. 2. 크기: voxel 0.02 → 0.01, sdf_trunc 0.04 → 0.02, shape_min_points 500 → 50 으로 바꿨습니다. 기본값으로는 YCB 물체가 모두 걸러져 지워집니다. 민감도는 아직 보지 않았습니다(논문 값 0.015 등). 3. 입력: 같은 정답 궤적, YCB-V 의 K, 깊이 배율 10000. 4. 속도(3080): 검출은 검출한 프레임당 약 1.2초, 지도 생성은 CPU 로 장면당 19~109초입니다. 5090 에서 돌리려면 GroundingDINO CUDA 연산을 CUDA 12.8 이상으로 다시 빌드해야 합니다.

DualMap (~/DeepLearning/baselines/DualMap, 스크립트 dualmap_prep.py, dualmap_run.sh, dualmap_export.py) 1. 클래스 목록: 21개 YCB 프롬프트 + unknown(공개 목록과 같은 형식). rerun 시각화는 껐습니다. 나머지는 저장소 기본값입니다. 2. 입력: Replica 형식으로 변환했습니다(PNG → JPEG q95, 깊이 배율 10000, 같은 정답 궤적). 3. BGR 판: DualMap 은 RGB 배열을 넘기는데, ultralytics(YOLO-World, MobileSAM, FastSAM)는 배열을 BGR 로 읽습니다. DUALMAP_ULTRALYTICS_BGR=1 로 색 순서를 바로잡은 판을 따로 돌렸고, F1 이 0.091 에서 0.168 로 올랐습니다. 공개 코드 그대로인 판과 고친 판 중 무엇을 표에 넣을지 정해야 합니다. 공정성 면에서는 고친 판을 주 행으로 두고 각주에 공개 판을 적는 것을 권합니다. 4. 지도에 unknown 으로 남은 물체는 채점 전에 뺍니다(장면 59: 12개 중 YCB 4개).

제안 방법 (run_ours.py, gt_pose_stream.py) - 실제 허브를 재생하되 ORB-SLAM3 대신 정답 궤적을 흘려 넣었고, 외부 파라미터는 단위 행렬입니다. - 설정은 OBJPOSE_LIVE_MODE=hybrid, --cluster-occupancy 0.3, --verify-cluster-first 입니다. - ours_obs 점군은 실행 뒤 같은 종류의 가장 가까운 지도 물체(0.15 m 안)에 붙였습니다(검출 2,841 개 중 2,811 개). - 처리 속도는 0.42~1.86 Hz 였는데, 다른 프로세스와 GPU 를 같이 쓴 시간이 있어 믿을 수 없습니다.

  • 치운 물체: 이전 방문(k−1)에 있었고 이번 방문(k)에는 같은 종류가 10 cm 안에 없는 물체(17개). "직전 지도에 있었음"은 방문 k−1 끝 지도에 같은 종류의 예측이 5 cm 안에 있던 것, "남음"은 방문 k 끝 지도에도 그대로 있는 것입니다. 지도에 올리지 못한 물체는 남을 수도 없으므로 "남음 / 직전 지도에 있었음"으로 읽습니다.
  • 새 물체: 방문 k 에 있고 방문 k−1 에는 같은 자리에 없던 물체(21개) 중 방문 k 끝 지도에서 맞게 짝지어진 것.

4. 해석

  1. 물체를 맞게 찾는 능력(방문별, 중심 5 cm): 제안이 재현율(0.76~0.88)과 정밀도(0.46~0.54) 모두 가장 높습니다. FM-Fusion 은 FP 가 많고(67, 대부분 배경과 이름 오류), DualMap 은 놓침이 많습니다. YCB-V(20 문서)와 같은 경향입니다.
  2. 3D 일치도: 이 데이터에서는 정답 점군 자체가 로봇 위치 추정과 ElasticFusion 재구성에서 나와 카메라 궤적과 프레임마다 cm 단위로 흔들립니다. 그래서 IoU 0.25 짝짓기는 세 방법 모두 거의 실패하고, mIoU·SD 도 YCB-V 보다 나쁩니다. 3D 일치도 비교는 YCB-V(20 문서) 결과를 주로 쓰는 것이 맞습니다.
  3. 상태 지도(치운 물체 반영): 이 실험의 핵심 질문인데, 세 방법 모두 방문 한 번 안에 치운 물체를 지우지 못했습니다.
  4. DualMap 기본 설정(구체 지도만)은 안정된 물체를 지우지 않는 구조라 예상대로입니다. FM-Fusion 은 상태 개념이 없습니다.
  5. 제안 방법은 보이는데 못 찾으면 존재확률이 내려가는 구조지만, 지금 값(P_D 0.08, 유지 조건 q* 3.86%)은 "시야를 벗어난 물체를 잊지 않는 것"에 맞춰져 있어, 1.9 Hz 인식으로 50초 방문 안에 66번 연속 미검출을 채우지 못했습니다.
  6. 새 물체를 올리는 쪽(15/21)은 제안이 가장 낫습니다. 후보 → 확정에 두 번의 검출만 필요하기 때문입니다.
  7. 논문에서의 쓰임: 방문별 중심 거리 결과(F1 0.67 대 0.25 / 0.35)는 2단계와 같은 주장을 다른 데이터로 뒷받침합니다. 연속 지도의 "치운 물체 반영"은 지금 설정으로는 우위를 주장할 수 없으므로, 아래 6절의 확인 없이 쓰지 않습니다.

5. 원 설정과 다르게 돌린 부분 (논문 각주용)

  • 공통: 같은 정답 카메라 궤적(데이터셋 /tf), YCB 21종 고정 문구, 프라이팬·접시 자리 예측 채점 제외.
  • FM-Fusion: 20 문서 4절의 변경(고정 문구, YCB 21종 클래스, 단위 우도 행렬, voxel 1 cm · sdf_trunc 2 cm · 최소 점 50)에 더해, 지도 생성 프로그램의 "4,000프레임 초과 시 종료" 상한을 20,000 으로 올려 다시 빌드했습니다(IntegrateInstanceMap.cpp 71행, 원본은 .orig_4000cap 으로 보관). 방문 1~3 이상 누적 입력(4,484~8,974장)을 처리하기 위한 입력 크기 제한 변경이며 알고리즘은 같습니다. 깊이 배율 1000(mm).
