RTAB-Map: 오도메트리를 갈아끼우면 결과가 얼마나 달라지나

오도메트리 소스 3종 × 링크 공분산 2종 = 6회 실행. 매퍼 설정은 전부 동일. 결론부터: 오도메트리 링크 공분산 기본값(단위행렬)이 오도메트리 개선을 통째로 삼키고 있었다.

rtabmap 0.23.8 (Homebrew)9445 프레임 · 29.98 Hz 기준: VLP-16 KISS-ICP 66.3 m / 315.0 sunpaced offline · 매퍼 1 Hz 동기

01 — 무엇을 비교했나

오도메트리 소스 3종

  • base — RTAB-Map 기본 비주얼 오도메트리 (Odom/Strategy 0 = F2M, GFTT/BRIEF, 로컬 워드맵 2000)
  • imu — 같은 VO + xsens MTi 자세를 SensorData::setIMU로 주입 (objpose/src/imu_source.h). 스톡 RTAB-Map이 이를 OdometryF2M의 번들 조정 제약과 노드별 Link::kGravity로 쓴다.
  • ext — VO를 끄고 KISS-ICP 궤적을 오도메트리로 주입 (objpose/src/rtab_aux.h의 ExtOdom). 카메라는 여전히 매퍼가 본다.

두 번째 축은 Rtabmap::process에 넘기는 오도메트리 링크 공분산입니다. 기본값은 라이브러리 기본인 단위행렬, 실제값은 오도메트리가 스스로 보고하는 값입니다. 아래 토글로 비교하세요.

IMU 좌표계는 실행할 때마다 자가검증합니다 — imu_source.h의 gravity_report()가 정지 구간 중력을 base 프레임에서 재고, (0, 0, +9.8)이 나와야 합니다. 이번 실행: 0.533 -0.041 9.781.

03 — 진단

1차 실행에서 드러난 이상

기본 공분산으로 돌린 결과에는 설명이 안 되는 점이 있었습니다: 최적화 궤적이 라이브 궤적보다 나빴습니다. 매퍼가 좋은 오도메트리를 망가뜨리고 있었다는 뜻입니다.

원인 — 오도메트리 공분산이 단위행렬

bool process(
    const SensorData & data,
    Transform odomPose,
    const cv::Mat & odomCovariance = cv::Mat::eye(6,6,CV_64FC1),   // σ = 1 m / 1 rad
    ...);

rtab_stream은 이 기본값을 쓰고 있었습니다. 오도메트리가 스스로 보고하는 값은 전혀 다릅니다:

오도메트리링크당 선형 분산 (중앙값)= σ기본값 대비

결과는 두 가지입니다. ① 루프 링크는 RegistrationVis의 PnP 공분산(훨씬 작음)을 가지므로, 오도메트리 링크가 수십 배 헐거워진 그래프에서 루프가 모든 걸 지배합니다. ② RGBD/OptimizeMaxError = 3.0은 "잔차 ÷ 각 링크의 표준편차"를 보는데 분모가 1 m이면 어떤 루프도 3σ를 못 넘어 거짓 루프 기각이 사실상 꺼집니다.

고친 방법

rtabmap_ros의 CoreWrapper.cpp:1152-1178을 그대로 복제했습니다 — 매퍼 업데이트 사이 프레임들의 최댓값을 유지하고("Use largest covariance error (to be independent of the odometry frame rate)"), 업데이트 후 리셋합니다. OdometryF2M이 초기화 시 내는 9999("the new pose is not linked with the previous one")는 그대로 통과시킵니다 — 실행당 1회만 나옵니다.

역전이 사라지고 세 실행 모두 좋아졌습니다. 이제 모든 조합에서 opt < live 입니다. 위 토글로 직접 확인할 수 있습니다.

04 — 순환 아닌 읽기

매퍼가 좋은 오도메트리를 얼마나 건드렸나

ext의 ATE는 순환입니다 — 주입한 KISS-ICP가 곧 채점 기준이니까요. 순환이 아닌 값은 들어간 궤적과 나온 궤적의 차이, 즉 매퍼(루프 클로저 + 그래프 최적화)가 스스로 만들어낸 움직임입니다(mapper_delta.py).

05 — 정리

오도메트리 정밀도가 중요한가, 매퍼 조정이 중요한가

  • 매퍼의 가중치가 틀려 있으면 오도메트리 개선이 최종 결과에 거의 도달하지 못합니다. 공분산 한 줄을 고친 효과가 IMU를 얹은 효과보다 컸습니다.
  • 가중치가 맞으면 오도메트리 품질이 그대로 최종 정확도로 이어집니다. 라이다 오도메트리의 우위가 비로소 결과에 나타납니다.
  • 즉 오도메트리 정밀도가 상한을 정하고, 매퍼 가중치가 그 상한에 도달할지를 정합니다. 순서는 가중치가 먼저입니다 — 틀린 가중치 위에서는 오도메트리 개선의 효과를 측정조차 할 수 없기 때문입니다.
  • 루프 횟수는 오도메트리 품질과 거의 무관합니다 — 외형 기반 탐지이기 때문입니다. 공분산을 고치면 ext의 루프가 줄어드는데, 그것이 OptimizeMaxError의 거짓 루프 기각이 되살아난 증거입니다.
  • VO가 런타임의 대부분을 씁니다 — VO를 끈 ext가 압도적으로 빠릅니다. 라이다 오도메트리가 따로 있는 시스템이라면 카메라를 매퍼 전용으로 두는 것만으로 CPU가 크게 절약됩니다.
